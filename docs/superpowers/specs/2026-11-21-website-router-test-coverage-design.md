# Полный сценарный red-набор для Website и Router

## Задача и цель

Создать исполняемую тестовую базу, которая покрывает все нормативные сценарии и инварианты спецификаций Website Engine и Router Engine, включая обычные тесты, интеграционные проверки и E2E. Сначала сформировать полный набор; текущая реализация не обязана проходить его. Затем исправлять и реализовывать код, пока сценарии не станут проходить. Набор служит проверяемым выражением целевого поведения, а не метрикой строкового покрытия.

## Что входит в охват

**Website:** `SPEC-website-engine.md`, `SPEC-site-editor-workspace.md`, `SPEC-data-model.md`, `SPEC-branches-snapshots.md`, `SPEC-feature-runtime.md`, `SPEC-static-site-artifact.md`, `SPEC-public-server-rendering.md`, `SPEC-seo.md`, `SPEC-system-pages.md`, `SPEC-design-tokens.md`.

**Router:** `SPEC-router-engine.md`, его Settings API, Delivery API, locale resolution, operations, file/artifact serving, uploads, route security, CAS и readiness.

**Границы зависимостей:** проверять взаимодействие с Core file/module-data capabilities, Coordinator workflows, Loader и worker handlers (`worker.archive`, `worker.media`, `worker.prerender`) как необходимую часть сценариев двух движков. Не включать полные независимые acceptance-наборы Core, Coordinator, Loader, Content или Forms. Использовать Content/Forms только для контрактных сценариев, которые прямо необходимы Website/Router flows.

**E2E:** админский/API workflow до публичного HTTP/browser результата, включая создание/импорт входов, запуск workflow, проверку его состояния, сборку артефакта, явную Router binding и выдачу посетителю. Проверять как успешные пути, так и отказ, retry, частичный результат и сохранение предыдущей публикации. UI входит в E2E там, где соответствующий сценарий описан в Site Editor/Router спецификациях.

## Тестовые уровни и данные

1. Unit: domain/application rules, валидация, URL/path/locale matching, error mapping, state transitions и изоляция отказов.
2. Contract: строгое соответствие HTTP/OpenAPI и typed component/worker contracts; отсутствие прямых междвижковых вызовов и обходов capability.
3. Integration: адаптеры и persistence на disposable PostgreSQL и disposable object storage; проверка CAS, идемпотентности, access revocation, streaming, восстановления и cleanup.
4. E2E: реальные HTTP процессы и браузер для admin/public flow на изолированных disposable данных; никаких write-запросов к рабочему API, БД, bucket.

Тестовые данные и внешние ресурсы создаются с уникальными именами, после прогона удаляются только ресурсы, созданные этим прогоном. Отсутствие обязательной инфраструктуры должно обозначаться отдельным явным статусом, а не считаться успехом или покрытием.

## Реестр и результат red-набора

Сценарии из перечисленных спецификаций, acceptance criteria и соответствующих строк `tests/ACCEPTANCE-MATRIX.md` получают стабильные ID с указанием первоисточника, уровня, предусловий, входа, ожидаемого результата, проверяемого состояния после выполнения и тестового источника. Реестр включает негативные и конкурентные сценарии, не только happy path. Каждый нормативный сценарий имеет исполняемую проверку либо отдельную запись о конкретном техническом блокере; заглушка или `skip` не считаются проверкой.

Покрытие сценариями и прохождение тестов — отдельные метрики. Сценарий засчитывается как покрытый, когда для него существует содержательная исполняемая проверка, независимо от того, проходит ли она сейчас; красный тест остаётся покрытым сценарием и отдельно учитывается как провал реализации. Технически заблокированные сценарии остаются в знаменателе и не засчитываются в покрытие; blocker показывается отдельным статусом, а не исключается из расчёта. Это сохраняет visibility гэпов и позволяет сопоставлять долю покрытия с целевым порогом не менее 60% для каждого модуля из `tests/ACCEPTANCE-MATRIX.md`. Statement/branch coverage остаётся отдельной диагностической метрикой.

Полный acceptance-red набор запускается отдельными командами по модулю и уровню, не входящими в стандартный CI до устранения целевых провалов. Это не скрывает его статус: отдельный запуск возвращает реальные failures и инфраструктурные blockers. Обычные unit/регрессионные проверки остаются отдельно запускаемыми и не становятся красными только из-за ещё не реализованных контрактов.

## Ограничения и нецели

- Не переписывать или ослаблять утверждённые контракты, чтобы подогнать их под текущую реализацию.
- Не включать production credentials, live API/DB/storage и не использовать shared stack для write QA.
- Не реализовывать новые продуктовые возможности до фиксации соответствующего требуемого сценария.
- Не вводить самостоятельные требования к проценту покрытия строк; его можно собирать отдельно как диагностическую метрику.
- Не объединять ответственность Website и Router: Website создаёт и проверяет page artifact; Router управляет route mapping и delivery.

## Порядок работ после утверждения дизайна

1. Сверить и нормализовать список нормативных сценариев по спецификациям и acceptance matrix; отметить уже существующие проверки, пробелы и противоречия.
2. Подготовить общую тестовую инфраструктуру и команды для unit/contract/integration/E2E, с безопасной disposable DB/storage конфигурацией.
3. Добавить полный red-набор Website и Router, включая Archive/Media/Prerender workflows, route locale/CAS/security cases и реальные HTTP/browser flows.
4. Запустить набор, сохранить исходную классификацию провалов и инфраструктурных блокеров в QA report.
5. Реализовывать недостающие сценарии по спекам; после каждой группы изменений запускать соответствующий набор и повторять затронутые проверки.
6. Завершить полным повторным прогоном, проверкой OpenAPI/acceptance parity и отражением evidence и оставшихся ограничений в QA report/TODO.

## Подходы

- **Полный red-набор сначала (выбранный пользователем):** единая ранняя карта пробелов; ожидаемо много целевых провалов до реализации.
- **Вертикальные срезы (не выбраны):** меньше долгих красных тестов, но реестр полного покрытия формируется позже и пробелы видны не сразу.

## Решения, оставленные реализации

- Стабильный формат Scenario ID и точное расположение новых test files выбирать по существующим conventions модулей.
- Не включать в Website/Router scope независимые требования других модулей; интеграционные harnesses должны проверять их только через реальные границы/контракты.
- Для сценария без доступной disposable инфраструктуры сначала добавлять исполняемую проверку и безопасный prerequisite guard; не подключаться к неопределённым внешним ресурсам.
