# Операторские команды

Список обязательных runtime-параметров и правила fail-fast собраны в [SPEC-configuration.md](SPEC-configuration.md). Возьмите ключи и примерные значения из `.env.example`, замените placeholders и передавайте секреты через окружение или secret files. Пропущенный обязательный параметр должен остановить запуск с указанием имени переменной. Настройки пулов БД, таймаутов, размеров страниц и лимитов хранилища также задаются явно; CLI-команды переименования веток и сервисов используют ту же конфигурацию БД.

## Переименование ветки или файлового сервиса

ID ветки и сервиса генерирует Engine при регистрации. В конфиге и командах используются имена; ID вводить не нужно. Для сохранения связи с прежним назначением или файлами сначала остановите Engine, переименуйте запись в БД, затем обновите имя в конфигурации и запустите Engine.

В контейнерной установке:

```sh
docker compose stop server
docker compose run --rm --no-deps server rename-branch OLD_NAME NEW_NAME
# Обновить имя в BRANCHES в .env
docker compose start server
```

Для сервиса файлов выполните ту же последовательность с командой `rename-service` и обновите имя сервиса в `FILE_SERVICES`. Запускайте команду из Engine image с тем же `DATABASE_URL`, что использует установка. Команда сохраняет созданный ID, назначение ветки или файлы владельца. Передавать секреты в аргументах команды не требуется.

После изменения конфигурации проверьте readiness Engine, список веток/сервисов и ожидаемое назначение или доступ к файлам. Не запускайте переименование против рабочей базы до резервного копирования и планового окна остановки сервиса.

## Чистая инициализация после перехода модели

Новая начальная схема не поддерживает перенос старых per-feature CMS-данных. Создайте пустую disposable базу, примените начальную миграцию, загрузите format 2 ZIP, настройте ER-модель и bindings в `/site`, затем внесите записи в `/content`. Для проверок используйте только ресурсы с явными QA-именами; не сбрасывайте рабочую базу или storage Vitasil.
