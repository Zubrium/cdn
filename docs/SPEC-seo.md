# SEO, браузерный пререндеринг и системные страницы

Статус на 9 ноября 2026: snapshot-level metadata, crawler policy, sitemap generation/cache, browser prerender и системные страницы реализованы и имеют ранее пройденные focused acceptance. Model-backed SEO-поля detail-записи через stable `fieldId`, единый `RuntimeComposition.Metadata` для runtime JSON и HTML, 404 при неразрешённом lookup опубликованной записи и защита sitemap от пустых slug прошли focused disposable acceptance для текущего `catalog-detail@2.0.0`: draft не попадает в public HTML и не меняет ETag, публикация обновляет title/description/OG image и cache identity. В последней проверочной волне также измерен 50k Product `PageIndex` и подтверждён warm-cache hit; точные значения и ограничения приведены ниже. Новый Go document-rendering перенос всё ещё требует полной повторной браузерной приёмки; целевая Lighthouse median 100 пока не достигнута (предыдущая матрица имела catalog mobile 99). Acceptance не доказывает production gateway/CDN, Search Console, field Core Web Vitals, production-scale sitemap delivery или полную матрицу Vitasil detail SEO. Старые manifest-derived acceptance с ZIP Vitasil `1.x` остаются историческими результатами и не подтверждают format 2 поведение.

## Контракт

Metadata хранится в payload снапшота: canonicalDomain (http(s) origin без path/query/userinfo), language, noIndex, существующие title/description/OG/media и переопределения страниц. Индексация разрешена только когда её разрешают и ветка, и metadata сайта/страницы. Пустой canonical допускается до настройки; sitemap в этом случае пустой и диагностика объясняет причину. Canonical не строится из Host запроса.

Payload назначенного снапшота — источник metadata публичного runtime на каждой статической ветке. Legacy singleton `site_metadata_state` и относящиеся к нему dev/prod metadata-маршруты удалены из чистой схемы и текущей модели; metadata не читается из отдельного глобального состояния.

GET `robots.txt` всегда позволяет crawler прочитать публичную страницу и запрещает административные URL. `/api/` запрещён, кроме allowlist публичных GET runtime/data/theme/assets endpoints, нужных для client rendering. Sitemap указывается только для индексируемой ветки с canonical origin. Публичная неиндексируемая ветка выдаёт page-level `noindex,nofollow` и пустой sitemap; приватный preview должен быть закрыт gateway/auth, поскольку `robots.txt` не контролирует доступ. Sitemap перечисляет статические route nodes и detailLink.pathTemplate по опубликованным записям коллекции, исключает страницы, назначенные в `systemPages`, noindex, дубли, query и отсутствующие записи. Неперечисляемые произвольные regex не угадываются; диагностика возвращает предупреждение. Каждый URL повторно проверяется runtime-маршрутизатором. Код 404 выдаётся для неизвестного URL/detail, 503 — без назначения, 500 — при ошибке runtime. `catchAll` — обычный маршрут со статусом 200; если его страница явно назначена в `systemPages["404"]`, запросы, совпавшие с этим catch-all маршрутом, сохраняют содержимое override, но получают HTTP 404 и `noindex,nofollow`. Имя страницы и используемая фича сами по себе HTTP-статус не меняют. Страницы ошибок исключаются из sitemap независимо от наличия их собственного SEO override.

Индексируемая страница со статусом 200 и полностью разрешённым `CacheKey` может выдаваться с `Cache-Control: public, max-age=0, must-revalidate` и сильным ETag, производным от этого identity. Origin повторно разрешает runtime composition перед обработкой `If-None-Match`; поэтому ETag/304 не позволяют пропустить публикацию, смену назначения, метаданных или сборки. Учитываются списки validators, `*` и weak comparison согласно HTTP для GET/HEAD. Query-варианты, noindex, ошибки и core fallback всегда `no-store`, без ETag. Shared cache не получает TTL, который мог бы скрыть изменение между origin revalidations; операторский CDN при желании может задавать собственную явно согласованную политику.

## Lighthouse Performance target — 9 ноября 2026

Целевой lab acceptance по последнему уточнению пользователя: Lighthouse Performance median `100/100` на стандартных mobile и desktop профилях для Vitasil `/`, `/catalog` и `/catalog/{slug}`. Состояние Engine HTML cache фиксируется отдельно: cold miss и warm hit — это разные результаты; каждый Lighthouse запуск начинает с пустого browser cache. Выполняются пять повторов каждой комбинации маршрута/профиля/cache state, фиксируются все scores и HTTP status, затем медиана и диапазон. Performance score не обещается на произвольных устройствах/сетях и не заменяет полевые INP/LCP/CLS.

Acceptance setup использует только отдельные disposable Engine DB/storage и актуальные ZIP Vitasil. Ветка индексируемая, canonical/robots корректны, document prerender включён; ответы `text/html`, CSS, JS, JSON, XML и SVG сжимаются gzip при `Accept-Encoding`, содержат `Vary: Accept-Encoding`, имеют корректные validators, а байтовые Range responses и бинарные media не перекодируются. Все реальные фичи остаются на ABI v1. Перед изменением сборки/загрузки фиксируются размер wire payload, JS execution/TBT, LCP candidate, CLS causes и worker latency.

Не считать Lighthouse pass, если тестовый harness отдаёт только SPA shell, если indexable routes возвращают 404/noindex или если ветка запущена с `PRERENDER_ENABLED=false`. Cold browser-worker miss может влиять на TTFB независимо от client-side Performance; его latency и cache hit/miss записываются отдельно. Search Console/field CWV проверяются отдельно, когда доступен production domain.

### Реализация и изолированная матрица — 9 ноября 2026

Prerender worker переносит в итоговый HTML небольшие загруженные same-origin stylesheets, только если CSS не содержит `url(...)`, `@import` или небезопасный `</style`, и общий inline CSS остаётся в пределах 96 KiB. Таблицы с внешними зависимостями, ошибкой CSSOM или превышением лимита остаются ссылками. Сохранённые `<style data-feature-style data-loaded="true">` распознаются ABI-v1 runtime как загруженные, поэтому повторный mount не инициирует второй fetch. Это не меняет feature ABI или структуру DOM.

Исправление уменьшило изолированный Vitasil home mobile baseline Lighthouse с Performance `75`, FCP `3.2 s`, LCP `5.0 s` до серии `99–100`, медианы FCP/LCP `1.36/1.66 s`; TBT и CLS остались `0`. Наиболее низкий результат матрицы — `99/100` (home/catalog mobile cold); все остальные значения — `100`. Для каждой из 12 комбинаций (3 маршрута × 2 профиля × cold/warm Engine HTML cache) выполнено пять Lighthouse прогонов на новых disposable prerender caches и пустом browser cache. Медианы и диапазоны записаны в [QA_REPORT.md](QA_REPORT.md).

Runtime compression дополнительно проверена на реальных public listeners Vitasil: gzip декодирует runtime composition JSON, feature JS/CSS и HTML; индексируемая sitemap менее 512 байт сохраняется несжатой согласно порогу и получает `Vary: Accept-Encoding`. Middleware unit tests покрывают validators, HEAD, 304, Range, q-values и несжимаемые binary responses. Lighthouse для gzip и CSS inlining прошёл с актуальными feature ZIP, ABI-v1, одним `<main>`, без browser errors и responsive overflow.

## Crawler-доступ и SEO detail-записей

Публичная indexable-ветка разрешает поисковым renderer-ам необходимые публичные GET-ресурсы runtime: композицию, опубликованные записи, тему и системные assets. `robots.txt` может запрещать административные API, но не те публичные endpoint-ы, которые нужны для client rendering. Публичные JSON runtime/data ответы выдают `X-Robots-Tag: noindex`, чтобы их прямой URL не становился поисковым документом; этот заголовок не запрещает загрузку ответа как данных страницы. Публичные изображения остаются доступными для crawler.

`robots.txt` не является контролем доступа. Неиндексируемая, но публично доступная ветка должна позволить crawler прочитать page-level `noindex,nofollow`; приватная preview-ветка защищается gateway/auth, который возвращает отказ неавторизованному запросу. Sitemap не включает неиндексируемые ветки. `Disallow: /` не применяется как способ добиться удаления URL из индекса.

Detail route lookup берёт запись по уникальному полю из `dataInputs` binding. На этом же record binding в snapshot config можно задать `detailSEO` с `titleFieldId`, `descriptionFieldId`, `ogTitleFieldId`, `ogDescriptionFieldId` и `ogImageFieldId`. Поля относятся к bound entity; текстовые роли принимают `text`/`longText`, изображение — `media`. Настройка допустима только для `record` input с route lookup на detail page, и одной detail page разрешён один такой источник. Это структурная настройка `/site`; значения остаются в `/content`.

Runtime выбирает только запись из опубликованной model workspace и строит метаданные из её опубликованных значений. Пустые/отсутствующие значения наследуют page/site SEO. Если OG title/description не назначены отдельно и не заданы явно статически, они следуют за динамическими title/description. OG media публикуется только вместе с публично доступным файлом и выводится под canonical origin. Удалённый/неверный `fieldId` блокирует structural save; неизвестный route lookup даёт 404, не пустую карточку. Browser prerender и `/api/v2/runtime` получают одинаковую итоговую `RuntimeComposition.Metadata`; эта metadata и resolved placement content входят в document cache identity. Черновик не участвует и не инвалидирует public representation; публикация/restore повышает `contentRevision`.

Sitemap перечисляет только индексируемые, реально разрешаемые маршруты и опубликованные detail-записи. Sitemap index дробит результат, если один XML превысит протокольный предел 50 000 URL или 50 MiB; отдельная часть содержит не больше любого из этих пределов. Список URL кешируется в памяти по одной записи на статическую ветку и ключу branch, active snapshot, content revision, structural digest, canonical origin и branch/page indexing policy. Изменение любого поля инвалидирует результат; draft save его не меняет. XML делится при выдаче, его сильный ETag считается по байтам представления; GET/HEAD используют conditional 304. Noindex/error responses не становятся shared-cache content. Объём первого расчёта для очень большого каталога и shared cache между процессами остаются предметом замеров.

При построении одного PageIndex движок загружает активный snapshot и компилирует его route tree один раз. Каждый статический кандидат и detail URL сохраняют ID route node, который его породил. Route IDs сопоставляются с индексами скомпилированных маршрутов один раз; для кандидата matcher проверяет маршруты в исходном порядке только до первого совпадения, начиная с его известного маршрута, а при несовпадении подсказки продолжает остаток списка. Поэтому более ранний динамический или regex route по-прежнему может затенить статическую страницу, captures и first-match priority не меняются, а маршруты после известного совпадения больше не проверяются. Скомпилированный route уже содержит page ID: для настроенных страниц движок до runtime composition проверяет system-page и noindex исключения по подготовленным индексам и не разрешает заведомо исключённые кандидаты. Неизвестная ссылка route на отсутствующую страницу идёт по прежнему пути композиции, чтобы сохранить поведение некорректного snapshot. Уникальная sitemap-кандидатура разрешается один раз; композиция использует уже выбранный route/args и разделяет read-only состояние ветки и опубликованных model records между кандидатами. Проверка доступности аргументов media кешируется по UUID в пределах одного построения PageIndex; положительный и отрицательный результаты переиспользуются, ошибки хранилища не кешируются, а приватные, отсутствующие и неготовые файлы остаются fail-closed. Кеш readiness не переживает HTTP-запрос. Это сохраняет route priority, system-page исключения, detail projection, media validation/hydration и ошибки композиции, не перечитывая snapshot, route tree, branch policy, published model state и уже проверенные media IDs на каждый URL. После перечисления snapshot/content identity проверяется повторно; при изменении результат отклоняется с conflict и не кешируется. Cache entry записывается только после полного успешного построения и identity recheck. Это уменьшает повторную работу на cold build, но само по себе не является замером производительности или подтверждением масштаба production-каталога.

Кодовая оптимизация и focused unit fixture добавлены 8 ноября 2026. Проверки завершены: `go test -count=1 ./features/sitebuilder` и отдельный opt-in integration acceptance на 50 000 опубликованных Vitasil Product записях прошли. Cold `PageIndex` сформировал 50 001 полный отсортированный URL за 24,935 мс, повторный вызов по in-memory cache — за 1 мс. Это локальный ориентир на одной disposable PostgreSQL, не SLA и не production/load/CDN-замер; разделение холодного времени на этапы, ограниченный сценарий конкурентной нагрузки и sitemap XML delivery остаются открытыми.

Detail lookup выбирает только опубликованную запись; черновики, submissions и private media не включаются в public HTML/cache.

## Worker

Go запускает отдельный Node/Playwright процесс без shell. Путь node, скрипта, установленного модуля Playwright и browser executable задаются явно. Docker-образ включает Node.js, системный Chromium и Playwright 1.62.1 с зафиксированными зависимостями; при запуске ничего не скачивается. Для самостоятельного развёртывания эти компоненты устанавливаются оператором. Число параллельных процессов, очередь, timeout, quiet interval, viewport, max HTML bytes, cache TTL/entries и JS heap задаются конфигурацией. Runtime кешируется по ветке, snapshot ID, опубликованной contentRevision, нормализованному пути, фактическим head metadata и эффективному результату разрешения размещений. Сырая query string не является cache identity. Неудачи не кешируются; cache miss после публикации/назначения не может выдать HTML другого состояния.

Worker использует новый непостоянный browser context без cookies/credentials. Доступны GET/HEAD к своему внутреннему listener и только публичные runtime/assets/media/collection endpoints. Внешняя сеть, admin endpoints, service workers, WebSocket и POST/PUT/PATCH/DELETE блокируются. Внутренняя служебная метка запрещает рекурсивный пререндеринг; её непредсказуемый process nonce не публикуется клиенту. Браузер должен работать в sandbox; no-sandbox не добавляется.

Страница, в которой хотя бы одно размещение настроено на зарегистрированный внешний backend, не запускает Chromium prerender и получает Cache-Control: no-store. Это исключает непредсказуемое ожидание/ошибку внешнего запроса в worker и не позволяет повторно использовать HTML, актуальность которого не подтверждается ревизией контента движка. Для браузера посетителя connect-src дополняется только точными HTTP(S) origins, которые сервер проверил и фактически разрешил для привязанных размещений этой страницы; same-origin относительные запросы остаются в connect-src self. Внешние origins не добавляются в worker allowlist и не открывают ему сетевой доступ.

Пример Compose подключает `deploy/seccomp-prerender.json`: это профиль Moby `moby/profiles` с ревизии `4b8214fc4971e06172938a1f1554ccff6647ee80` с дополнительными разрешениями `clone`, `setns`, `unshare`, необходимыми для непривилегированных пространств имён Chromium. Ядро и настройки контейнерной платформы должны поддерживать непривилегированные user namespaces. При другом способе запуска оператор применяет эквивалентный профиль; не следует отключать seccomp или sandbox. Если ограничения платформы не позволяют запустить sandbox, worker сообщает ошибку и отдаётся серверная оболочка без заявления об успешном пререндеринге.

Ранее проверявшаяся Alpine-сборка Chromium не проходила seccomp/sandbox в OrbStack; она больше не является целевым образом. Текущий production image основан на `node:22-bookworm-slim`, запускает Go-сервер и Chromium под непривилегированным `app`, а Chromium остаётся в sandbox. На OrbStack arm64 повторно собраны образ и worker smoke с `deploy/seccomp-prerender.json`, без сети. Дистрибутив Linux и контейнерная платформа должны поддерживать профиль seccomp и непривилегированные user namespaces; каждый целевой способ развёртывания нужно проверять отдельно.

Compose запускает контейнер с `init: true`, чтобы init-процесс собирал осиротевшие дочерние процессы Chromium. При прямом `docker run` используйте `--init`; сам Go-сервер не является контейнерным init-процессом.

Worker ждёт готовой композиции, feature modules, запросов коллекций и quiet interval. Наличие ошибки фичи или несовпадение snapshot/contentRevision завершает генерацию ошибкой. При успешном worker результат содержит inert prerendered copy, доступную без исполнения JS, и отдельный пустой скрытый `#root`; после одной paint opportunity runtime монтирует те же feature ABI в `#root`. Формы в статической копии inert, ссылки работают, формы требуют JavaScript. Если worker выключен или завершился ошибкой, Go shell всё равно содержит direct `static-html-v1` fragments, но не содержит выполненную browser-разметку `static-module-v1` / `legacy-react-v1`. Этот fallback edge и отсутствие ошибочной заявления о полном no-JS page render должны быть включены в новую acceptance. Одинаковый HTML получает любой клиент, User-Agent не участвует в выборе.

Перенос публичного document shell на Go `html/template` не меняет три существующих feature ABI (`legacy-react-v1`, `static-module-v1`, `static-html-v1`), их lifecycle, context, assets, route/data/media и worker prerender/cache hit/miss semantics; новые ABI и manifest root-tag поля не вводятся. Host `legacy-react-v1` загружается лениво только для соответствующей фичи. В итоговом DOM у `#root` нет дополнительных page/slot wrappers. Placement lifecycle roots остаются одиночными нейтральными `<div>`: основные размещения находятся внутри ровно одного page-level `<main>`, неосновные — непосредственно под `#root`, без вложенных placement roots. Go shell, Chromium prerender и no-JS fallback должны сохранять это устройство и видимый контент.

Текущий runtime поддерживает `legacy-react-v1`, `static-module-v1` и `static-html-v1` для ZIP, собранных браузерным toolchain: worker ждёт readiness lifecycle module, а HTML-фрагмент статичен и не исполняет шаблоны или скрипты. Go template формирует document shell; feature execution по-прежнему происходит текущим runtime в Chromium worker. Подробности контрактов и ранее выполненных acceptance см. [SPEC-feature-runtime.md](SPEC-feature-runtime.md) и [QA_REPORT.md](QA_REPORT.md).

Worker блокирует запросы за пределы текущего origin и разрешает только runtime API, выбранные content/media endpoints и статические runtime assets, включая `/favicon.svg`. Любой метод кроме GET/HEAD, неизвестный путь, превышение числа запросов или сетевого лимита отклоняется и завершает генерацию ошибкой.

Кеш HTML находится в памяти процесса и ограничен настроенными TTL и числом записей. Ключ учитывает branch ID, snapshot ID, content revision, структурный digest, фактические SEO head metadata, нормализованный путь и эффективный результат разрешения маршрута: route arguments, собранные данные размещений/коллекций, тему и системные ресурсы. Сырая query string не входит в ключ. Параметры, связанные с аргументами размещений в конфигурации выбранного snapshot, влияют на ключ через разрешённые arguments и runtime data. Неиспользуемые параметры, включая tracking-параметры, не создают отдельные варианты; порядок независимых query-параметров не влияет на идентичность. Порядок повторённых значений, связанных с array-аргументом, сохраняется, поскольку он может влиять на вывод. `__designPreview` учитывается через эффективную тему, поэтому разные preview-темы не сталкиваются. Путь запроса всегда включён в ключ. Query-ответы сохраняют свою SEO-политику (indexable URL с query получает `noindex,follow`); политика отражается в head metadata. После изменения этих данных получается новый ключ. Успешные идентичные одновременные запросы объединяются в одну генерацию. При заполнении лимита вытесняется запись, к которой дольше всего не обращались (LRU); ошибки не кешируются. Межпроцессного общего кеша и прогрева маршрутов нет.

При отказе worker выдаётся актуальная server shell с метаданными и диагностическим заголовком; результат не называется успешно пререндеренным. Некорректные URL и ошибки имеют содержательные серверные fallback страницы в стиле админки. На клиенте error boundary сохраняет fallback при ошибке пользовательской error-фичи. Переопределение может использовать зарегистрированную в снапшоте страницу системного состояния.

При сбое worker сервер журналирует только фиксированное название последнего этапа и категорию (`timeout` или `worker_error`). Диагностика процесса может содержать пользовательские данные, URL и ключи и целиком в журнал не записывается. Таймаут принудительно завершает всю группу процессов worker; превышение очереди и отменённые клиентом запросы не объявляются успешной генерацией.

Общий таймаут, таймаут отдельной попытки и максимальное число попыток задаются явно. Если browser завис до создания контекста, сервер завершает группу процессов и может повторить запуск в пределах общего таймаута и исходного слота очереди. Ошибки страницы, запреты запросов и таймауты после создания контекста не повторяются автоматически. Каждый повтор получает отдельный непостоянный контекст и те же ограничения доступа; частичный HTML не кешируется.

В редакторе маршрутов администратор выбирает страницы состояний из страниц с хотя бы одним статическим маршрутом; пустое значение возвращает встроенную страницу. Выбор хранится в `config.systemPages` как часть локального изменения структуры и сохраняется созданием дочернего снапшота с обычной защитой несохранённых изменений. При удалении страницы с назначением нужно сначала снять это назначение; если маршрут выбранной страницы позже удалён или стал динамическим, интерфейс показывает предупреждение, а runtime использует встроенный fallback. Catch-all остаётся ответом 200 по умолчанию; если его страница назначена в systemPages[404], маршрут сохраняет содержимое override, но возвращает HTTP 404 и noindex. Сам по себе catch-all не означает 404. Для ветки без назначенного снапшота всегда используется встроенная страница HTTP 503 «Сайт ещё не настроен» с noindex; 503 не настраивается в startup config или снапшоте. Текущие источники runtime не формируют отдельное состояние 403; выбор пользовательской страницы для него доступен после реализации соответствующего состояния, но не заявляется рабочим сейчас.

## Диагностика renderer и локальный cache benchmark — 7 ноября 2026

При уровне логирования `debug` renderer пишет одну структурированную запись `prerender render` для каждого вызова. `cache_result` принимает `hit`, `miss`, `coalesced` или `bypass`; `outcome` отдельно принимает `success` или `error`. Поэтому ошибка генерации видна как `cache_result=miss outcome=error` (либо `bypass outcome=error`) и никогда не сохраняется как отрицательная cache entry. Холодный cache miss, прогретый cache hit и конкурентные followers различимы по этим полям; followers общей генерации получают `coalesced`. Каждая запись также содержит `render_duration_ms`; cache miss содержит `cache_miss_reason` (`absent` или `expired`) и `queue_wait_ms`, а bypass — `cache_miss_reason=document_uncacheable`; попытки worker — суммарные `worker_duration_ms`, `worker_attempts` и последний безопасный `worker_stage`. Успешная генерация также пишет `html_bytes`; неуспех получает ограниченный `error_code` (`timeout`, `cancelled`, `queue_full`, `invalid_output`, `worker_error` и т.п.). Отдельное событие `prerender cache eviction` содержит только причину (`expired`/`lru`) и число записей. События не включают URL, query, cache key, snapshot ID, HTML, содержимое stderr или данные посетителей. Ошибки worker продолжают иметь краткое warning-событие с фиксированной стадией и причиной.

`queue_wait_ms` измеряется от принятия запроса bounded очередью до получения worker slot; `worker_duration_ms` охватывает попытки Node/Chromium и сериализацию результата. Worker передаёт только фиксированные строки `timing phase=<name> ms=<integer>` для `browser_launch`, `context_creation`, `navigation`, `runtime_data`, `readiness` и `serialization`. Они отражают `chromium.launch`; создание browser context/page; `page.goto`; завершение разрешённых same-origin GET к точным runtime/data маршрутам `/api/v2/runtime` и `/api/v2/content/{snapshot}/records`; ожидание `engineReady`, совпадения snapshot/revision и сетевого quiet interval; формирование и сериализацию DOM с проверкой размера HTML. URL используется только для внутреннего сопоставления runtime/data запросов: URL, query, ID, тела ответов и ошибки запросов в diagnostics не попадают. `readiness` включает подтверждение актуальности данных и последующее ожидание settling, поэтому его длительность не является чистым временем ответа API. Go отдельно пишет debug event `prerender phase timing` с `phase=document_resolve` и `duration_ms`, охватывающий полный вызов resolver до запуска worker. Parser принимает только allowlist фаз и ограниченные целые миллисекунды; произвольный stderr worker не выводится.

В текущем implementation sweep код и focused unit fixtures уже содержат эти поля для cold/warm cache, ошибки worker, разрешённых data-response timings, privacy markers и coalesced concurrent requests. Эти проверки в текущем отложенном QA pass ещё не запускались; применимые команды перечислены ниже. Логи дают событийные данные для локального профилирования, но непрерывный сбор, агрегация и экспорт в metrics backend не реализованы. Из них также нельзя получить production CPU/memory/load или серверное время БД внутри runtime/data handlers.

Локальный benchmark `go test ./pkg/runtime -run '^$' -bench 'Prerender' -benchmem` на `darwin/arm64`, Apple M4, показал в одном запуске synthetic shell worker: холодный cache miss `2.80 ms/op`, `86,380 B/op`, `134 allocs/op`; прогретый cache hit `185 ns/op`, `128 B/op`, `2 allocs/op`. Это проверяет стоимость пути cache miss/hit без Playwright и Vitasil, не является сравнительным production benchmark и не задаёт порог производительности. Абсолютные цифры зависят от машины и не заменяют Lighthouse/PageSpeed, mobile/browser Performance и измерения реального Vitasil.

Проверки этого изменения прошли: `go test ./pkg/runtime -count=1`, `go test ./pkg/runtime -run 'PrerenderCache|PrerenderQueue' -count=1`, `go test ./pkg/runtime -run '^$' -bench 'Prerender' -benchmem`, `go test -race ./pkg/runtime -run 'Prerender(Cache|Queue|Concurrent|Logs)' -count=1`, `go vet ./pkg/runtime`, форматирование `gofmt` и `git diff --check`. Benchmark не покрывает Chromium startup, реальные Vitasil страницы, HTTP round-trips или device metrics.

## Query robots и cache acceptance на актуальных ZIP Vitasil — 7 ноября 2026

До Go-rendered bootstrap query-варианты уже получали в `PageDocument` `noindex,follow`, `no-store` и не получали ETag, однако прежний клиентский runtime повторно запрашивал `/api/v2/runtime` и заменял robots metadata без query policy. ## Same-branch multi-instance Vitasil cache acceptance — 7 ноября 2026

`TestVitasilPrerenderCacheMultiInstanceAcceptance` проверяет две независимые публичные router/worker-инстанции с одним и тем же branch ID, одновременно читающие одну disposable Engine БД. Каждый runtime имеет собственный `Prerenderer` и in-process HTML cache. Настроен одинаковый root snapshot с текущими ZIP `catalog@1.0.10` и `catalog-detail@1.0.9`; обе инстанции сначала отдельно генерируют и прогревают один опубликованный detail route.

Проверка поочерёдно публикует новую версию Vitasil content в root, назначает тот же branch на независимый child snapshot с другим published content и canonical domain, затем откатывает назначение к root. После публикации обе инстанции должны вернуть новый HTML и одинаковый изменённый strong ETag; после назначения обе должны показать child HTML и canonical с новым identity без parent content; после rollback обе должны вернуть parent HTML и parent ETag, а запрос с уже устаревшим child validator не должен получать 304. Для успешных индексируемых страниц проверяются HTTP 200, `X-Engine-Prerender: hit`, `Cache-Control: public, max-age=0, must-revalidate` и `index,follow`. Затем новый router/worker с пустым cache должен холодно разрешить текущее branch assignment из той же БД, сгенерировать правильный parent HTML/ETag и подтвердить miss в diagnostics. Это воспроизводит пересоздание локального worker/cache внутри тестового Engine процесса; production Engine process не перезапускается.

Acceptance подтверждает межинстанционную согласованность через повторное разрешение текущего branch/snapshot/content identity из общей БД при каждом запросе. Она не добавляет и не проверяет shared/distributed HTML cache, push invalidation, cache warming или production gateway/CDN. Каждый cache по-прежнему живёт в памяти своего процесса; non-indexable/no-store policy, query handling, worker failures и coalescing остаются покрыты существующими acceptance и здесь не дублируются.

Команда прошла: `go test -count=1 -v ./cmd/integration -run '^TestVitasilPrerenderCacheMultiInstanceAcceptance$'` (PASS, 7.87s). Acceptance использовал disposable БД `website_engine_seo_multi_instance_vitasil_qa_20261107_root01` на `127.0.0.1:35474`; до и после теста подтверждён ноль посторонних сессий, затем удалена только эта БД. ZIP `catalog@1.0.10` и `catalog-detail@1.0.9` прочитаны из текущей сборки Vitasil без изменений, storage — in-memory fake; рабочие Vitasil API, БД, S3 и volumes не использовались.

Проверка запускает два независимых public router/worker и два локальных prerender cache в одном Go integration test process, с общей БД и одним branch ID. Она доказывает согласованность при повторном разрешении текущего состояния через БД, но не проверяет два отдельных deployed `cmd/api` процесса, distributed/shared cache, CDN/gateway или межпроцессную push-инвалидацию. При каждом процессе HTML cache остаётся локальным.
