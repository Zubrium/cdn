# Route targets: pages and public files

Status: page/file route-target support is implemented in the working tree. Route compilation, reference/remapping, disposable PostgreSQL routing, direct public-file handler (`GET`/`HEAD`, Range, ETag and disposition), browser creation/edit, and the local frontend suite pass. A combined snapshot-to-route acceptance against a real disposable object store remains open.

This contract extends the existing snapshot route tree without adding a second public router. A rendered route has one target: a page or a ready public media object. The page target remains the normal feature-composition path. The file target is a direct public-file delivery endpoint.

## Route tree

`RouteTreeNode` keeps the existing `id`, `type`, `path`, `value`, `name`, `pattern`, `child` and `pageId` fields. It adds:

- `fileId?: string` — the generated media object ID.
- `fileDisposition?: "inline" | "attachment"` — direct browser display or forced download; omitted or empty means `inline`.

For every compiled route node:

- Exactly one of `pageId` and `fileId` may be set.
- `fileDisposition` is valid only with `fileId` and accepts only `inline` or `attachment`.
- The virtual site root cannot target either a page or a file.
- A file target must be a UUID, must be terminal, and cannot expose named path captures.
- The site editor accepts only a fixed absolute URL for a file route. Page routes retain static segments, parameters, regex segments and catch-all support.
- Route IDs remain generated by the editor. The selected file and internal IDs are not user-editable primary labels.

The public file UI selects an existing media item; uploads remain owned by `/media`. At structural snapshot creation the server checks that the target exists, has status `ready`, and is public. A missing, private, failed or still-processing file rejects the snapshot without creating a child.

## Public behavior

For `GET` and `HEAD`, public request handling resolves the active branch snapshot and matches the request path before HTML document resolution. A matched file route is served directly by the file handler with the existing safe public-file semantics:

- stored `Content-Type`, `ETag`, conditional requests and byte ranges;
- fixed `Content-Disposition` chosen by `fileDisposition`;
- no feature composition, feature runtime, page metadata, sitemap page entry or HTML prerender;
- no redirect to a private or unrelated object.

The production file handler streams the object. A legacy/test media adapter may use the existing public redirect fallback; that fallback is not the canonical delivery contract. Invalid active-snapshot route configuration must not be silently reinterpreted as a page route.

Page-target routes keep the current HTML behavior: match the snapshot, compose the referenced page and its placements, resolve published model content, emit metadata and allow the existing prerender/cache path. A compiled route without a page target is rejected by the runtime composition resolver if it reaches HTML handling.

## Persistence, references and permissions

- Route targets and disposition are structural snapshot payload. Saving them uses the normal immutable child-snapshot flow and never assigns a branch.
- Sitepack export/import treats route `fileId` values as media references, exports the referenced objects and remaps the IDs on import.
- File reference discovery includes route targets so deletion warnings and confirmation cannot overlook a public URL.
- Replacing or removing a file route leaves the media object intact. Deleting a referenced media object follows the existing reference-confirmation and snapshot-invalidation rules.
- `/site` page and file route editing uses the existing site-manager guards, revision checks, local-draft protection and unsaved-change warnings.

## Failure cases

- Both `pageId` and `fileId` set: reject the route.
- Neither target set on a rendered leaf: reject the route.
- `fileDisposition` on a page route or an unsupported value: reject the route.
- Dynamic capture in a file route: reject the route.
- Child route below a file route: reject the tree.
- Missing, non-ready, failed, or private target file during structural save: reject the snapshot.
- Duplicate absolute URL in the editor: show an inline validation error and preserve the current draft.
- Missing route target at editor deep link: show a "not found" state with a return action; do not mutate the snapshot.
- File read/storage error: return the controlled file/public-document error path; never expose a private object.

## Acceptance criteria

1. A site manager creates a file route through the UI, picks a ready public file, chooses inline or attachment, saves a child snapshot, reloads the deep link, and sees the same target and disposition.
2. The route editor rejects parameters, regex, catch-all, child routes and duplicate URLs for a file target without losing the local draft.
3. `GET` and `HEAD` serve the selected file with the expected content type, ETag, range behavior and disposition; no feature HTML or runtime composition is invoked.
4. Page routes continue to render their existing features and support their existing dynamic syntax.
5. Snapshot creation rejects missing/private/non-ready files. File references and sitepack remapping include route targets.
6. Deletion guards list a route target before media deletion, and removing a file route itself preserves the media file.
7. Tests run against an isolated database and object store; no working Vitasil data or storage is used.
