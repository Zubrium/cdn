# Фичи, модель данных, снапшоты и ветки

Эта страница описывает текущий контракт Website Engine. Подробные требования и состояние проверок ведутся в [TODO](TODO-admin-snapshots-content-files.md), спецификациях [модели данных](SPEC-data-model.md), [веток и снапшотов](SPEC-branches-snapshots.md) и [runtime фичей](SPEC-feature-runtime.md).

## Feature ZIP и manifest

Каждая сборка фичи — неизменяемый ZIP с `manifest.json` и готовыми browser assets. Реестр ZIP хранит версии, но загрузка сборки сама по себе не добавляет её в сайт. Снапшот закрепляет версию для каждого размещения.

Используется manifest format 2. В нём:

- `arguments` описывает настройки фичи, редактируемые только в `/site`;
- `dataInputs` описывает типизированную форму runtime-данных, но не редактор CMS;
- `form.submissionSchema` строго проверяет публичную отправку формы;
- runtime metadata и design tokens описывают исполняемую сборку.

CMS-схемы `content.*` и manifest format 1 не принимаются и не конвертируются. Отдельного редактора схем фич нет. Текущий Engine сохраняет совместимость с уже поддерживаемыми runtime ABI; актуальные Vitasil ZIP собраны с `static-module-v1`. Подробнее — [контракт сборок](SPEC-feature-runtime.md) и [руководство автора](FEATURE-RUNTIME-AUTHORING.md).

Go `html/template` отвечает за формирование публичного документа, не за замену runtime фич. Сохраняются текущие ABI `legacy-react-v1`, `static-module-v1` и `static-html-v1`, их lifecycle и передача context, route/data/media/assets. В DOM не добавляются page/slot wrappers: `#root` не оборачивается, каждый placement сохраняет ровно один neutral `<div>` mount root; `main` roots находятся внутри одного page-level `<main>`, остальные являются прямыми детьми `#root`. Новый ABI и поле manifest для выбора root tag не вводятся. Chromium prerender остаётся ответственным за исполнение существующих фич и продолжает использовать прежние cache semantics.

## ER-модель и редакторы

ER-модель принадлежит снапшоту. В `/site/data-model` задаются сущности, типы полей, связи и расположение карточек; структурное сохранение создаёт новый снапшот. В редакторе сайта также задаются все аргументы фич и bindings из `dataInputs` к сущностям и полям модели. Редактор показывает связи источников и сопоставления полей, но не меняет редакционные значения.

`/content` автоматически строит формы записей по модели выбранного снапшота. Записи, черновики, публикация, история и выбор/порядок записей для размещений управляются здесь. Все поля модели необязательны; переданные значения проверяются по типу и ограничениям. Черновик сохраняется отдельно; публикация обновляет тот же снапшот без создания нового.

Сущность `singleton` автоматически получает одну пустую запись в черновике снапшота и не публикуется до явного действия. В `/content` для неё одна форма без добавления или удаления записи; подтверждённая очистка полей и связей сохраняет ID. Для singleton входы фич `record` и `scalar` связываются автоматически; `collection` остаётся массивом из нуля или одной записи. Переход `many` → `singleton` разрешён только при не более чем одной записи в текущем черновике и публикации; история прошлых публикаций сохраняется.

Каталог, карточка товара и главная используют одну сущность `Product`. Каталог показывает опубликованный набор, слайдер получает выбранное упорядоченное подмножество, а detail-размещение находит ту же запись по уникальному полю маршрута.

Фичи и SEO-настройки могут выбирать уже загруженное публичное медиа. Загрузка, обработка, замена и удаление выполняются только в `/media`; выбор существующего файла не загружает его повторно.

## Снапшоты

Снапшоты образуют дерево. Структурные изменения страниц, маршрутов, аргументов, bindings, модели и дизайн-системы сохраняются отдельным корнем или дочерним снапшотом. У снапшота нет серверного конфигурационного черновика. Потомок получает независимую копию модели, опубликованных записей, черновиков и выборок размещений; дальнейшие изменения родителя и потомка разделены.

Контент имеет собственные ревизии и историю публикаций, отдельные от структурного digest снапшота. Публикация не меняет назначения веток. Runtime и prerender используют только опубликованные записи выбранного снапшота.

Удаление защищает снапшот, назначенный ветке, и его непосредственного родителя. Разрешённое удаление промежуточного узла перепривязывает его потомков и сохраняет их состояние.

## Статические ветки

Оператор задаёт конечный список веток, их имена, порты, CORS и политику индексации в startup-конфигурации. Админка не создаёт новые ветки. Каждая ветка может обслуживать самостоятельный сайт или отдельную стадию одного сайта.

Только `/snapshots/branches` назначает снапшоты веткам. Назначение проверяет актуальную ревизию и не меняется при редактировании сайта, публикации контента или создании потомка. Внешний домен и TLS задаёт gateway; canonical-домен задаётся в настройках сайта.

## Основные административные API

Префикс: `/api/v2/admin`.

| Маршрут | Назначение |
| --- | --- |
| `GET/POST /feature-builds` | Список и регистрация неизменяемых ZIP |
| `GET /branches` | Статически сконфигурированные ветки и назначения |
| `PUT /branches/{id}/snapshot` | Явное назначение снапшота ветке |
| `GET /site/snapshots` | Дерево снапшотов |
| `POST /site/snapshots` | Создать корневой снапшот или потомка |
| `GET/DELETE /site/snapshots/{id}` | Прочитать или удалить разрешённый снапшот |
| `GET/POST /site/snapshots/{id}/design-system` | Прочитать или сохранить дизайн-систему новым снапшотом |
| `GET /content/snapshots` | Снапшоты, доступные редактору контента |
| `GET/PUT /content/snapshots/{id}/model` | Прочитать или сохранить черновик записей и выборок с проверкой ревизии |
| `POST /content/snapshots/{id}/model/publish` | Опубликовать записи и выборки внутри того же снапшота |
| `GET /content/snapshots/{id}/model/history` | История публикаций модельных данных |
| `POST /content/snapshots/{id}/model/history/{publicationId}/restore` | Восстановить публикацию в новый черновик |
| `GET /site/snapshots/{id}/export`, `POST /site/snapshots/import` | Экспортировать или импортировать sitepack |

Per-feature CMS endpoints, relation envelopes и глобальные dev/prod deploy endpoints удалены из действующего контракта. Старые данные не переносятся; новая установка использует чистую начальную миграцию.

## Публичная выдача и заявки

Публичный runtime получает композицию назначенного ветке снапшота через `GET /api/v2/runtime?path=...`. HTML, метаданные, пререндер, `robots.txt` и sitemap строятся по опубликованному состоянию. Неиндексируемая ветка запрещает обход и отдаёт пустой sitemap. Черновые записи не становятся публичными.

Заявки и пользователи не принадлежат снапшоту. Публичная форма валидируется по `form.submissionSchema`, а её редакционный текст хранится в модели сайта. Заявки изолируются по branch ID и обрабатываются существующими ролями и ограничениями.
