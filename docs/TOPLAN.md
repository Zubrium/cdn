## Архитектурные границы, обязательные для новых предложений

- Схема данных принадлежит снапшоту. Структурные изменения модели и bindings сохраняются дочерним снапшотом; записи, черновики и публикации принадлежат выбранному снапшоту и изолируются при fork.
- Решение по singleton: у сущности `many` или `singleton`. Новый singleton получает одну пустую черновую запись при сохранении структуры, но запись не публикуется автоматически. `/content` показывает одну форму без добавления, дублирования, перемещения и удаления записи. Подтверждённая очистка значений и связей сохраняет ID записи и остаётся черновиком до ручной публикации. Значения полей контента необязательны; формы отправки по-прежнему валидируются отдельно по `form.submissionSchema`. Реализация singleton и unit/API/browser acceptance fixtures, включая сценарий клавиатурного переключения ER-модели и отдельную публикацию, внесены в рабочее дерево; все focused checks остаются отложенными до общего verification sweep. Пункт TODO остаётся открытым до подтверждения критериев проверками.
- `/site` отвечает за графическую ER-модель, аргументы фич и структурные bindings. `/content` отвечает за значения записей, черновики, публикацию и выбор/порядок записей для размещений. Назначение снапшотов веткам происходит только в `/snapshots/branches`.
- Ветка — статическая запись startup-конфигурации с собственным портом, назначением снапшота и политикой индексации. Публичный URL и TLS задаёт gateway; canonical origin настраивается в metadata снапшота. Модель фиксированных `dev`/`prod` не является целевой.
- Manifest format 2 объявляет метаданные фичи, `/site` `arguments`, типизированные `dataInputs`, static runtime и, для форм, строгую `form.submissionSchema`. ER-модель снапшота формирует редактор записей. В манифестах не описываются CMS-формы или значения записей. Каталог, карточка товара и слайдер Vitasil используют одну сущность `Product`.
- Engine принимает готовые feature ZIP и не запускает на сервере React SSR/hydration. Go `html/template` может формировать публичный HTML-документ, но не заменяет feature runtime: `legacy-react-v1`, `static-module-v1` и `static-html-v1`, их lifecycle и передачу данных остаются без изменений. DOM-рефакторинг ограничен лишними engine wrappers: `#root` без page/slot containers, один neutral `<div>` mount root на placement, `main` placements внутри одного `<main>`, остальные roots напрямую в `#root`. Chromium worker продолжает выполнять те же модули и возвращать опубликованный runtime composition; новых ABI и manifest root-tag полей не вводить.

## Уже покрыто текущими контрактами

Эти направления не нужно повторно предлагать как новую архитектуру. Их фактическое состояние и конкретные проверки следует сверять со спецификациями, TODO и QA-отчётом:

- Snapshot metadata, branch indexing policy, `robots.txt`, sitemap, canonical, detail SEO bindings через стабильные ID полей, HTTP-статусы системных страниц, prerender и cache identity описаны в [SPEC-seo.md](SPEC-seo.md). Это не доказывает корректность production gateway/CDN, Search Console или показателей Core Web Vitals.
- Format 2, static-module runtime, модельная проекция в существующий ABI и разделение аргументов, данных и редакционной схемы описаны в [SPEC-data-model.md](SPEC-data-model.md), [SPEC-feature-runtime.md](SPEC-feature-runtime.md) и спецификации Vitasil. Покрытие отдельных ZIP/маршрутов см. в [QA_REPORT.md](QA_REPORT.md); оставшиеся критерии указаны в TODO.
- Media registry, публичные производные файлы и media rendition контракты уже имеют отдельные API и критерии. Предложения ниже не должны добавлять загрузку файлов в `/site` или вводить параллельный реестр изображений.

## Открытые предложения

### 1. Structured data

При необходимости поддержать JSON-LD для `Organization`, `WebSite`, `WebPage`, `BreadcrumbList`, `Product` или `Offer`. Сначала определить минимальный перечень типов и источник каждого значения. Разметка должна строиться из metadata снапшота и опубликованных model-backed записей и отражать только то, что реально видно на странице. `FAQPage`, `Article` и `LocalBusiness` добавлять только при наличии соответствующего видимого содержания и согласованной модели. Не помещать CMS-схему в манифест и не использовать черновые данные.

### 2. Изображения и скорость

Провести production-подобные измерения LCP, INP, CLS и TTFB с реальными конфигурацией gateway, CDN, публичными медиа и representative-мобильным профилем. По результатам решить, нужны ли дополнительные размеры `srcset`, форматы WebP/AVIF, preload LCP-файла или оптимизация критического CSS. Использовать текущие renditions и политики доступа; alt-текст хранить как обычное поле видимого контента, не делать его универсально обязательным на уровне схемы.

### 3. Внешний мониторинг поиска

Рассмотреть отдельную операционную инструкцию для Google Search Console, Яндекс Вебмастера и Bing Webmaster: подтверждение домена, отправка sitemap, проверка URL и периодический просмотр ошибок. Автоматическую интеграцию, credentials, позиции и CTR не считать частью текущего Engine API без отдельного решения о владельце секретов, хранении, разрешениях и объёме данных.

### 4. SEO-подсказки в админке

Специальная SEO-CMS, SEO-схема в manifest и обязательные SEO-поля каждой записи не входят в согласованный контракт. Если появится подтверждённая потребность, отдельно спроектировать read-only диагностику текущих snapshot metadata, маршрутов, опубликованных detail records и alt-текста. Не дублировать поля ER-модели, не менять `form.submissionSchema` и не подменять ручную публикацию автоматической.

### 5. AI-поиск и внешняя авторитетность

Это рекомендации по содержанию и деятельности владельца сайта, а не обещание ранжирования или функция движка. Публиковать точные характеристики, цены и условия; указывать источники и актуальность; поддерживать ясную структуру и стабильные canonical URL; собирать реальные отзывы и отраслевые упоминания. Не создавать массовые дубли страниц и не обещать первое место в Google, Яндексе или ответах AI-сервисов.
