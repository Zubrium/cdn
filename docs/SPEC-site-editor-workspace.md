# Site editor and model-driven content

Status: the current ownership model is implemented in the working tree. The authoritative ER and record contract is [SPEC-data-model.md](SPEC-data-model.md); this document defines the editor boundaries and user workflows. Earlier per-feature CMS schema, content relation, and collection-source descriptions are retired and are not migration requirements.

## Ownership

- `/site` owns the snapshot's structure: pages, routes, placements, SEO, design, the graphical data model, feature arguments, and typed `dataInputs` bindings from each placement to model entities and fields. All feature arguments are configured here.
- `/content` owns model records, relations between records, local drafts, publication history, and record selection/order for each placement. It generates its forms from the selected snapshot's model. It does not edit feature arguments or model structure.
- `/media` owns uploads, file metadata, and deletion. Other editors may pick an existing authorized file; they never upload a file into a feature or record.
- `/snapshots/branches` is the only place that assigns snapshots to statically configured branches. `/site` may select its working snapshot, but it has no branch picker or assignment action.

## Model and placement editing

The ER model is part of an immutable snapshot configuration. Entity, field, and relation IDs are generated by the system. The graphical editor supports typed fields, uniqueness, enum options, relations, layout positions, and a keyboard-operable list alternative. A structural save creates a child snapshot; it does not change the parent or any branch assignment. Before removing or changing a bound field, the editor identifies affected bindings and requires an explicit decision.

Feature ZIP manifests use format 2. `arguments` defines the values configured by `/site`; typed `dataInputs` defines only runtime input ports. In each placement, `/site` binds those ports to model entities and stable field IDs and validates output type, relation path, and route lookup against the pinned build. It does not copy editorial values into arguments and does not choose records for a collection. The selected feature version and runtime ABI are part of the immutable placement contract.

Argument source controls match the existing route resolver: query values can populate a route-coercible scalar argument or an array of route-coercible scalars. Objects and arrays of objects remain literal arguments and use nested controls. When a route capture, query binding, or media argument binding becomes invalid after a manifest or route change, the editor keeps the saved value visible as a repairable warning. Build-registry loading, an empty registry, and a missing pinned build are distinct states; a missing build explains how to restore or register the immutable build.

The registry rejects format 1 and the retired manifest `content.*` CMS schema. There is no compatibility endpoint or data conversion for per-feature CMS records or `contentRelations`. Public form submission validation remains the explicit `form.submissionSchema` contract in the feature manifest.

## Record editing and publication

`/content` selects a snapshot and presents `many` model entities as record collections and each `singleton` entity as one record form. A new singleton automatically receives one empty draft record; it is not published until the user explicitly publishes it. Its form has no add, duplicate, reorder, or delete-record actions. Confirmed clear resets field and relation values while retaining the record ID. Forms are generated from model field types; every CMS value may be omitted, while supplied values, uniqueness, relations, and media ownership are validated. Record IDs are generated and remain stable across sorting and publication. Relations select records from the target entity. Media fields select an existing file in `/media`.

Saving creates a revisioned content draft inside the same snapshot. Autosave and manual save retain local edits on network failures and revision conflicts. Publishing is explicit and updates the snapshot's public records and placement selections atomically; it does not create a structural snapshot. History restore creates a new draft and requires a separate publication. Only published records and selections are exposed to runtime, public HTML, and prerendering.

Collection bindings choose the entity and field projection in `/site`. `/content` then either uses all published records or an ordered list of selected record IDs for each placement. A catalog, detail page, and slider can therefore use the same `Product` records, with the slider showing a subset without duplicating product fields. Detail route lookup uses a bound unique model field.

## Shared workspace behavior

The site workspace uses one snapshot selection and one local structural draft across its canvas, settings, design, and data-model views. It has a single explicit save that creates a child snapshot. Changing views preserves the draft; leaving the workspace, changing snapshots, or discarding a conflict requires an explicit decision. There is no persistent server-side structural draft. Content drafts and publication are independent of this structural save.

The model editor provides entity and field cards for linear keyboard use and an ER graph for visual layout. Graph movement is also available through named keyboard-operable controls. Small screens keep the document within the viewport and allow the graph canvas to scroll internally. Feature argument and binding controls retain visible labels and validation. Existing role checks, revision checks, media-owner checks, unsaved-change warnings, and destructive confirmations remain enforced.
