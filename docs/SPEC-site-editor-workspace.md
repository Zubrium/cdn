# Site editor and model-driven content

Status: the current ownership model is implemented in the working tree. The authoritative ER and record contract is [SPEC-data-model.md](SPEC-data-model.md); route target semantics are defined in [SPEC-route-targets.md](SPEC-route-targets.md); this document defines the editor boundaries and user workflows. Earlier per-feature CMS schema, content relation, and collection-source descriptions are retired and are not migration requirements.

Навигация редактора: `Страницы`, `Версии`, `Бэкенд`, `Настройки сайта`, `Дизайн-система`, `Модель данных`. Выбор снапшота, предупреждения и общая кнопка сохранения остаются в шапке workspace во всех режимах. `/site/pages` является списком, а не встроенным мастер-детейлом: одна запись объединяет данные страницы и её основной/дополнительные маршруты, отдельными записями показаны файловые маршруты. Список поддерживает поиск по названию, URL, стабильному ключу и отображаемому имени фичи, группировку по первому сегменту URL и сортировку только для отображения.

Страница открывается на весь экран по `/site/pages/:pageId` с вкладками `Фичи`, `Параметры`, `SEO`. Размещение открывается по `/site/pages/:pageId/features/:placementId`, где настраиваются аргументы фичи, контентные `dataInputs`, параметры страницы/query, внешний backend и detail-ссылки. Оба маршрута сохраняют query выбранного снапшота. Переходы создают отдельные browser history entries, поэтому кнопка браузера «Назад» возвращает на предыдущий список или страницу; на экранах также есть явные ссылки возврата. На телефоне список и выбранная страница являются отдельными URL-экранами; это сохраняет рабочий draft, но не создаёт искусственную вложенную навигацию.

Файловый маршрут создаётся из списка и открывается по `/site/pages/files/:routeId`. Он выбирает готовый публичный файл из `/media`, задаёт фиксированный URL и режим `inline`/`attachment`. Параметры пути, regex и catch-all для файлового маршрута недоступны. Точный серверный и публичный контракт описан в [SPEC-route-targets.md](SPEC-route-targets.md).

Упорядоченные редакционные списки поддерживают drag-and-drop за отдельную ручку с подписью. Порядок фич на странице, выбранных записей размещения, записей модели, элементов массивных аргументов и скалярных/объектных полей формы контента, включая табличный вариант, сохраняется в существующих данных редактора. Кнопки «выше/ниже» остаются доступной альтернативой для клавиатуры и точного перемещения. Перетаскивание не запускается со ссылок, полей и кнопок внутри строки.

## Ownership

- `/site` owns the snapshot's structure: pages, routes, placements, SEO, design, the graphical data model, feature arguments, and typed `dataInputs` bindings from each placement to model entities and fields. All feature arguments are configured here.
- `/content` owns model records, relations between records, local drafts, publication history, and record selection/order for each placement. It generates its forms from the selected snapshot's model. It does not edit feature arguments or model structure.
- `/media` owns uploads, file metadata, and deletion. Other editors may pick an existing authorized file; they never upload a file into a feature or record.
- `/snapshots/branches` is the only place that assigns snapshots to statically configured branches. `/site` may select its working snapshot, but it has no branch picker or assignment action.

## Model and placement editing

The ER model is part of an immutable snapshot configuration. Entity, field, and relation IDs are generated by the system. The graphical editor is the primary model workspace: a full-height React Flow canvas shows compact entity/table summaries and directed relation connectors. A right-click on empty canvas space opens the table-creation action at that position; dragging from a table's source handle to another table's target handle creates a relation. A labelled toolbar action and a keyboard-operable relation dialog provide the accessible alternatives. The inspector is hidden until an entity or relation is selected and then appears beside the canvas for entity, field, cardinality, enum, uniqueness, and relation editing. Fields can be reordered by dragging their labelled handles; named movement controls and ordinary form inputs remain the keyboard alternative to pointer movement. Generated IDs are not presented as editable or primary labels. A structural save creates a child snapshot; it does not change the parent or any branch assignment. Before removing or changing a bound field, the editor identifies affected bindings and requires an explicit decision.

Feature ZIP manifests use format 2. `arguments` defines the values configured by `/site`; typed `dataInputs` defines only runtime input ports. In each placement, `/site` binds those ports to model entities and stable field IDs and validates output type, relation path, and route lookup against the pinned build. It does not copy editorial values into arguments and does not choose records for a collection. The selected feature version and runtime ABI are part of the immutable placement contract.

Argument source controls match the existing route resolver: query values can populate a route-coercible scalar argument or an array of route-coercible scalars. Objects and arrays of objects remain literal arguments and use nested controls. When a route capture, query binding, or media argument binding becomes invalid after a manifest or route change, the editor keeps the saved value visible as a repairable warning. Build-registry loading, an empty registry, and a missing pinned build are distinct states; a missing build explains how to restore or register the immutable build.

Page routes remain serialized to the existing `path`, `static`, `param`, `regex`, and `catchAll` nodes. The editor accepts a complete URL/segment as text and offers a visual segment builder for static text, named parameters, an optional catch-all, and regex presets for integer, number, slug, UUID, and date. Raw regex2 input remains available as an expert mode. The editor previews captured values and rejects duplicate capture names, empty matching patterns, `/` inside a regex segment, invalid catch-all placement, and malformed values before save; the server remains authoritative.

Each placement groups its configuration under `Источники данных`: page/path and query arguments, model content, external backend requests, and public values whose reusable origins/constants live in `/site/backend`. Content bindings use readable entity, relation, field, and output names instead of generated IDs, describe the resulting projection, and state that actual records and their order are edited in `/content`. Stale bindings remain visible with an inline repairable warning after a route or model change. Backend bindings retain the existing contract: the engine supplies the public origin, path and typed source/destination values, while the feature code performs the request and parses its response.

The registry rejects format 1 and the retired manifest `content.*` CMS schema. There is no compatibility endpoint or data conversion for per-feature CMS records or `contentRelations`. Public form submission validation remains the explicit `form.submissionSchema` contract in the feature manifest.

## Record editing and publication

`/content` selects a snapshot and presents `many` model entities as record collections and each `singleton` entity as one record form. A new singleton automatically receives one empty draft record; it is not published until the user explicitly publishes it. Its form has no add, duplicate, reorder, or delete-record actions. Confirmed clear resets field and relation values while retaining the record ID. Forms are generated from model field types; every CMS value may be omitted, while supplied values, uniqueness, relations, and media ownership are validated. Record IDs are generated and remain stable across sorting and publication. Relations select records from the target entity. Media fields select an existing file in `/media`.

Saving creates a revisioned content draft inside the same snapshot. Autosave and manual save retain local edits on network failures and revision conflicts. Publishing is explicit and updates the snapshot's public records and placement selections atomically; it does not create a structural snapshot. History restore creates a new draft and requires a separate publication. Only published records and selections are exposed to runtime, public HTML, and prerendering.

Collection bindings choose the entity and field projection in `/site`. `/content` then either uses all published records or an ordered list of selected record IDs for each placement. A catalog, detail page, and slider can therefore use the same `Product` records, with the slider showing a subset without duplicating product fields. Detail route lookup uses a bound unique model field.

## Shared workspace behavior

The site workspace uses one snapshot selection and one local structural draft across pages, versions, backend, settings, design, and data-model views. It has a single explicit save that creates a child snapshot. Changing views or selecting another page preserves the draft; leaving the workspace, changing snapshots, or discarding a conflict requires an explicit decision. There is no persistent server-side structural draft. Content drafts and publication are independent of this structural save.

The pages list supports search across page/file names, routes, feature keys and labels; grouping by the first route segment; and display sorting by manual route priority, name, route, or type. Display sorting never changes route priority. Page routes are edited from the full-screen page editor; the route dialog accepts a complete root URL or one child segment and offers the existing visual segment builder and expert regex syntax. File routes are edited separately and cannot include dynamic segments. Deep links between `/site/pages`, a page, a feature placement, and a file route preserve the selected snapshot and local structural draft. Existing role checks, revision checks, media-owner checks, unsaved-change warnings, and destructive confirmations remain enforced.
