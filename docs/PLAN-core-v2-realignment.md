# План приведения Core к файловой архитектуре

Статус: исторический план; его заменяют целевые [SPEC-core-architecture.md](../spec/SPEC-core-architecture.md), [SPEC-coordinator-platform.md](../spec/SPEC-coordinator-platform.md) и [SPEC-module-data.md](../spec/SPEC-module-data.md). Использовать этот документ как актуальный план реализации или критерий приёмки нельзя. Старые решения и результаты сохранены только для истории.

Существует один тип пользователя без поля `kind`: сервис получает отдельный ключ и прямые права как обычный пользователь. Управление учётными записями — отдельное разрешение, не тип пользователя и не обход групповых проверок.

## 1. Контракты и подготовка

- Инвентаризировать внешний legacy API файлов, медиа, feature ZIP, снапшотов, маршрутов и Sitepack, включая роли, ошибки, подтверждения, ограничения и streaming/Range. Определить адаптацию каждого контракта к Core без прямого изменения байтов. Зафиксировать остающиеся расхождения и acceptance до замены реализации.
- Зафиксировать конкретные Go-интерфейсы файлов, статичных групп, динамических наборов, администраторов, сервисных учётных записей и кеша; типы запросов, коды ошибок и правила конкурентных изменений. Не добавлять роли, владельцев или индивидуальные файловые права в модель.
- Зафиксировать единую схему `core` и таблицу `core.module_data` для всех engine-owned JSONB documents; удалить требование отдельных engine databases/schemas/Atlas histories. Спроектировать и реализовать scoped Core API с namespace/scope, TTL, CAS, typed selectors/indexes и атомарными batch CAS. Данные Core (files, identities, permissions, sets) остаются в нормализованных Core tables; Loader sessions/parts/idempotency/cleanup — JSON records в namespace `loader`; staging bytes остаются за Core/S3 API.

## 2. Перестройка Core

- Переработать политику доступа: убрать все роли и старую матрицу `admin/moderator/staff/user`; новый API и админка представляют прямые права. Все люди — администраторы с индивидуальными назначениями; сервисы имеют отдельные учётные записи. Отдельное право управления администраторами делегируется и не обходит групповые проверки. Любая операция требует авторизации, кроме локального операторского bootstrap/recovery с защищённым доступом к БД. Удалить публичный режим Core и продуктовые исключения `media`/`submission`.
- Реализовать статичные группы доступа и несколько принадлежностей файла. Проверять прямое действующее назначение субъекта; отсутствие разрешения — отказ, явных запретов нет. Управление учётными записями требует отдельного права, а назначение группы — ещё и собственного уровня `2` в ней. Новый администратор получает `0`, пока создатель явно не назначит уровни. Файл сохраняет хотя бы одну принадлежность; при исключении всех его групп из YAML записи не удаляются и доступ закрывается.
- Реализовать первоначального администратора: право управления и уровень `2` по умолчанию, с конфигурационными исключениями при создании и первом появлении новой группы. Не перезаписывать позже изменённые права при перезапуске или возвращении ранее известной группы. Сериализовать bootstrap, выдачу/отзыв права управления и защиту последнего действующего управляющего администратора; предусмотреть восстановление.
- Реализовать динамические наборы, создаваемые и изменяемые авторизованными движками. Пересекающиеся наборы не дают прав; выборка и поиск исключают недоступные файлы и не раскрывают их наличие через имена, идентификаторы, счётчики и пагинацию. Удаление набора не удаляет файлы.
- Заменить модель версий неизменяемым файлом: новый UUID на новые байты; разрешить изменение метаданных и групп с защитой от конфликтов. Убрать Core API замены, истории и восстановления содержимого, флаг публичности, владельцев, индивидуальные файловые гранты, корзину и глобальный реестр ссылок. Операции движков, сохраняющие внешнюю совместимость, проектируются отдельно.
- В Core оставить проверку полномочий, staging/final S3 I/O, файловый кеш и generic module-data persistence API; upload protocol, session state machine, idempotency, хэши частей/итогового файла, автоматический streaming/buffered выбор, session cache и очистку сессий реализовать в Loader Engine. Состояние Loader хранить в `core.module_data` через capability Loader. Обеспечить повтор загрузки, окончательное удаление, атомарные CAS/batch обновления, резервирование и очистку после сбоев PostgreSQL/S3.
- Подключить реальный ограниченный локальный кеш байтов и метаданных к выдаче; большие файлы передавать потоком. Обеспечить оповещение через PostgreSQL и обязательную проверку актуального доступа и состояния в БД перед любой выдачей. Проверить отказы, потерянные уведомления, восстановление подписки и несколько экземпляров; не применять локальный кеш как доказательство прав.

## 3. Интеграция движков и presentation

- File API вызывает Loader Engine contract; Loader обращается к Core contract и не использует SQL или S3 напрямую. Реализовать resumable upload, metadata, Range и set CRUD с управляющей статичной группой (1 read, 2 write); membership не даёт доступа, добавление файла требует также уровень 2 в одной из его групп. Router держит публичные маршруты в своей конфигурации, использует отдельную сервисную capability Core и отдаёт только явно назначенные файлы/обработчики. Сохранить независимые маршруты и назначения веток, обработку ошибок, CORS и необходимые внешние HTTP-контракты.
- Website сохраняет распакованные файлы ZIP в настроенных группах доступа и создаёт наборы сборок фич. Content создаёт наборы фич, моделей и записей; общие файлы могут входить в несколько наборов. Наборы не должны превращаться в новую модель связей между записями.
- При изменении содержимого engine сначала создаёт новый файл, затем атомарно переключает собственную JSON-ссылку через scoped batch CAS Core; прямой доступ engine к БД запрещён. Core хранит payload без интерпретации предметных ссылок. Старый файл удаляется только после успешного переключения и проверки самим engine; общий ответственный процесс может удалить общий файл без опроса других engines. Отказ переключения не повреждает действующую ссылку; отдельная очистка заброшенного нового файла безопасна при повторе.
- Перенести продуктовые политики, предупреждения, подтверждения удаления, сохранение снапшотов и Sitepack в engines/presentation. Удалить поле `role` и старую матрицу из нового API и админки как согласованное исключение совместимости; остальные внешние контракты сохранить. Зафиксировать и протестировать адаптацию существующих внешних операций update/restore/history к новым неизменяемым файлам; не заявлять совместимость, пока эта адаптация не реализована.

## 4. Проверка и завершение

- Сначала подготовить регрессионные сценарии: прямые уровни администраторов/сервисов, несколько групп, предел делегирования, запрет эскалации и защита последнего управляющего администратора, новые и возвращённые YAML-группы, сохранение назначений после перезапуска, удаление последней принадлежности, отказ анонимного Core и явный публичный маршрут Router. Проверить, что редактирование группы доступа и управление наборами не раскрывают закрытые файлы.
- На изолированной PostgreSQL и S3 проверить единственный Core Atlas migration set и `module_data`; запрет произвольного SQL и capability-доступа к namespace другого engine; namespace/scope isolation, typed selector validation и планы индексов, TTL, CAS conflicts, атомарный batch rollback, payload upcasting и конкуренцию нескольких экземпляров. Затем проверить Loader upload/resume/retry, короткое/длинное тело, лимиты, сбои staging/finalize, безопасную очистку и отсутствие видимого файла до commit. Отдельных Loader databases или Atlas migrations не должно быть.
- В нескольких экземплярах проверить кеш хита/промаха и большого файла, отзыв доступа, изменения назначения и конфигурации, потерянные сообщения, перезапуск и недоступность БД/S3. При невозможности подтвердить актуальные права чтение должно завершаться отказом.
- Прогнать тесты, `go vet`, оба профиля сборки и агрегированное покрытие нового Core и каркаса не ниже 70%; затем необходимую изолированную интеграционную и browser/Vitasil acceptance по затронутым внешним сценариям. Записать конкретные команды, окружение, версии, покрытие, результаты, пропуски и ограничения в [QA_REPORT.md](QA_REPORT.md). Удалить только явно созданные для проверки ресурсы.
- Закрывать соответствующие пункты TODO только по проверенным acceptance. Не считать исторические 71,1% старого каркаса доказательством для новой архитектуры и не объявлять новую систему заменой legacy до подтверждения совместимости.
