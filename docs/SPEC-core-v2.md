## Назначение и границы

Core владеет только PostgreSQL-схемой `core`: файлами и их метаданными, группами доступа и назначениями, наборами, пользователями, credentials и правом управления администраторами. Он проверяет доступ к файлам и управляет постоянными файловыми байтами в S3. Core не владеет предметными таблицами движков, включая upload-сессии Loader. Ролей в новой модели нет. Core не знает, является ли файл контентом, фичей, формой, сайтом, медиа или конфигурацией, и не реализует бизнес-правила конкретного движка.

PostgreSQL-схема `core` — источник истины для метаданных файлов, групп, наборов, идентичностей и полномочий; S3 хранит байты объектов под внутренними UUID-ключами. Core обращается только к `core`, каждый engine — только к собственной схеме; Presentation не владеет схемой и вызывает typed Go contracts. Межсхемные SQL-запросы, внешние ключи и прямой доступ к таблицам соседа запрещены. Модули используют типизированные Go-контракты; только Core получает прямой доступ к S3 и своему файловому кешу. Все schema DDL хранится в отдельных SQL-файлах миграций Atlas; production Go выполняет запросы данных и запускает зафиксированный Atlas CLI `v1.3.0`, но не содержит и не исполняет SQL-команд создания/изменения схемы. Из-за начального отсутствия `core` его схема создаётся отдельной Atlas bootstrap-миграцией с журналом в `public.atlas_schema_revisions`; таблицы Core и их миграции ведутся в `core.atlas_schema_revisions`. Runtime PostgreSQL login отделён от мигратора, является прямым членом только `NOLOGIN` роли `zubrium_core_runtime` и получает только DML-права на таблицы Core; у login и grant-role нет других членств или повышенных атрибутов. Runtime membership не может дать приложению право переключиться на мигратора или другую роль. Runtime и migration URLs обязаны указывать на одинаковые PostgreSQL host, port и database; приложение отклоняет расхождение адресов, даже если имя базы совпадает. Миграционные credentials не используются для запросов приложения. Схема Core — чистый начальный baseline; существующие базы и данные нельзя сбрасывать или переносить без отдельного разрешения. Развёртывание описано в [CORE-OPERATIONS.md](CORE-OPERATIONS.md).

## Файлы и жизненный цикл

- HTTP File API передаёт запросы Loader Engine; он загружает файл возобновляемой сессией: создание резервации, потоковая передача частей, чтение статуса, commit или abort. Инициатор передаёт `Idempotency-Key`, имя, MIME, размер, итоговый SHA-256, атрибуты и одну или несколько целевых групп. Части принимаются отдельными потоковыми запросами с номером и SHA-256; статус позволяет продолжить с недостающими частями после паузы или обрыва соединения. Loader проверяет каждую часть и итоговую сумму, полноту и размер; только успешный commit через Core делает файл доступным.
- Сессии, idempotency records и состояние частей принадлежат Loader и хранятся только в его схеме `loader`; локальный кеш Loader — производная оптимизация. PostgreSQL `loader` обеспечивает восстановление после перезапуска и координацию нескольких экземпляров. Core не читает эту схему и не хранит upload-session таблицы. Временные байты передаются в S3 только через Core staging API; Core сохраняет staging-объекты отдельно от видимых файлов и не включает их в каталоги до commit.
- Сессия привязана к создавшей её учётной записи. Только она может читать её статус или отменять её; Loader при каждой операции подтверждает identity через Core, а Core заново проверяет активность пользователя и уровень `2` во всех целевых группах на каждой части и commit. Отзыв доступа блокирует продолжение и commit; инициатор может отменить сессию, чтобы освободить ресурсы. Loader ограничивает число, размер и срок жизни частей и инициирует удаление просроченных/отменённых staging-данных через Core.
- Loader Engine должен автоматически выбирать потоковый или буферизованный режим по конфигурационному порогу и лимиту совокупной памяти. Буферизация разрешена только для файлов не больше установленного порога и при наличии memory budget; большие файлы и исчерпание бюджета обрабатываются потоком. HTTP-клиент не может принудительно включить неограниченную буферизацию. Core использует один S3 `PutObject`, поэтому настроенный `max_object_bytes` ограничен 5 GiB. Core предоставляет `PutStagedObject`, `ReadStagedObject` и `DeleteStagedObject`: байты остаются закрытыми и привязаны к инициатору и группам, запись проверяет SHA-256 и уровень `2`, чтение заново проверяет пользователя и текущие назначения, удаление повторяемо. Core убирает только устаревшие незавершённые reservations; готовые staging-объекты удаляет Loader по собственному состоянию и сроку сессии. Политика Loader и её интеграция ещё не реализованы.
- Успешная загрузка создаёт файл с новым UUID. Байты неизменяемы: изменение содержимого означает создание другого файла с другим UUID. Core не поддерживает версии файла, замену байтов или восстановление версии.
- Имя, допустимые метаданные и принадлежность к группам доступа и наборам можно менять при наличии соответствующих полномочий. Служебная ревизия метаданных для проверки конкурентных изменений и кеша допустима; это не версия содержимого и не создаёт историю файлов.
- Каждый файл принадлежит как минимум одной группе доступа. Нельзя удалить его последнюю принадлежность. Группа может быть временно отсутствующей в текущей конфигурации: принадлежность сохраняется, но не предоставляет доступ. Это состояние не является основанием удалить файл.
- Core удаляет файл окончательно, включая байты в S3; корзины и пользовательского восстановления нет. Файл, находящийся в нескольких группах, можно удалить при уровне `2` хотя бы в одной из них. Core не проверяет ссылки сайтов, форм или контента и не предупреждает об их последствиях.
- Новые идентификаторы генерирует система; пользователь не вводит UUID вручную. Переданные байты, размер и тип содержимого проверяются в установленных ограничениях; произвольное имя файла не используется как путь в S3.

### HTTP File API

`presentation/fileapi` — внешний HTTP-адаптер к Go-контракту Loader Engine. Он передаёт bearer credential в Loader и не принимает пользовательский `principal_id`. File API не вызывает Core напрямую, не обращается к БД/S3 и не реализует протокол загрузки. Loader подтверждает identity через Core и вызывает типизированные операции Core для авторизации, файлов и staging. Управление динамическими наборами выполняется движками через in-process Go-контракт Core и не публикуется generic File API.

| HTTP операция | Маршрут | Контракт |
| --- | --- | --- |
| Начать загрузку | `POST /api/v2/files/uploads` | JSON с `name`, `contentType`, `size`, `sha256`, `groups[]`, `attributes`; обязательный `Idempotency-Key` |
| Статус загрузки | `GET /api/v2/files/uploads/{id}` | Только инициатор; возвращает полученные части и expiry, чтобы продолжить загрузку |
| Отправить часть | `PUT /api/v2/files/uploads/{id}/parts/{number}` | Поток `application/octet-stream`, обязательные Content-Length и `X-Content-SHA256`; часть можно повторить идемпотентно |
| Завершить загрузку | `POST /api/v2/files/uploads/{id}/commit` | Core повторно проверяет владельца сессии, активность, текущие уровни групп, полноту, размер и checksum |
| Отменить загрузку | `DELETE /api/v2/files/uploads/{id}` | Только инициатор; отменённое/истёкшее staging-содержимое очищается Core |
| Список файлов | `GET /api/v2/files?group=&q=&cursor=&limit=` | Core возвращает только доступные файлы, без total count и утечки через cursor |
| Метаданные | `GET/PATCH/DELETE /api/v2/files/objects/{id}` | Изменяющие методы требуют `If-Match: "{id}-r{revision}"`; байты неизменны |
| Содержимое | `GET/HEAD /api/v2/files/objects/{id}/content` | Авторизованная потоковая выдача; GET поддерживает одиночный HTTP Range; ответ закрыт от shared cache |
| Членство в группе | `PUT/DELETE /api/v2/files/objects/{id}/groups/{group}` | Обязательный `If-Match`; Core проверяет запись и запрет удаления последней группы |
| Наборы файлов | Нет маршрутов в generic File API | Движок создаёт и меняет свои наборы через внутренний Core-контракт; пользователь управляет ими через интерфейс соответствующего движка |

Тело загрузки разбивается клиентом на отдельные потоковые части; это не один multipart/form-data запрос, который нельзя возобновить после потери соединения. Streaming/buffered выбирает Loader по конфигурации; HTTP-запрос не может принудительно включить неограниченную буферизацию. `Idempotency-Key` повторно использует только ту же резервацию с теми же метаданными; другой запрос с этим ключом завершается конфликтом. Для файла или сессии с отсутствующим либо закрытым доступом HTTP-ответ не раскрывает существование ресурса. Наборы не предоставляют доступ к файлам: внутренний поиск Core фильтрует каждый файл по его текущим группам. Группы и назначения групповых прав имеют отдельные конфигурационные/административные операции и не создаются маршрутом файлов.

### Сбой и конкурентность PostgreSQL/S3

Состояние загрузки и idempotency records находятся в схеме Loader; файловые метаданные и группы — в схеме Core. Межсхемной транзакции нет и она не требуется: Loader использует явные состояния сессии и идемпотентные вызовы Core. Временные байты хранятся как непрозрачные staging-объекты, которыми управляет Core API; видимый файл появляется только после успешной проверки и финального Core commit. Восстановление сверяет состояние Loader с результатом Core по idempotency key, а не читает таблицы Core напрямую. Запись S3 и транзакция Core DB не атомарны. До завершения загрузки файл не выдаётся. Уникальные ключи staging-объектов и синхронизация загрузки с очисткой исключают удаление байтов активной или другой операции. Повтор после неопределённого ответа не должен создавать дубликаты; ключ идемпотентности генерирует клиентский код, а не пользователь. Повторное использование ключа для другого запроса отклоняется согласно документированному контракту.

Удаление сначала делает файл недоступным через Core; затем S3 и метаданные очищаются с безопасным повтором после сбоя. Это техническое состояние операции, не корзина: восстановление пользователем не предоставляется. Конкурирующие выдача, загрузка, удаление, изменение групп и прав не должны раскрывать закрытые данные, повторно публиковать удалённый объект или оставлять доступ к частичной записи. Для управления метаданными и принадлежностью использовать проверку конкурентных изменений, чтобы потерянный ответ или устаревшая запись не затирали чужое изменение.

## Статичные группы доступа

Список групп задаётся YAML-конфигурацией при запуске. Уровни назначаются напрямую каждой учётной записи администратора или сервиса, без ролей и наследования через роли. Через административный интерфейс назначениями управляет администратор, у которого есть отдельное право управления администраторами и уровень `2` в соответствующей группе. Создание новой фичи, модели или записи не создаёт новую группу доступа и не требует перезапуска.

| Уровень | Право в группе |
| --- | --- |
| `0` | Нет доступа через эту группу |
| `1` | Чтение файлов группы и разрешённых метаданных |
| `2` | Чтение и запись: загрузка, изменение метаданных и принадлежности, удаление |

Для файла достаточно прямого назначения уровня хотя бы в одной действующей группе; `0` означает отсутствие разрешения, а не явный запрет. Индивидуальных разрешений на файл, ролей и явных запретов нет. Уровень `1` разрешает только чтение; добавление фичи или загрузка её файлов требуют уровня `2` в соответствующей группе. Уровень `2` сам по себе не даёт право управлять учётными записями и назначениями: для этого дополнительно требуется право управления администраторами.

Чтобы добавить существующий файл в другую группу доступа, субъект должен иметь уровень `2` на файл через одну из его текущих действующих групп и уровень `2` на целевую группу. Дополнительного права расширять доступ нет. Добавление может открыть файл всем субъектам, у которых есть чтение целевой группы; это следствие операции. Удаление принадлежности также требует прав записи и не должно оставлять файл без единой сохранённой группы.

Если группа убрана из YAML, Core запускается: её сохранённая принадлежность и назначения не предоставляют доступа, пока группа не возвращена в конфигурацию. Файлы и другие группы не удаляются. Если отсутствуют все группы файла, файл недоступен; возвращение хотя бы одной прежней группы восстанавливает действие её сохранённых назначений. Право управления администраторами не обходит этот запрет. Изменения конфигурации и назначений должны учитываться всеми экземплярами без выдачи устаревших прав.

## Динамические наборы

Набор — динамическая сущность для поиска и организации файлов, отдельная от статичной группы доступа; данные наборов принадлежат схеме `core`. Движки создают и меняют свои наборы через внутренний Go-контракт Core; generic File API и административные маршруты Core не позволяют пользователю управлять ими напрямую. `created_by` связывает набор с учётной записью движка, которая его создала, и ограничивает операции изменения состава и удаления. Это не тип пользователя и не право на файлы. При добавлении Core требует активную учётную запись и уровень `1` хотя бы в одной текущей группе файла; при чтении набора Core возвращает только файлы, доступные запрашивающему субъекту. Один файл может находиться в нескольких наборах и группах доступа. Набор не выдаёт прав на файлы и не меняет их группы доступа. Удаление набора или исключение файла из набора не удаляет файл.

При получении набора и поиске Core возвращает только файлы, доступные вызывающему субъекту. Имена, идентификаторы, счётчики, курсоры и прочие метаданные ответа не должны раскрывать существование закрытых файлов. Операции через File API дополнительно требуют уровень в управляющей группе набора; прямые внутренние Go-потребители используют тот же контракт авторизации Core. Полномочия сервисных учётных записей ограничиваются назначенными группами и задачами.

Действие человека через админку не получает полномочия сервисного ключа движка автоматически: presentation/engine проверяет прямой уровень администратора для соответствующей операции и группы, а обращение engine к Core проходит также под собственным сервисным ключом с необходимым уровнем. Например, просмотр набора фич требует `1`, импорт новой фичи — `2` у администратора; сервису Website тоже нужен соответствующий доступ для чтения и записи файлов. Прямые сервисные операции без пользователя ограничиваются назначениями самого сервиса. Анонимный публичный маршрут Router остаётся отдельным явно настроенным сценарием.

Пример: Website Engine распаковывает ZIP и создаёт набор сборки фичи из manifest, HTML, JS и assets, сохраняя файлы в заранее настроенной группе доступа. Content Engine помещает контентные файлы в нужную группу доступа и добавляет их в наборы фич, моделей или записей. Одна модель или файл могут использоваться несколькими фичами: наборы могут пересекаться; Core не вводит отношения между моделями или записями.

## Идентичность и публичная выдача

В Core существует одна сущность пользователя: поле типа `kind`, категории пользователей и роли отсутствуют. Термины «администратор» и «сервисная учётная запись» описывают применение одной и той же сущности, а не разные типы или неявные привилегии. Движки, Router и другие сервисы используют обычных пользователей с отдельными ключами и собственными прямыми назначениями групп. Право управления пользователями назначается отдельно и само по себе не даёт группового доступа. Все операции Core требуют проверенной идентичности. У файла и группы нет понятия владельца.

Первоначальный администратор создаётся при первом запуске с отдельным правом управлять администраторами. По умолчанию ему назначается уровень `2` во всех группах, если конфигурация при создании не задаёт для группы другой уровень. Конфигурация инициализирует назначения только при создании: последующие изменения через админку сохраняются после перезапуска и не перезаписываются YAML. Если позднее в YAML впервые добавлена группа, первоначальному администратору для неё назначается `2` по умолчанию или явно указанный для этой новой группы уровень. Возврат уже известной ранее группы не считается первым добавлением и восстанавливает её сохранённые назначения, не перезаписывая их. Первоначальный администратор не имеет неявного обхода групповых проверок: его фактические назначения могут быть ограничены конфигурацией или последующими разрешёнными действиями.

Администратор с правом управления администраторами может создавать других администраторов и сервисные учётные записи, выдавать и отзывать это право другим администраторам и управлять ключами. Новый администратор, созданный через админку, имеет уровень `0` во всех группах, пока создающий явно не назначит права. Назначать или изменять уровень другого администратора либо сервиса в конкретной группе может только администратор с правом управления администраторами и собственным уровнем `2` в этой группе. Он не может таким способом выдать доступ к группе, где у него нет `2`. Это же право управления требуется для создания сервисных учётных записей; их групповые уровни подчиняются тому же правилу делегирования.

Нельзя отключить или удалить последнего действующего администратора с правом управления администраторами или отозвать у него последнее такое право. При проверке действующий управляющий администратор должен быть активен и иметь действительный ключ. Защита работает при конкурентных операциях и не оставляет частичных изменений; предусмотрена защищённая операторская процедура восстановления при потере ключей или доступа к группам. Если секрет первого администратора не задан, он генерируется случайно и выводится один раз; хранится только проверочный хеш. Bootstrap сериализуется между экземплярами и не пересоздаёт существующий ключ.

Core не знает анонимной выдачи и не хранит флаг публичности файла. Router определяет публичный маршрут в своей конфигурации, обращается к Core под собственной сервисной учётной записью и может получить только файлы, разрешённые этой записи. Администратор настраивает назначения для Router. Публичный маршрут не превращает всю группу Router в автоматически опубликованный каталог; публикуются только явно назначенные маршруты или обработчики.

Запреты операций над медиа, заявками, контентом и иными продуктами принадлежат соответствующим engines/presentation, а не файловой модели Core. По прямому решению пользователя поле `role` и старая матрица `admin`, `moderator`, `staff`, `user` удаляются из нового API и админки. Это явно согласованное исключение из прежнего требования сохранить все внешние контракты; остальные контракты по-прежнему требуют переноса и проверки. Адаптер не должен незаметно вводить роли заново.

## Зафиксированный Go-контракт Core

Публичный контракт реализации зафиксирован в test-local интерфейсе [`coreV2RuntimeContract`](../core/platform/core_v2_contract_test.go). Production `Runtime` должен реализовать эти сигнатуры до приёмки. Изменение сигнатуры сначала отражается в этой спецификации, затем в интерфейсном тесте; реализация не должна заставлять переписывать приёмочные сценарии по ходу работы.

- `Principal` представляет единственный тип учётной записи и сообщает `ID`, `Name`, `Active`, `CanManageAdministrators`. Дополнительного `kind`, `role` или матрицы ролей нет. Создание учётной записи возвращает её ID и секрет нового ключа один раз; назначения групп по умолчанию равны `0`. Управление ключами, блокировкой и отдельным правом управления администраторами выполняется операциями контракта.
- `File` содержит системный `ID`, `Groups []string`, непрозрачные `Metadata map[string]string`, `ContentType`, размер и служебную ревизию метаданных. Значение `Metadata["name"]` — имя файла. Пути, владельцы, visibility и типы продуктовых сущностей не входят в контракт Core. Байты неизменяемы; новый набор байтов создаёт новый UUID.
- `CreateFile(ctx, session, requestKey, groups, metadata, contentType, size, body)` требует уникальный сгенерированный UUID ключ запроса, хотя бы одну активную группу и уровень `2` во всех исходных группах. Повтор идентичного запроса с тем же ключом возвращает прежний ID; конфликт метаданных с тем же ключом завершается `ErrRequestConflict`. Неверный размер или метаданные не создают доступный файл.
- `UpdateFile` принимает ожидаемую ревизию и новую map-метадату. Она не меняет байты, а устаревшая ревизия завершается `ErrRevisionConflict`. Изменение состава групп — отдельные `AddFileToGroup` и `RemoveFileFromGroup`, также с ревизией. Последняя группа не удаляется. Любой субъект с `2` хотя бы через одну группу файла может удалить весь файл.
- `ListFiles` фильтрует по одной статичной группе, `ListFileSet` по набору, `SearchFiles` применяет поиск и необязательные группу/набор. Сигнатуры и порядок аргументов заданы тестовым интерфейсом. Во всех трёх операциях доступ проверяется до подсчёта и пагинации: возвращаются только доступные файлы, cursor не раскрывает количество скрытых записей.
- Диапазоны `ReadFileRange` включают обе границы: `start=1,end=2` для `one` выдаёт `ne`. Метаданные и права проверяются при каждом чтении, даже если байты были в локальном кеше.
- `CreateFileSet` принимает пространство имён и имя набора; набором управляет создавшая его учётная запись движка через внутренний Go-контракт. В Core и generic File API нет обязательной управляющей группы для набора. Наборы не дают доступ к файлам и удаление набора не удаляет файлы. Машинные пользователи создаются как обычные principals и получают прямые назначения групп.
- Свежая схема хранит набор в `core_file_sets` с `id`, `created_by`, `namespace`, `name`; связь набора с файлом хранится отдельно в `core_file_set_members(file_set_id, object_id)`. Метаданные файла хранятся одной непрозрачной JSON-структурой вместе с UUID-ключом S3, размером, content type и служебной ревизией. Прямые назначения и сохранённые принадлежности используют ключ конфигурационной группы, поэтому её выключение не удаляет данные.
- `RuntimeConfig` явно задаёт `AccessGroups map[string]access.Level`, лимит байтов файла и метаданных, `CacheMaxBytes`, `CacheTTL`, `MaxCachedObjectBytes` и параметры фонового обслуживания. Максимальный размер одного объекта, который Core может целиком прочитать для кеширования, не превышает общий лимит кеша; ошибочная конфигурация отклоняется до запуска. Удалённые без восстановления файлы не имеют `DeletedRetention`. Конфигурация групп назначает уровни первоначальному пользователю только при создании или первом добавлении группы; повторный запуск не затирает административные изменения.
- Ошибки авторизации возвращаются как `ErrUnauthorized` для отсутствующей/отозванной идентичности и `ErrForbidden` для действующего пользователя без достаточного уровня. Не найденный файл возвращает `ErrFileNotFound`. Отказ проверки БД не превращается в разрешение из кеша.

## Кеш и несколько экземпляров

Каждый экземпляр Core имеет локальный ограниченный кеш метаданных и байтов часто запрашиваемых файлов. Общий лимит, TTL и максимальный размер отдельного кешируемого файла настраиваются явно. Большие файлы возвращаются потоком из S3 и не загружаются целиком в память. Кеш не хранит решение об авторизации как основание для последующей выдачи.

PostgreSQL — общая инфраструктура оповещения об изменениях файлов, принадлежности к группам, состава конфигурации и назначений прав. Перед каждой выдачей, в том числе из кеша, Core проверяет актуальные права субъекта и состояние/ревизию файла в БД. Потерянные или задержанные уведомления не позволяют выдать устаревшие данные или сохранить отозванный доступ. Если актуальность или права нельзя проверить из-за недоступности БД, доступ закрывается. После восстановления соединения кеш и подписка должны быть приведены в согласованное состояние.

## Границы движков и удаления

Движок сам отвечает за смысл своих файлов и собственные ссылки. Его данные и ссылки хранятся только в схеме этого движка; изменения выполняются его repository в собственной PostgreSQL-транзакции. При изменении контента или конфигурации движок загружает новый файл, атомарно переключает свою ссылку в своей схеме и после успешного переключения проверяет использование старого файла по собственным ссылкам, затем вызывает Core для его удаления. Core не предоставляет SQL-доступ к чужим схемам, общий кросс-схемный transaction helper или глобальный реестр продуктовых ссылок. Если переключение завершилось ошибкой, действующая ссылка сохраняется; новый файл подлежит последующей очистке. Сбой между обновлением ссылки, вызовом Core и записью в S3 обрабатывается повторяемой операцией очистки, а не общей транзакцией PostgreSQL и S3.

Каждый движок проверяет только собственные ссылки. Общий ответственный процесс может удалить общий файл без опроса остальных движков; в этом случае ссылки других движков могут перестать работать. Core не хранит глобальный реестр ссылок и не блокирует удаление по продуктовым зависимостям. UI и движки отвечают за применимые предупреждения и подтверждения. Снапшоты и импорт/экспорт Sitepack остаются задачами движков: они должны сохранять необходимые файлы и внешние контракты без введения версий файла в Core.

## Приёмка

До отметки о выполнении проверить на изолированных ресурсах:

1. Создание, чтение, потоковую загрузку и выдачу, метаданные, несколько групп и наборов, поиск и фильтрацию закрытых файлов; повторную загрузку и отказ без частичных видимых изменений.
2. Все комбинации прямых уровней `0/1/2` для администраторов, сервисов и нескольких групп; создание с `0`, выдачу уровней только управляющим администратором с `2` в нужной группе, делегирование и отзыв права управления, защиту последнего управляющего администратора. Проверить сохранение изменённых назначений после перезапуска, первое добавление и возвращение YAML-группы, отсутствие последней принадлежности и отказ при недостаточном уровне без частичных изменений.
3. Сервисный ключ Router, публичный явно назначенный маршрут и отказ анонимного прямого Core-запроса; отсутствие утечки через метаданные набора и кеш.
4. Несколько экземпляров, изменение и отзыв прав, потерю уведомлений, разрыв/возврат соединения с PostgreSQL и недоступность S3; при невозможности проверки прав выдача закрыта.
5. Сбои между БД и S3, повторную очистку, конфликт параллельных операций, окончательное удаление и отсутствие восстановления; отсутствие Core-версий, владельцев, индивидуальных файловых грантов, корзины и продуктовых правил.
6. Удаление `role` и старой матрицы из нового API и админки, перенос остальных legacy-контрактов и Sitepack на границах engines/presentation, а также изолированные unit, интеграционные и браузерные сценарии. Покрытие нового Core и каркаса — не менее 70% исполняемых строк; одно число не доказывает безопасность и совместимость.

Потоковая S3-загрузка текущего каркаса применяет SigV4 `UNSIGNED-PAYLOAD`; при дальнейшей реализации обеспечить защиту содержимого при передаче через TLS. HTTP допустим только по явно включённой настройке доверенной локальной среды; это не обеспечивает целостность по недоверенной сети. Реальное поведение и доступность конфигурации подтверждаются проверками, а не этой спецификацией.
