# Snapshot-scoped flat data model and feature bindings

Status: current contract, 15 November 2026. Model-to-model relations and record-to-record relations are retired. The current Vitasil snapshots contain flat models and no relation maps, so this change requires no production data migration.

## Product decisions

- A site snapshot owns one versioned `dataModel`.
- `DataModel` contains `formatVersion`, ordered `entities`, and optional legacy `positions`. `positions` remains in the payload for compatibility but is no longer edited by the UI.
- A `DataModelEntity` is one model. It has a generated stable ID, stable generated key, editable name, `many` or `singleton` cardinality, and ordered fields.
- Model-to-model relations, relation cardinality, relation IDs, nested relation paths, and record relation maps are not part of the product contract.
- Structural model changes create a child snapshot. Record drafts, publication, history, and placement selections remain snapshot content state.
- `/site` owns model structure, feature arguments, direct typed `dataInputs` bindings, page routes, placements, SEO, design, and external backend bindings.
- `/content` owns record values, drafts, publication, history, and the editorial selection/order of records for a placement.

## Model editor

`/site/data-model?snapshot=...` is a searchable model list. It shows model name, cardinality, field count, and whether its fields are referenced by feature bindings. The list supports grouping/filtering between collections and singleton models and sorting by name or field count. Every row opens:

`/site/data-model/:model?snapshot=...`

where `:model` is the stable generated entity key. The selected snapshot remains in the query string. Browser back/forward and the explicit return link preserve normal navigation and the shared `SiteWorkspace` draft.

The model page has one vertical scroll owner. It edits the model name, cardinality, and ordered fields. Field editing includes name, type, uniqueness, enum options, drag ordering, labelled handles, and named up/down controls. Deleting a model or field and changing a field type or cardinality use the existing confirmation flow and report affected feature bindings. Generated UUIDs are not displayed in visible interface text.

The model list and model page do not contain a relation tab, relation counter, relation dialog, connector, canvas, empty relation state, or disabled placeholder.

## Model structure

Fields support text, long text, integer, number, boolean, date, date/time, URL, email, enum, and media. Every editorial value is optional. The server validates supplied values by type and format, enum membership, uniqueness, media ownership/access, and the current singleton cardinality.

Changing a model from `many` to `singleton` is allowed only when both current draft and published state contain at most one record. A new singleton receives exactly one empty draft record. Clearing a singleton record preserves its record ID and removes supplied field values; clear remains a draft until explicit publication.

Record IDs are generated by the server and remain stable through sorting, publication, snapshot fork, history restore, and sitepack remapping. A record contains only `id`, `entityId`, `sortOrder`, and `values`.

## Feature data contract and bindings

Feature manifests remain format 2 and keep the existing runtime ABI. `dataInputs` declares `scalar`, `record`, or `collection` ports and typed output fields. A port maps directly to fields on one root entity.

Each placement's `DataInputBinding` contains:

- `inputKey`;
- `entityId`;
- `fieldId` for scalar ports;
- `fields` with `inputPath` and `fieldId` for record/collection ports;
- optional unique-field route lookup for record ports;
- optional detail SEO field mappings.

Bindings do not contain `relationIds`, relation traversal, wildcard segments used to cross model boundaries, relation previews, relation validation, or relation errors. Direct nested output objects remain allowed and are assembled from fields on the same root record. Unsupported legacy relation-path bindings fail before a snapshot is created.

For a collection input, `/content` chooses all published records or an ordered subset for that placement. A detail record may resolve from a unique field and a path argument. Scalar and record inputs resolve one selected record, or the sole published singleton automatically.

## Compatibility boundary

Legacy JSON is accepted only when retired relation data is empty:

| Input | Accepted | Rejected |
| --- | --- | --- |
| `dataModel.relations` | absent, `null`, or `[]` | any non-empty array |
| `modelContent.records[].relations` | absent, `null`, or `{}` | any non-empty object |
| placement `relationIds` | absent, `null`, or empty | any non-empty relation path |

Rejected input returns an error containing `legacy_model_relations_not_supported`. The server does not silently delete or migrate non-empty legacy relation data. New API responses omit all relation fields.

Snapshots with empty legacy relation fields continue to load and can be forked or imported through sitepack. A sitepack with non-empty retired relation data is rejected during complete preflight, before storage writes. Entity, field, record, media/file, placement, selection, publication-history, and snapshot identities retain their existing remapping behavior.

## Persistence and runtime

Runtime resolves only published records and selected placement order. It does not follow record graphs. A feature receives scalar values, record objects, or ordered collection arrays assembled from direct fields of one model. Missing optional values are omitted or represented by empty records/arrays according to the input kind.

Model structure and bindings belong to immutable snapshot payload. Records, drafts, publication history, and selections remain in snapshot content storage with revision checks. Snapshot fork copies both structural and content state transactionally. Cache identity includes the snapshot digest and published content revision.

## Permissions and failure behavior

Existing role guards, branch isolation, optimistic revisions, local recovery, unsaved-change protections, destructive confirmations, media ownership checks, and publication safeguards remain in force. A stale revision cannot partially save or publish content. Invalid model bindings or retired relation data cannot create a snapshot.
