# Snapshot-scoped data model and feature bindings

Previous verification state, 8 November 2026: the Engine stores the ER model in snapshot configuration, validates typed feature bindings, edits model records through a snapshot-scoped API, projects published records into the existing runtime ABI, and accepts Vitasil format 2 builds. Disposable API and Chromium acceptance passed for model editing, child-snapshot creation, shared Product data across catalog/detail/slider, record and relation editing, manual save, publication, branch-assignment isolation, responsive layout, and media rendition processing. All nine current Vitasil source features built into disposable ZIPs and were accepted by Engine as format 2 with explicit `dataInputs`; browser acceptance exercises important placements, but not all nine feature placements. The integration suite has since been migrated off the removed per-feature CMS API: `go test ./...`, `go vet ./...`, the current-schema integration suite, and cross-install model Sitepack acceptance pass. The aggregate integration run intentionally skips tests whose database/S3 namespace differs from its selected isolated environment; those acceptance groups have separate successful runs. Browser acceptance of every feature placement and the broader full cutover criteria remain open.

Implementation-first status: follow-up code changes made after that verification state are being completed before the next test/debug pass. Their tests and browser/runtime acceptance are pending; the previous results above do not imply that newer changes have passed.
This specification supersedes earlier instructions that prohibited a snapshot-scoped ER model. The product contract is authoritative. The former per-feature CMS editor and `contentRelations` model are retired; no read/write compatibility or conversion path is part of the target.

## Product decisions

- The graphical ER model belongs to a site snapshot. Editing its structure is a structural site change and saves as a child snapshot. Saving or publishing entity records changes content revisions inside the selected snapshot and does not create a snapshot.
- A child snapshot receives a full independent copy of the model structure, published records, content drafts, and curated placement selections. Later edits to either snapshot do not leak to the other. Branch assignments remain independent and are changed only in `/snapshots/branches`.
- `/site` owns pages, routes, placements, feature arguments, and structural data bindings. Every feature argument is edited only there. It also maps a feature's typed data inputs to entities and fields in the model. It never edits model-record values or uploads files.
- `/content` owns model records, their drafts and publication, and editorial selection/order of records for a placement. Its forms are generated from the snapshot model, not from a feature's CMS editor schema. A shared record is entered once and all bound features use that record.
- Feature manifests use format 2 only. Format 1 and any manifest `content.*` CMS schema are rejected, not decoded or converted. Manifests keep `arguments` for values configured in `/site`; CMS editor descriptions (`content.mode`, `content.schema`, `content.settingsSchema`, and placement-scoped content schema) do not exist. Every manifest declares `dataInputs` (an empty array when no model data is consumed); these declarations describe only the feature's typed runtime input shape, not a record form. The public form submission schema remains in `form.submissionSchema` and retains strict required-field validation. Changed feature data contracts use a new major feature version.
- The existing feature runtime ABI remains unchanged. Engine resolves bindings and model records into the same runtime `content` object shape expected by the feature. Model records do not become feature-specific copies.

## Model structure

The snapshot payload contains a versioned `dataModel` with entities, fields, relations, and editor canvas positions. Entity, field, and relation identifiers are generated by the system and remain stable when labels change. User-facing names are editable; users never type internal IDs. Field mappings reference stable IDs rather than labels or mutable names.

An entity is a reusable record type such as `Product`, `SiteNavigation`, or `HeroContent`. Fields support scalar text, long text, integer, decimal, boolean, date/time, URL, email, enum, and media values. References are represented as typed relations between entities rather than nested copies of target records. The record contract stores relation targets by stable relation ID and generated record ID. Validation enforces source/target entity types, cardinality limits, unique ownership for one-to-one and one-to-many, and rejects dangling targets. Typed feature inputs project a finite directed relation path into nested object/array values; each multi-target relation corresponds in traversal order to one declared `*` segment in the manifest output path. Polymorphic relations and arbitrary executable expressions are out of scope.

## Singleton entities — agreed 8 November 2026

An entity may have `cardinality: "many"` or `cardinality: "singleton"`. New entities default to `many`; omitted cardinality in existing snapshot payloads is interpreted as `many`. Entity cardinality is independent of relation cardinality and does not change the manifest or feature runtime ABI.

Adding a singleton entity and saving its structural snapshot automatically creates one empty record in that snapshot's content draft. It is not published automatically. Forking copies the parent's draft and published singleton record IDs and values like other model content; if a singleton draft has no row, the new snapshot receives one empty draft row. A published singleton may have zero rows until the first explicit publish, then has exactly one. A valid editable draft has exactly one row for every singleton entity. The server enforces the invariant on draft save and publish; duplicate writes and stale revisions remain protected by the existing transaction and revision checks.

`/content` renders a singleton as one record form with no add, duplicate, reorder, or delete-record controls. The user can clear all values and relations after confirmation; the same record ID remains, and the change is a draft until explicit publication. Fields remain optional. This preserves a stable identity for references, history, media accounting, fork, rollback, and sitepack.

Changing an entity from `many` to `singleton` is allowed only when both its current draft and published state contain at most one row. If either has multiple rows, structural save fails with a clear instruction to clean up and publish the parent content in `/content` first. No rows are discarded or selected implicitly. Creating a singleton and deleting/recreating its entire entity continue to use ordinary snapshot and explicit orphan-cleanup safeguards.

Historic publications are immutable records of earlier content states and do not block a transition that satisfies the current draft/published limit. The child keeps that history; sitepack preserves it while validating each historic state's schema and relations without applying the newer singleton row-count invariant. Runtime and current content continue to use only the current published state. Restoring a historic state with multiple rows into a singleton model is rejected before writing anything; the parent snapshot with the original `many` model remains available for that recovery path.

For a singleton entity, scalar and record `dataInputs` resolve its sole published row automatically; no editorial record picker is shown for those ports. A configured route lookup on a record input still applies. A singleton collection port retains the `collection` output shape and resolves to an array with zero or one record; `/content` may include or omit that row for the placement. Ordinary many-record selection and ordering remain unchanged. With no published singleton row, record inputs resolve to `{}`, scalar inputs omit the value, and collection inputs resolve to `[]`.

Singleton entities may participate in ordinary typed relations; the existing relation cardinality rules continue to govern each relation edge. Fork, content history/restore, runtime resolution, media reference scans, deletion safeguards, and sitepack import/export must all preserve the singleton cardinality and stable record identity.

The graphical editor shows entities as movable cards and relations as labelled connectors. Users can create and rename entities, add/rename/reorder fields, choose field types and enum options, add relations, and see incoming feature bindings before destructive changes. A keyboard-operable entity/field list and detail form provide an accessible alternative to canvas interaction. The editor does not require JSON, SQL, code, or manual IDs.

All CMS values are optional. The engine validates the type and format of supplied values, media ownership/access, relation targets, unique constraints explicitly configured on a field, and feature binding compatibility. Deleting or changing the type of a field referenced by a feature binding or record requires confirmation; the engine must not silently discard values or bindings. Structural edits are validated before a child snapshot is created.

When a structural edit removes an entity, field, or relation that is still referenced by copied draft or published content, the fork preserves every value and selection and returns a snapshot warning. The child remains editable, but draft save and publication reject the incompatible payload until it is repaired. `/content` surfaces unknown field values and relation IDs, and offers an explicit confirmed cleanup; records whose entity was removed can be explicitly deleted with incoming links and placement selections cleared. The parent content remains unchanged. Removing the entire data model stays blocked while any model workspace exists, because a model-less snapshot would not have an editor for that inherited data.

## Feature data contract and binding

`dataInputs` declares named `scalar`, `record`, and `collection` input ports. Each `key` is a top-level property of the runtime `context.content` object. A scalar port supplies one value, a record port an object, and a collection port an ordered array of objects. Record and collection fields use typed RFC 6901 paths. The declaration contains only information needed to validate and render the feature input contract; it does not define labels, help text, required CMS values, defaults, or an editor layout.

Each placement stores bindings from its input ports to model entities and fields. A mapped field uses a stable `fieldId` and may include an ordered `relationIds` path from the bound entity to the field's entity. The path is directed and finite; runtime follows only those declared edges. A one-to-one edge adds no array wildcard; a one-to-many or many-to-many edge adds exactly one wildcard at the matching output path level. Type mismatches, missing fields/relations, wrong path direction, mismatched wildcard/cardinality, ambiguous paths, and invalid collection/detail bindings block structural save with a field-level explanation. A binding is snapshot-scoped and uses the feature build version pinned by that snapshot.

Feature arguments remain separate from data bindings. Route values, presentation options, and other manifest-declared arguments are configured only in the `/site` feature editor and are passed through the existing `arguments` runtime channel. Content records and curated record choices are never stored as arguments.

For a collection input, `/site` chooses the model entity and field projection. `/content` chooses either all published records or an ordered list of selected record IDs for that placement. This keeps shared entity data canonical while allowing a slider to show only a curated subset of catalog products. A detail placement resolves a record through its route argument and a model field with a uniqueness constraint.

## Content editing and lifecycle

`/content` lists entities available in the selected snapshot, shows record tables with search/sort, and generates record forms from model fields. Relation controls select existing records; media controls select an existing authorized file from `/media`. Upload remains exclusively in `/media`.

Autosave and manual save create a draft with revision checks. Explicit publish changes the selected snapshot's published records and curated selections without creating a snapshot. A stale revision returns a conflict and preserves local edits. History/restore follow the existing content publication safeguards. Branches assigned to the snapshot see the same published state.

Model-record IDs are generated and stable across sorting, publication, snapshot fork, and sitepack import remapping. Record deletion previews relation references, placement selections, feature bindings, and media consequences; no dangling references are published.

## Persistence, runtime, and migration

The model definition and placement bindings are structural snapshot payload. Draft and published model records, publication history, and editorial placement selections are content state scoped to a snapshot. The storage contract must preserve atomic revision checks for changes that publish records and selections together. Snapshot fork copies schema and all published/draft content state in one transaction or with a verified atomic staging protocol.

Runtime resolves only published records from the assigned snapshot, follows validated relations, applies published placement selection/order, and projects the result into the existing feature input shape. Draft-only record IDs never reach public HTML or runtime. Cache identity/invalidation includes snapshot structural digest and published content revision.

Sitepack export/import includes model structure, bindings, published and draft records, selections, media references, and identity remapping. It validates the complete model and references before writing storage. The retired `contentRelations` envelope is not read, written, or converted.

All current Vitasil feature builds must be updated to the new manifest contract without changing their public runtime ABI. Catalog and slider bind to the same `Product` entity; catalog exposes the full published collection while the slider stores an ordered selection of product IDs in content. Feature-specific text and settings move into model entities or remain feature arguments only when they are configuration by nature. Form copy is CMS model data; `form.submissionSchema` remains the form validation contract.

The transition has no backward compatibility requirement. Old per-feature content data is not converted or silently read by the new application. Reset only uniquely identified disposable QA databases and storage created for a test run. Never migrate, reset, or write to the working Vitasil API, database, object store, volumes, or user data.

## Permissions and failure behavior

- Existing role guards, branch isolation, snapshot assignment, file owner checks, unsaved-change warnings, and destructive confirmations remain in force.
- `/site` structural saves and `/content` record saves use the current permission helpers and optimistic revisions. A stale model or feature build returns a conflict and does not partially save.
- A feature build missing `dataInputs`, an invalid model, a missing binding target, a deleted referenced record, or an incompatible field type cannot be published into a snapshot or rendered with guessed data.
- Form submission validation stays strict and independent from the optionality of CMS model fields.

## Concrete payload and API contract

The snapshot `config.dataModel` JSON has `formatVersion: 1`, generated UUIDs for entity, field, and relation IDs, editable stable keys/names, typed fields and relations, and optional canvas positions. No model field has a required flag: omitted values are valid. A `Placement` stores `dataBindings`, each with an `inputKey`, `entityId`, optional scalar `fieldId`, typed field mappings (`inputPath` to stable `fieldId`), and optional unique-field route lookup metadata. Bindings are validated against the pinned manifest and the same snapshot model before structural save.

Each format 2 manifest has an explicit `dataInputs` array, including `[]` for a feature that consumes no model data. A port uses `{key, kind, type?, profile?, fields?}`. `kind` is `scalar`, `record`, or `collection`. A scalar port declares `type`; record and collection ports declare a non-empty `fields` array of `{path, type, profile?}` where `path` is a JSON Pointer into the runtime object. A media leaf can carry the existing typed processing profile (`accept`, optional `renditions` or `video`); a profile on a non-media leaf or a parent port is invalid. Port keys and paths are unique. These are output types only: they never encode CMS labels, required values, form layout, or defaults. The engine injects a generated stable `id` on each record projected to runtime; it is reserved and cannot be edited as a model field.

Each placement stores one `DataInputBinding` per manifest port: `{inputKey, entityId, fieldId?, relationIds?, fields?, lookup?, detailSEO?}`. Scalar ports map `fieldId` and an optional one-to-one relation path to one model field. Record and collection ports map each declared output path to one stable model `fieldId` and an optional directed `relationIds` path. A multi-target relation contributes one output wildcard in traversal order. A record port may add `{argument, fieldId}` lookup metadata only when the manifest argument is path-bound and the root model field is unique; otherwise `/content` selects one record ID. Collection ports do not use route lookup. Model relations are record values keyed by stable `relationId`. For enum compatibility, every value offered by the model field must be included in the corresponding manifest enum; the model may offer a narrower subset, but unsupported extra options are rejected before creating a child snapshot.

An optional `detailSEO` mapping may be added to one record binding on a `detail` page. It contains stable IDs for `titleFieldId`, `descriptionFieldId`, `ogTitleFieldId`, `ogDescriptionFieldId`, and/or `ogImageFieldId`; all point to direct fields on that binding's root entity. It is valid only when that input has the page's unique route lookup. Text slots accept `text` or `longText`; `ogImageFieldId` accepts `media`. At least one slot must be configured. The mapping stores structure only. At request time the engine resolves it from the one published record selected by the lookup, sanitizes text and uses only ready public image media, falling back field-by-field to page/site metadata. Draft values and private media never enter public head metadata. The resolved metadata is part of HTML cache identity and sitemap output; publish/restore changes use the snapshot content revision to invalidate those representations.

Generic record content is snapshot-scoped and separate from immutable structural payload. A content workspace consists of a monotonic `revision`, `publishedRevision`, records (`id`, `entityId`, `sortOrder`, `values`, relation-ID-to-record-ID lists), and placement input selections. Record IDs are generated by the server. For collection ports, an absent selection means all published records in the bound entity in editorial order; `mode: "ids"` means exactly the supplied ordered IDs, including an empty list. Scalar/record ports use an explicit single-record selection unless a record binding resolves from a path argument to a unique field; they never copy record fields into arguments or feature-owned envelopes.

The admin content API is rooted at `/api/v2/admin/content/snapshots/{id}/model`. `GET` returns the model-bound draft workspace and published revision. `PUT` requires the expected workspace revision and atomically saves records and selections as a draft; supplied values are type-checked, but absent fields are accepted. `POST /publish` requires the saved revision, revalidates unique fields, relations, selections, file ownership/access and structural binding compatibility, then atomically replaces published records/selections, increments snapshot `contentRevision`, marks that draft revision published, and appends history. A stale revision returns the existing conflict response and leaves both server and caller-local edits intact. `GET /history` returns publication revisions; restore creates a new draft from a selected published version and does not publish implicitly. These actions do not create a structural snapshot or alter branch assignments.

Structural saves continue to use immutable snapshot creation. Forking copies the data model and bindings in the payload plus published records, draft workspace, selections, and content revision in one transaction; subsequent writes are independent. Runtime and prerender load published model content only. Snapshot deletion, file reference scans, media cleanup and sitepack import/export include model content. Legacy per-feature rows are outside the new contract and are not converted.

## Acceptance criteria

1. The ER editor creates and edits entities, scalar/media fields, and 1:1/1:N/N:M relations, persists layout, validates conflicts, and is usable by keyboard without a graph dependency.
2. Site structural save creates a child snapshot containing model and binding changes; it does not change branch assignments or edit record values.
3. Feature arguments can be configured only in `/site`; data bindings map feature inputs to model fields with type validation and an accessible preview.
4. `/content` creates/edits/publishes model records and placement selections with autosave, manual save, revision conflicts, history, media picker, and no schema-specific editor code in manifests.
5. One `Product` record appears identically in catalog and slider; the slider can choose a subset and order without duplicating product field values. Detail routing resolves that same record by a unique field.
6. Form copy is model-backed while public form submission schema and required-field validation remain manifest-backed.
7. Child snapshot fork copies model, records, selections, drafts, history references, and files safely; parent/child subsequent changes are independent.
8. Runtime, prerendering, SEO metadata, and cache invalidation use only published model data and continue to use the current feature runtime ABI.
9. Sitepack export/import and Vitasil feature builds use the new contracts; all nine Vitasil features are exercised in an isolated Engine/database/storage environment. The working Vitasil instance is not written to.
10. Format 1 manifests, old per-feature content payloads, and relation envelopes are rejected at the new contract boundary; the model-backed workflow initializes and completes against a fresh disposable database and storage. The working Vitasil instance and user data remain untouched.
