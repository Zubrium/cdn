## Уточнение модели от 4 ноября 2026 — согласовано

Этот раздел имеет приоритет над прежними формулировками ниже о фиксированных dev/prod. Исторические отметки проверок относятся к старой реализации двух сред и не означают готовности новой модели веток.

### Согласованное направление

- Снапшоты образуют дерево наследования. В разделе «Снапшоты» редактируются состояние сайта, страницы, маршруты, фичи и другие настройки выбранного снапшота.
- Ветка запускает назначенный ей снапшот на собственном порту. Раздел «Ветки» показывает ветки и позволяет назначать им снапшоты; создание и имена веток задаются конфигурацией запуска, а не админкой.
- Ветки существуют строго в количестве и с параметрами, заданными конфигурацией запуска: никакие дополнительные ветки автоматически не создаются. В конфигурации должна быть хотя бы одна ветка; изменение набора или портов требует перезапуска и согласования с Docker.
- Ветки позволяют разместить разные сайты на одном движке или отдельные тестовые и публичные стенды одного сайта. CORS и индексация настраиваются отдельно для каждой ветки; публичные URL и маршрутизация доменов принадлежат reverse proxy / gateway.
- Изменение страниц, маршрутов, конфигурации или версий фич создаёт дочерний снапшот и не изменяет структуру родительского. Дочерний снапшот получает состояние родителя на момент создания и затем живёт независимо.
- Для отдельного сайта администратор может создать дополнительный независимый корневой снапшот в любой момент. Это пустое начало с одной валидной главной страницей `/`, без фич, размещений и контента; оно не наследует другой сайт. Действие не переключает открытый редактор и не переназначает ветки. Для запуска корень отдельно назначается одной из статически настроенных веток. Сохранение изменений уже выбранного снапшота по-прежнему создаёт потомка.
- Отдельных сохраняемых черновиков конфигурации снапшота нет: результат изменения структуры оформляется новым снапшотом. Черновики контента сохраняются и при создании потомка наследуются наряду с опубликованным контентом, после чего редактируются независимо.
- Контент является исключением: он редактируется в самом снапшоте. Автосохранение и ручное сохранение создают черновик; отдельное действие публикует контент внутри того же снапшота. Опубликованное изменение отражается во всех ветках, которым назначен этот снапшот.
- Поля редакционного контента необязательны, включая вложенные; это правило не отменяет обязательность полей пользовательских форм и проверку отправляемых заявок. Остальные ограничения схемы для заданных значений сохраняются.
- После создания дочернего снапшота интерфейс предлагает сразу назначить его выбранной ветке. До подтверждения назначение не меняется.
- При повторном назначении снапшота ветка получает его текущий опубликованный контент, а не обязательно контент прошлого назначения. История и восстановление прежних версий контента проектируются отдельно.
- Canonical-домен задаётся отдельно в настройках сайта; gateway отвечает за маршрутизацию внешних URL. CORS и индексация настраиваются по веткам.
- Заявки форм привязаны к ветке. Список заявок должен поддерживать гибкие фильтры и сортировку.

- Единый реестр хранит версии фич. Снапшот определяет, какие фичи и их версии в него добавлены: в редакторе контента и дизайн-системы видны только фичи этого снапшота, независимо от того, размещены ли они на странице.

- В дизайн-системе снапшота можно создавать размеры экрана и переопределять для них существующие токены через графический интерфейс.
- Снапшоты можно удалять, кроме назначенного любой ветке снапшота и его непосредственного родителя: это обеспечивает быстрый откат на предыдущий снапшот. При удалении промежуточного узла его потомки перепривязываются к его родителю; при удалении корня они становятся корневыми. Содержимое потомков не меняется. Защита пересчитывается по непосредственным родителям назначений всех веток.
- Сервисные ключи конфигурируются оператором; сервис регистрируется по имени, идентификатор создаётся автоматически. Загрузки файлов до 5 ГБ поддерживают передачу частями и возобновление.
- Пользователь не вводит идентификаторы вручную; система генерирует их сама. Для ветки или сервиса отдельная операторская команда переименования сохраняет ID и связанные данные; затем оператор обновляет имя в конфиге. Сопоставление сохраняется после перезапуска.
- Эксплуатационные параметры — порты, лимиты, TTL, размеры частей, таймауты, квоты, настройки кеша и подобные значения — задаются явно в конфигурации, без скрытых значений по умолчанию в приложении. Примерные значения находятся в примере конфига. Технические константы протоколов и алгоритмов, например HTTP 404 и размер SHA-256, остаются в коде. Секреты передаются через переменные окружения или файлы секретов; пример содержит только заглушки.
- Диапазоны размеров экрана задаются порогами «от ширины» в пикселях; при нескольких подходящих переопределениях выбирается порог с наибольшей шириной. Перед удалением порога с переопределениями показывается предупреждение об удаляемых значениях.

#### Сравнение режима с Chromium worker и режима без него — 7 ноября 2026

- Текущий worker — это изолированный браузерный рендер на сервере: при cache miss Go запускает Node и Playwright, Chromium загружает публичную страницу и данные, после готовности сериализует HTML. Одинаковый результат отдаётся всем клиентам; User-Agent не используется для разделения роботов и посетителей. Успешные результаты кешируются только в памяти одного процесса движка.
- Без worker Go всё равно формирует HTTP status, head, page-level `<main>`, placement roots и inert bootstrap композиции. Проверенные `static-html-v1` fragments включаются в те же roots сразу; `static-module-v1` и `legacy-react-v1` требуют JavaScript и не имеют feature HTML в ответе при отключённом JavaScript. С включённым JavaScript framework-neutral runtime читает bootstrap без начального fetch `/api/v2/runtime`, затем монтирует динамические features.
- Поэтому полностью отключить worker означает убрать задержку Chromium на холодном ответе, но динамические Vitasil features не будут включены в исходный HTML и no-JS HTML. Поисковые/социальные клиенты, не исполняющие JavaScript, увидят только статические fragments и системную оболочку. Google выполняет JavaScript в отдельной очереди рендеринга, однако prerendered HTML помогает другим crawler-клиентам и сокращает ожидание видимого содержимого.
- В пользу worker: локальная матрица даёт cold TTFB `822.8–907.6 ms` и warm `6.1–13.3 ms`; медиана самого worker на cache miss `854.3 ms`, очередь ожидания `0.001 ms`. Это указывает на стоимость запуска/работы Chromium при промахе, а не на ожидание слота. Замеры выполнены на unthrottled loopback; они не показывают production LCP/INP/TBT и не доказывают, что браузер worker улучшает Lighthouse у конкретного публичного сайта.
- Ограничение производительности: при cache miss ответ ждёт завершения Chromium; concurrency и очередь ограничены конфигом, ошибки выдают server shell с `no-store`. Кеш локален экземпляру, поэтому новый процесс/другая реплика начинает с промаха. При cache hit генерация HTML повторно не выполняется, но engine всё ещё разрешает composition/cache identity до conditional response. Повторное client-side монтирование сохраняет интерактивность, но потенциально повторяет CPU работу и может влиять на TBT/INP/CLS; полевых измерений этого эффекта пока нет.
- Предварительное решение: Chromium worker целесообразно сохранить как совместимый рендер текущих browser-only ABI, пока нет подтверждённого общего HTML renderer для тех же фич. Полное удаление оправдано только вместе с заменой: предварительно генерируемым HTML из разрешённого snapshot/public content или совместимым SSR ABI. Текущий `static-html-v1` — статический HTML-фрагмент; он не подставляет редакционные значения и сам по себе не заменяет dynamic Vitasil placements. Чистый client-only режим можно рассматривать для закрытых/неиндексируемых app-веток, где отсутствие HTML до JavaScript приемлемо.
- Варианты: (1) оставить worker и после публичного baseline оптимизировать cold path, затем рассмотреть общий cache/prewarm по branch/snapshot/content revision; (2) использовать `static-html-v1` только для действительно неизменяемых фрагментов, не считая его заменой рендеру динамического контента; (3) проектировать генерацию готового HTML на публикации/назначении, если измерения оправдают стоимость, с атомарной инвалидацией после publish/rollback/assignment; (4) не выбирать full client-only как оптимизацию публичного сайта без доказательства, что выигрыш TTFB компенсирует задержку контента/интерактивности.
- До решения о замене нужны корректные публичные URL/ветка Vitasil и сравнительный mobile/desktop Lighthouse для indexable маршрутов. Текущий Lighthouse 74 получен на 404, а изолированные локальные замеры недостаточны для вывода о публичном режиме. 9 ноября выполнена новая disposable indexable Vitasil матрица и закрыт согласованный lab target; оставшиеся cache/load, sitemap, gateway/CDN, production и field-CWV TODO остаются открытыми.

## Исторические решения прежней модели dev/prod

Следующие формулировки и прежние отметки о двух средах отражают старую реализацию и не являются целевыми требованиями; приоритет у раздела «Уточнение модели» выше.

- «Файлы» — отдельный пункт меню рядом с «Главной».
- Снапшот редактируется как рабочая ревизия. Окружения dev и production меняются только отдельным назначением сохранённой ревизии.

- Единый сервис движка — источник файлов и контента сайта.
- Экспорт снапшота включает только файлы, используемые этим снапшотом.

## Прежняя структура dev/prod — историческая справка

Для сайта остаются два независимых назначения: какой снапшот используется в dev и какой — в production. Понятия dev/prod не входят в модель самого снапшота и не используются для классификации его ревизий. Специфические токены фич описываются разработчиком в `manifest.json` внутри ZIP и регистрируются вместе с версией сборки. Снапшот выбирает фичи и их версии из единого реестра. Редактор показывает только токены добавленных в него фич; значения одной фичи общие для всех её размещений. Редактор дизайн-системы полностью графический: пользователь не пишет CSS, JSON, имена переменных или выражения. Генерация безопасных значений для runtime — внутренняя ответственность движка. Это не отдельный редактор схем и не отдельная система манифестов.

В текущем коде определения темы находятся в allow-list движка; среди них есть специфичные для Vitasil значения, а часть значений редактируется как CSS. Необходимо выделить универсальную базу и перенести специфичные определения в манифесты соответствующих фич, не вшивая новые фиче- или сайтозависимые токены в ядро.

### Файловый API для доменных сервисов — реализация и локальная приёмка выполнены; внешний gateway/CDN открыт

Цель: доменный сервис может сохранить файл в файловом сервисе движка, получить его устойчивый идентификатор и затем запрашивать содержимое и сведения о нём. Согласовано: у каждого файла есть владелец; владельцы файлов админки и внешних систем различаются. ## Критерии готовности

- Изменение структуры создаёт потомка и не меняет назначения веток до отдельного действия.
- Назначения статических веток независимы; контентные черновики и опубликованные данные наследуются потомком независимо.
- Используемый снапшот и один предшествующий ему снапшот защищены от удаления согласно согласованной модели дерева.
- Несовместимые изменения схемы не теряют данные и показывают понятный план миграции.
- Контент, дизайн-система и связанные файлы корректно загружаются из выбранной ревизии.

- Системные страницы работают при ошибке или отсутствии error-фичи.
- Рефакторинг ядра сохраняет доступность, поведение и адаптивность интерфейса.
