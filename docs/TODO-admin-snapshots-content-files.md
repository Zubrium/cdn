# Активный план Website Engine

## Состояние

Внешний HTTP API использует пути `/api/...` без версионного префикса. OpenAPI остаётся версии 3.1; `info.version` — метаданные документа. Внутренние версии данных, схем, feature builds, component contracts, snapshots и миграций сохраняются.

Композиция `main` собирает компоненты профиля через запечатанный runtime bus со статическим allowlist. Record store Website, Content, Forms, Router, Loader, Archive и Media использует typed `pkg/contracts` operations с composition-bound owner scope. Durable Coordinator использует generic operation/task-class contracts; component descriptors лежат в нейтральном `pkg/contracts`, собираются `main`, а Core registry хранит только opaque owner IDs. Файловые операции Prerender, Archive, Media и Router delivery используют `core.files.*` DataBus clients со scoped stream bytes; Router Routes identity/group authorization — typed `core.access.*` операции. `make lint-core-boundary` зелёный: `Architecture boundaries OK ... across 20 repository-local Go modules`; прямых Core imports в `engines/`, `workers/` и `presentation/` нет, Core-адаптеры находятся только в `main/internal/composition`. Durable Website build подключён в full-профиле: root `engine.website/build-page/v1` эмитит `worker.prerender/render-page/v1`; manifest-pinned media derivative работает через изолированный runner. Успешная Content publication через composition запускает trusted `contracts.PublicationPublishOperation`, а durable retirement withdraw'ит зарегистрированные route target'ы и сохраняет page/snapshots/content/forms данные. `GET /api/admin/pages/{pageID}` отдаёт `ETag`, совместимый с обязательным `If-Match` для DELETE.

Integration-прогон на disposable PostgreSQL/S3 прошёл: `CORE-001`, `WEB-012`, `WEB-018`, `WEB-019`, `WEB-020`, `WEB-021` и `WEB-022` исполнены реально, а не через `t.Skip`. Живой Website/Router E2E прошёл в run `e2e-20261123T160114Z-82a196` с точными строками `PASS E2E-PUB-001` и `PASS E2E-RET-001`. Полный `tests/qa/run-release-checks.sh ... --with-e2e` завершился успешно на свежем стеке `release-final-20261123-c`: 67/67 gates, 32/32 исполняемых сценария. Browser QA Admin ранее выполнен в отдельном checkout с изолированным full-профилем, disposable PostgreSQL и `moto`; проверены 12 экранов, responsive 360–1920 px, темы, клавиатурный фокус, диалоги и публичный listener. Найденные дефекты — пустой фильтр `ListSnapshots`, глобальная Core revision в Website-декодерах, пустой metadata новой страницы, mobile overflow и SSE same-origin — исправлены с regression-тестами. Точные команды и evidence — в [QA report](QA_REPORT.md); непокрытые требования не трактуются как pass.

Контракт Forms переведён на глобальные схемы без `snapshot_id`: метаданные — только `key + fields`, ключ глобально уникален, submissions фильтруются по обязательному `form_id` и необязательному `key`, Router-привязки остаются pinned на версию схемы. Admin получил вложенные страницы `/admin/forms`, `/admin/forms/new` и `/admin/forms/:formId`; публикация из UI использует редактируемый base path `/forms/<key>` и включает upload-операцию только при `file`-полях. Site editor поддерживает route-аргумент `format: "route"`/`source: "route"` с предупреждением, не блокирующим сохранение. Текущие проверки и известные ограничения (в том числе 503 feature catalog) зафиксированы в [QA report](QA_REPORT.md).

Целевой контракт описан в модульных спецификациях и OpenAPI. Ни этот план, ни наличие интерфейсов/заглушек не доказывают готовность реализации. Чекбоксы закрываются только после выполнения критериев и записи результатов в [QA report](QA_REPORT.md).

## Порядок проверки

Сначала завершается применимая реализация и документация. Затем выполняются `make test`, `make vet`, `make build`, `make build-full` и из `frontend/` — `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`. Интеграционные проверки выполняются только на одноразовых ресурсах с точным учётом созданных идентификаторов и безопасной очисткой.
