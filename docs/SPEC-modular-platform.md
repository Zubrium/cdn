# Модульная платформа Zubrium: целевая архитектура

Статус: согласованное направление, реализация и проверка не завершены. Экспериментальная ветка `dev_v2`. Основание — план, согласованный с пользователем, и экспорт «Модульность Zubrium CDN.json».

## Границы и сборка

Платформа — статически компонуемый Go-монолит. `Presentation` — верхний внешний модуль и объединяет Router, File API, Admin API и Admin UI. Отдельного набора Go modules `config/*` нет. Чтение и проверка YAML — отдельная ответственность кода приложения (`cmd/zubrium/config`), она не является presentation-адаптером и не требует собственного `go.mod`. Composition root читает конфигурацию, выбирает и связывает модули. YAML настраивает только уже скомпонованные модули.

Core, каждый engine и каждый компонент Presentation — самостоятельный Go module. YAML loader — обычный package в module composition root. Фичи движка — packages внутри его module; каждая имеет model, application, repository и собственный pkg. Engine предоставляет единый типизированный presentation-контракт с операциями и требуемыми правами. Composition root явно регистрирует модули сборки; динамическая загрузка библиотек не входит в первую версию.

### Изоляция схем и миграций

Core и каждый engine владеют отдельной PostgreSQL-схемой: Core — `core`, Loader Engine — `loader`, остальные движки — схемой со своим стабильным именем. Engine выполняет запросы данных только в своей схеме; Presentation не владеет схемой и обращается к данным через типизированные Go-контракты. В Go-модулях запрещены SQL-команды schema DDL (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`): DDL находится только в отдельных SQL-файлах Atlas migrations. Composition root может вызывать закреплённый Atlas CLI для миграции, но не строит DDL в Go. Роли PostgreSQL и база provision-ятся отдельно инфраструктурным процессом. Межсхемные запросы, внешние ключи и прямое чтение таблиц другого владельца запрещены. Например, Loader хранит upload-сессии в `loader`, а файлы, группы доступа и наборы читает или изменяет через API Core.

У Core и у каждого engine, владеющего схемой, собственные Atlas migration directory, `atlas.hcl`, `atlas.sum` и журнал применённых миграций внутри его схемы. Исключение для самого первого шага Core: Atlas bootstrap создаёт отсутствующую схему `core` и ведёт отдельный одноразовый журнал в `public.atlas_schema_revisions`; дальнейшие таблицы и история Core находятся в `core`. Конфигурация миграции явно задаёт целевую схему и не должна изменять объекты других схем. У каждого Core/engine runtime отдельная учётная запись с правами только на его схему; миграционные credentials отдельны от runtime. Отдельные DSN и grants обеспечивают изоляцию на уровне PostgreSQL, а не только договорённостью в коде. Composition root запускает миграции Core и выбранных движков.

Presentation включает Router, File API, Admin API и Admin UI. File API преобразует внешний HTTP-протокол в типизированные Go-вызовы Loader Engine; прямой вызов Core из File API запрещён. Loader владеет протоколом загрузки, состояниями и кешем upload-сессий, потоковой проверкой частей и итоговой суммы, выбором streaming/buffered режима и очисткой незавершённых сессий. Для файлов, авторизации и групп Loader вызывает контракт Core; в БД и S3 напрямую он не обращается. Наборы принадлежат workflows Website/Content и создаются этими движками через внутренний Core-контракт; generic File API не публикует CRUD наборов или отдельную управляющую группу для них. Admin API выступает адаптером внешнего протокола: он преобразует HTTP-запрос в типизированную операцию контракта движка, получает результат и преобразует его в действующий HTTP-ответ. Вызов между слоями внутри статической сборки — прямой Go-вызов; HTTP, gRPC и сокеты между движками не используются. Router сопоставляет URL либо с файлом, либо с зарегистрированным handler движка. Вызов handler идёт через его engine presentation contract. Admin UI поставляется отдельными статическими файлами либо опционально включается как assets Presentation.

Движки Website, Content и Forms могут отсутствовать в сборке. Loader Engine обязателен для сборки с File API; если File API не включён, Loader может быть исключён. При отсутствии нужной возможности зависимая операция возвращает управляемую ошибку; остальные функции и запуск продолжают работать. Core обязателен. Admin API и UI необязательны; UI может поставляться файлами или быть встроен в отдельный профиль сборки. Протокол feature ZIP и три существующих runtime ABI сохраняются.

## Core: данные и доступ

Core — единственный владелец файловых байтов и метаданных файлов, статичных групп доступа и наборов, пользователей, credentials и назначений прав; эти данные хранятся только в схеме `core`. S3 хранит содержимое файлов под UUID. Байты файла неизменяемы: новый контент получает новый UUID; версии файлов, владельцы и индивидуальные файловые права в Core отсутствуют. Core отвечает за собственные Atlas migrations, файловый кеш, потоковый доступ к S3 и авторизацию файловых операций. Каждый engine хранит принадлежащее ему предметное состояние только в собственной схеме и имеет собственный набор Atlas migrations; доступ к общим файлам, пользователям, группам и наборам выполняется только через контракт Core. Ни один модуль не читает или не меняет таблицы другого модуля напрямую. Подробные правила и критерии: [SPEC-core-v2.md](SPEC-core-v2.md).

Loader Engine хранит upload-сессии, idempotency records, состояние частей и служебную ревизию сессии в `loader`. Его локальный кеш сессий — производный и ограниченный TTL/объёмом; PostgreSQL `loader` остаётся источником истины для восстановления после рестарта и работы нескольких экземпляров. Временные байты частей Loader передаёт в Core staging API: Core управляет S3 и выдаёт непрозрачные staging references, не записывая upload-сессии в `core`. Финальная регистрация файла и проверка прав выполняются Core до выдачи файла.

Запись в S3 и транзакция БД не являются атомарной операцией. Контракт реализации обязан предотвращать выдачу незавершённого объекта и предусмотреть идемпотентный повтор, восстановление после сбоя и безопасную очистку осиротевших объектов без удаления объекта конкурентной операции. Права проверяются до доступа к приватному содержимому и перед условной или кешированной выдачей.

Core всегда проверяет авторизацию. Статичные группы доступа определяют уровни `0/1/2`, назначаемые напрямую администраторам и сервисным учётным записям. Ролей и отдельных обычных пользователей нет. Управляющий администратор может создавать учётные записи и менять назначения только в группах, где имеет собственный уровень `2`; право управления администраторами делегируется отдельно. Файл может входить в несколько групп; достаточно разрешения одной из них. Динамические наборы создаются движками для поиска и не дают прав. Индивидуальных файловых разрешений, владельцев и неявного полного доступа администратора нет.

Все учётные записи представлены одной сущностью пользователя, без поля типа `kind`. Сервис — обычный пользователь со своим ключом и прямыми назначениями; слово «администратор» не задаёт отдельный тип или автоматические привилегии.

Первый администратор создаётся при первом запуске с правом управления администраторами и уровнем `2` во всех группах по умолчанию либо с явными ограничениями конфигурации. YAML инициализирует его назначения при создании и при первом появлении новой группы, не перезаписывая последующие изменения. Нельзя потерять последнего действующего управляющего администратора; предусмотрено операторское восстановление. При отсутствии заданного секрета создаётся криптографически случайный секрет, который выводится в журнал только при создании; хранится только проверочный хеш. Требуется безопасная процедура сброса, сериализация конкурентного bootstrap и документация о доступе к журналам. Секреты конфигурации поступают через окружение или файл секретов.

## Маршруты и пользовательские контракты

Router назначает адреса файлам либо операциям движков. Только явно настроенные публичные маршруты позволяют анонимную выдачу; Router обращается к Core со своей сервисной идентичностью и ограниченными правами. Движки могут резервировать маршруты; резервации и конфигурация записываются как файлы через Core. Общий файл содержит область действия веток. Изменение маршрута одной ветки не меняет поведение другой, а конфликты пользовательских и зарезервированных маршрутов должны выявляться до публикации. Изменённая конфигурация создаётся новым файлом; движок атомарно переключает свою ссылку. Снапшоты и явные назначения веток сохраняют действующие гарантии.

Website управляет фичами, шаблонами, prerender и оптимизацией изображений, видео, аудио и assets. После распаковки ZIP он объединяет manifest и assets в динамический набор и сохраняет их в заранее настроенных группах доступа. Content отвечает за плоскую snapshot-scoped модель и записи без отношений; общие файлы могут входить в наборы нескольких фич, моделей и записей. Forms отвечает за формы и отправки. Движки проверяют собственные ссылки и последствия удаления; Core не ведёт глобальный реестр. Общий ответственный процесс может удалить файл без опроса других движков, поэтому ссылки могут перестать работать. Управление структурой, контентом, файлами и ветками использует индивидуальные групповые назначения.

Внешние HTTP API, формы ошибок, поддерживаемые форматы, feature ABI и существующие сценарии остаются целевым требованием совместимости, **за исключением** отменённых поля `role` и матрицы ролей `admin/moderator/staff/user`: новый API и админка переходят на индивидуальные права. Исторические версии контента, снапшоты, публичная выдача и предупреждения об удалении при необходимости реализуются engines и presentation, без версий файлов, публичного флага и глобальных ссылок в Core. Эта совместимость ещё не реализована и не проверена. Sitepack, экспортированный текущей поддерживаемой версией продукта, должен импортироваться с сохранением структуры, данных и файлов. Это не расширяет текущий Sitepack-контракт на исторические форматы, которые он уже отклоняет; их поддержка требует отдельного решения. Прямая миграция существующей БД не входит в текущий план.

## Перенос и приёмка

До переноса составить инвентаризацию маршрутов и методов API, форматов Sitepack и manifest, прав, интеграций, runtime ABI и пользовательских сценариев, затем сохранить проверяемые контрактные примеры. Перемещение в `legacy/` должно сохранить исполняемость и сборку эталона, включая относительные пути, frontend assets, Docker, миграции и команды CI; пользовательские данные и секреты не перемещать и не удалять. Новая реализация создаётся рядом и не объявляется заменой до полного паритета.

Приёмка включает сравнение внешних контрактов с legacy, импорт реального текущего Sitepack, роли и сервисные гранты, публичные и приватные файлы, отказ без частичных изменений, конкуренцию и восстановление БД/S3, независимость веток, публикацию и откат, работу профилей без выбранного движка, обе поставки UI, browser QA и Vitasil. Интеграции выполняются только на явно изолированных одноразовых ресурсах. Результаты и ограничения записываются в QA-отчёт; TODO закрывается только по фактическим результатам.
