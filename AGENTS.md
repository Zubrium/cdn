# Website Engine agent guidance

## `dev_v2` experimental module layout

In `dev_v2`, the historical product is preserved under `legacy/`. The new workspace is defined by `go.work`: Core is in `core/`, engines in `engines/`, and external entry points in `presentation/`; static configuration belongs to `cmd/zubrium/config`. The root `frontend/admin/` is the SPA being adapted to the new API; `legacy/frontend/` is the historical reference. The target precedence is `spec/SPEC-core-architecture.md`, `spec/SPEC-modular-platform.md`, the target section at the start of `spec/SPEC-feature-runtime.md`, then engine/API-specific target sections. Where those files contain later historical/legacy material that conflicts with their target section or an explicit user decision, the target decision wins and the historical text is reference only. `spec/SPEC-core-v2.md` is historical wherever it conflicts with the new Core architecture. Paths such as `features/`, `pkg/`, and `presentation/http/` describe legacy code unless a target module has explicitly adopted them. Preserve legacy behavior as a migration reference; do not treat placeholder target packages as migrated functionality.

The target Core model is defined by `spec/SPEC-core-architecture.md`: immutable files without versions or owners; YAML-defined static access groups with direct levels `0/1/2`; one user entity and no role/kind field; a separate administrator-management permission; dynamic FileSets that grant no access; authenticated Core file access; explicit Router routes for public delivery; and no Core reference registry or recycle bin. Legacy public behavior, snapshots, content history and Sitepack remain compatibility requirements to implement in engines/Presentation. Do not infer that other contracts are already ported or restore legacy roles in the new API/admin UI.

There is exactly one user entity, without a `kind` column or administrator/service types. A service is an ordinary user with its own credential and direct group assignments. Account-management permission is separate from group access.

For the target modular system, one PostgreSQL database represents one logical system. All persistence is behind the single Core Go module and its public `core/presentation` facade. Keep Core's `domain`, `application`, `infrastructure`, and `presentation` packages directly under `core/`; do not add a `core/internal` layer. Domain models have no business behavior beyond validated construction; use cases and policy live in application; PostgreSQL/S3/cache adapters live in infrastructure; presentation exposes typed capabilities and composition. Core migrations are the sole Atlas migration set. The fresh schema is split by bounded context (`access`, `files`, `uploads`, `file_index`, `engine_data`, `coordination`); engines store versioned JSON records in scoped `engine_data.records`, not `core.module_data`. Engines own Go models and validation but have no DSN, SQL access, schemas, or migrations. Module identity is injected by composition, never accepted from a request, and a module cannot read/write another module's namespace. File API calls Loader; Loader owns upload-session/part/idempotency/cleanup state while Core remains the only PostgreSQL/S3 gateway. FileSets are search indexes: their static management group controls set metadata/membership, and membership never grants access to file bytes. See [SPEC-core-architecture.md](spec/SPEC-core-architecture.md) and [SPEC-module-data.md](spec/SPEC-module-data.md).

### Identity, sessions, and browser transport

- There is exactly one principal/user type in the new system. Do not add `kind`, administrator/service subtypes, or a role matrix. A service integration is an ordinary user with a separately issued credential and direct group grants.
- Static groups are declared in startup YAML. Direct access is `0` (deny), `1` (read), or `2` (read/write). Group `2` authorizes writes and file/group operations covered by that group; it does not grant administrator-management permission.
- Only a user with the separate `can_manage_administrators` permission can create/deactivate users, manage that permission, and issue/revoke credentials. Granting or changing a group level additionally requires the acting user to have level `2` in that group. Newly created users receive level `0` unless the creator explicitly selects grants. Bootstrap YAML seeds levels when the bootstrap user is created and when a group first appears; later restarts or restoration of a previously known group must preserve admin-managed levels.
- Core `sessions` are generic revocable sessions for using one exact `credential_id`, with explicit idle and absolute TTL configuration. They are not browser sessions. Core stores only the token digest and session lifecycle state; revoking the credential or deactivating its user invalidates its sessions. Core never reads or writes cookies, CSRF tokens, HTTP Origin, or browser state. Do not confuse Core authentication sessions with Loader upload sessions or Forms visitor sessions, which belong to their engines.
- Cookie creation/parsing/expiry/clearing, CSRF proof, exact Origin validation, and Secure/SameSite/HttpOnly policy belong exclusively to the HTTP Presentation layer. Browser Admin requests use the Core session in an HttpOnly cookie; CSRF proof is sent separately in a header. Service-to-service integrations may use their configured Bearer credential. Reject ambiguous cookie-plus-Bearer requests. Never store credentials or session tokens in browser `localStorage` or return them in ordinary API responses.
- The user has frozen Core after the approved generic credential-bound session feature. Do not expand Core for cookies, Router uploads, engine workflows, Admin UI behavior, or other product rules. Use existing Core capabilities. Change Core again only to fix a demonstrated breakage in its agreed contract; keep any such repair minimal and add regression evidence.

### Router public operations and uploads

- Router exposes only explicitly configured public routes. A route is private unless its configuration explicitly enables anonymous access. Default response caching is `no-store`; missing routes return 404 and fallback behavior must be explicitly configured.
- Public routes may dispatch only operations compiled into the selected build profile and registered by the owning Presentation/engine contract. Do not accept arbitrary handler names, callbacks, URLs, Core IDs, group IDs, or FileSet IDs from a visitor request. A public file GET route serves exactly its configured `file_id` and requires exact path matching; a FileSet never enables dynamic anonymous file lookup.
- A public upload route has server-configured destination access group/FileSet, byte/type limits, and exactly one raw file body per request. Loader session expiry and multipart part budgets come from explicit Loader startup configuration. The compiled `public.form-upload` operation depends on Loader and Router, not Forms. It requires explicit `enabled: true`, an access group, `max_bytes`, and an exact MIME allowlist; an optional FileSet is an index only. Before storing a route and before staging each request, verify the Router service identity has current level `2` for the destination group and, when configured, the FileSet management group; Loader repeats authoritative checks during writes. It stages fully read bytes in a dedicated absolute directory with mode `0700`, uses `0600` temporary files, checks SHA-256 and size before creating the Loader session, and requires a visitor idempotency key. Bound concurrent staging and verify `max_concurrent_uploads * max_file_bytes <= max_staged_bytes`. It generates the filename and Loader idempotency key; never infer file ID, group, FileSet, filename, mode, or limits from visitor data. Active browser content types are rejected. A Core file remains private; making it downloadable requires a separate explicitly configured public GET route bound to exactly one configured `file_id`, with exact path matching. FileSet membership never makes a file anonymously readable. Router has no request-rate limiter. Anyone deploying public routes must keep the Router listener private behind an external proxy. Proxy selection, configuration, and admission/rate-limit policy belong to the deployer; this repository does not configure or operate that proxy. Upload bytes flow through Router's registered operation to Loader and then Core; Router never writes to storage directly. Forms may use uploads inside form sessions and may also use separately configured upload routes.
- If a selected API is missing its required engine or registered handler, startup fails closed. Development fixtures are allowed only in an explicitly selected development build/profile; they must be visibly synthetic, isolated from production profiles, and must not claim successful persistence or publication.
- Each external Presentation module owns its versioned OpenAPI 3.1 contract under `spec/openapi/` and its Go HTTP adapter. New product endpoints are `/api/v2`; do not add a v1 compatibility layer unless the user explicitly approves it. Keep error schemas, validation, request-size bounds, idempotency/revision headers, and security requirements aligned between OpenAPI, Go handlers, frontend types, and acceptance tests. The target Admin access UI manages users, credentials, and direct group grants; it has no role-management route or role field.

New-module checks are run across the workspace with `make test`, `make vet`, `make build`, and `make build-full`; `make coverage` requires separate disposable PostgreSQL and S3 resources and targets at least 70% combined statement coverage for the new Core and scaffold. This is separate from target-functionality coverage: each module must have executable acceptance tests for at least 60% of its distinct agreed input/result scenarios, tracked in `tests/ACCEPTANCE-MATRIX.md`. A specification or an expected-failing placeholder does not count as an executable test; define the public contract first when an acceptance scenario is underspecified. Follow the sandbox requirements of any active audit skill and record skipped or unavailable acceptance checks. Never move or delete the root `.env`, old dependency caches, or other untracked user data as part of moving source.

## Application map

- The target admin is a React 18 + TypeScript SPA in `frontend/admin/src`, built with Vite and served below `/admin/` by the Go composition root. `legacy/frontend/` is a reference implementation, not the target API client.
- Admin routes live in `frontend/admin/src/app/router.tsx`; route guards and `can*` helpers must use the authenticated principal's direct group levels and separate administrator-management permission. Do not use `principal.role` in the target admin. The shared shell is `frontend/admin/src/app/layouts/AppShell.tsx`.
- API request code is centralized in `frontend/admin/src/api.ts`; frontend types in `frontend/admin/src/types.ts` mirror versioned Go Presentation contracts. The owning Go contracts/handlers are under `presentation/<module>`; there is no central `presentation/http/routes.go` authority for the modular target.
- `frontend/admin/src/domains/` holds reusable domain logic; `frontend/admin/src/pages/` holds route screens; `frontend/admin/src/components/ui/` holds admin Radix-based controls.
- Keep admin styles isolated from public runtime styles. Legacy public HTML templates and lifecycle code under `legacy/pkg/runtime/` remain migration references until a target module explicitly owns the replacement. Never share admin CSS with public pages.
- The target public route matcher and HTTP document/delivery adapters belong to Router Presentation. Browser feature lifecycle scripts must preserve the documented ABI and markup contract. Feature Lab remains a separate loopback source-preview tool in `feature-lab/`, launched with the Vitasil frontend toolchain.

## Product invariants

- Preserve existing CMS capabilities, user data, and legacy role checks inside `legacy/`; do not migrate the old role field/matrix into the target API or Admin UI. The target model uses direct group levels and a separate administrator-management permission. The target branch model uses statically configured branches instead of fixed dev/prod environments; snapshot assignments are managed through `/snapshots/branches`. Preserve backend contracts unless the user's task or an approved specification explicitly requires changing them. Do not bypass or weaken target route guards or `can*` permission helpers; make them evaluate the new group grants.
- Keep destructive confirmations and editor unsaved-change protection.
- Preserve revision checks, content autosave, independent branch assignments, and publication/rollback safeguards. The current snapshot and branch model is defined in the TODO and its linked specifications; keep implementation and those contracts aligned.
- Do not send writes to a running API during visual QA unless it is an isolated test environment with disposable data.
- Do not add a UI, state, or test dependency without a concrete need and user approval.
- Keep `/site/**` focused on page, route, feature-placement, feature arguments, the flat data-model list/page, and direct structural mapping from model fields to typed feature inputs. All feature arguments are configured only in `/site`; this includes selecting an existing media file when it is an argument, but uploads remain in `/media`. `/site` never edits model record values. `/content` generates record editors from the selected snapshot's `dataModel` and owns record drafts/publication plus editorial record selection/order for placements. Branches and snapshot-to-branch assignments are managed only in `/snapshots/branches`. Choosing a snapshot in `/site` is not branch management.
- Model entities have `many` or `singleton` cardinality. A new singleton gets exactly one empty draft record in its snapshot and is not published automatically. `/content` shows one record form; confirmed clear keeps the record ID. The server rejects cardinality changes that would discard records, and typed singleton `record`/`scalar` bindings resolve automatically while `collection` remains an array of zero or one records.
- Legacy-only role matrix: in the product under `legacy/`, `admin` and `moderator` manage site structure, feature builds, and branch assignments; the historical permissions for `staff` and `user` remain until migrated. Do not port the legacy `role` field or matrix into the new API/admin UI. Migrated modules use one user entity with direct group levels `0/1/2` and separately delegated administrator-management permission, as defined by the target specs.

## Agreed target architecture

- Branches are defined statically in startup configuration, each with its own port and independent snapshot assignment, CORS, and indexing policy. Run one Router process per branch; its configured branch ID and public listener are process-local bindings, while shared Core/Coordinator settings and the compiled profile must match across processes. Keep a public Router listener private behind an external proxy. The Router has no request-rate limiter; proxy selection, configuration, ingress routing, and admission policy belong to the deployer and are outside this repository. Router owns configured path-to-file/artifact/registered-operation delivery within a branch. Canonical domain is set in site settings. Do not create extra branches outside the configuration.
- The read-only `/settings` branch overview requires level `1` on `features`; snapshot assignment remains a level `2` operation under `/snapshots/branches`. Runtime topology changes only through YAML plus a full restart.
- Snapshots form a tree. Structural and design changes create a child snapshot; there are no persistent configuration drafts. Content drafts and published content are copied to children and become independent. Saving content creates a draft; explicit publication updates that snapshot and all branches assigned to it.
- Protect a snapshot assigned to a branch and its immediate parent from deletion. Reparent children when deleting an allowed intermediate snapshot; preserve their state. Never alter branch assignments without an explicit action.
- Feature ZIPs include `manifest.json`, which remains the source of feature metadata, site-editor `arguments`, typed `dataInputs`, form submission contracts, design tokens, and runtime metadata. Use only the new target lifecycle ABI (`render`, `hydrate`, `update`, `dispose`); the three historical ABI values `legacy-react-v1`, `static-module-v1`, and `static-html-v1` are not target runtime contracts. Adapt Vitasil ZIPs to the new ABI at their build/export boundary. Do not silently infer or convert a legacy ABI during import. The exact manifest discriminator and lifecycle signatures are still an open contract decision; do not invent them or claim the runtime is implemented until `spec/SPEC-feature-runtime.md` defines them.
- Snapshot-scoped `dataModel` is the source of CMS entity/field schemas and record forms; do not put CMS editor layouts or record values in feature manifests. The flat model list/page lives in `/site`; changes to model structure create child snapshots. Model-to-model and record-to-record relations are retired. New builds use the framework-neutral static runtime contracts in [spec/SPEC-feature-runtime.md](spec/SPEC-feature-runtime.md).
- Preserve Vitasil feature UI, semantic markup, and behavior when adapting its ZIPs to the target ABI. The ABI change is intentional; do not preserve legacy lifecycle wrappers solely for compatibility. Never add engine page wrappers or shared `background`/`header`/`footer` slot wrappers without a target contract. Keep placement composition semantic, avoid nested placements and nested `<main>`, and make server-rendered markup hydratable by the target runtime.
- The common `ui-provider` feature is used by both public sites and the Admin UI. Keep a built-in minimal Admin fallback that can authenticate and restore a previously uploaded compatible provider version when the shared provider is unavailable. Provider selection switches Admin after compatibility checks, then schedules independent rebuilds of affected published sites. Each site gets a child snapshot; one child can serve multiple routes, whose assignments switch separately. Preserve the old site publication on failure, report the failed site, and allow manual retry. If the source publication changes during a rebuild, discard the stale result and rebuild from the newer publication. These provider updates are explicit work and may update routes even when ordinary automatic route publication is disabled.
- The content and design editors show only features included in the selected snapshot, using their selected versions. Editorial content fields are optional, including nested fields; continue validating supplied values and preserve required-field validation for user-facing form submissions.
- Forms submissions are immutable after acceptance: authorized administrators can view and delete them, while status changes follow the Forms contract. Retain submissions until explicit deletion. Public form sessions may resume uploads until their configured expiry; after expiry the visitor starts again. Unpublishing a form or changing its schema cancels open sessions and safely removes their temporary and uploaded files. Delete confirmation removes the submission and all its attachments, including file memberships in other sets/groups, as specified by Forms.
- Base design tokens and values belong to a snapshot; feature-specific tokens are declared by the feature manifest and shared by that feature's placements in the snapshot. The admin editor is graphical and must not require CSS, JSON, variable names, or expressions. Support graphical links to base tokens and configured screen-width overrides. Do not embed a live site preview in the design editor.
- Legacy-only file behavior: files under `legacy/` use their existing owners, public/private visibility, service credentials, and delete confirmations. The new Core target has no file owners or public flag: files are immutable, all direct access is authenticated and determined by static group levels; explicitly public routes are implemented by Router. File API uses Loader Engine, which delegates file authorization and S3 access to Core. See the target specs before migrating a file workflow.
- Generate internal identifiers instead of requiring users to enter them. Configure operational values explicitly—including per-API pagination defaults and maxima—in startup YAML, with examples in example configs; do not introduce hidden runtime defaults. Protocol and algorithm constants may remain in code, and feature manifests may declare token defaults as part of their contract. Pass secrets via environment variables or secret files, never example credentials as real secrets.
- When implementing SEO or prerendering, use the agreed TODO, keep branch indexing policies and snapshot/content changes consistent with cached HTML, and verify real feature behavior and public HTML without claiming guaranteed search rankings.
- The model-v2 cutover uses a clean Core schema and one Core-owned Atlas history; defaults and constraints are declared with their tables. Engines do not own schemas or run SQL migrations; engine JSON payload evolution uses versioned Go upcasters through the scoped Core API. Compatibility/conversion for old dev/prod databases is not required. This does not authorize deleting existing databases, files, or user changes; rebuild only isolated disposable databases and refill them from current Vitasil v2 feature ZIPs during QA.

## Frontend conventions

- Use the existing React Router, TanStack Query, React Hook Form, Zod, Radix, Tailwind, and Lucide patterns.
- Use semantic HSL tokens from `frontend/ui/styles/admin.css` for admin surfaces; define matching light and dark values. Avoid new one-off colors and spacing values where a token or utility already fits.
- Keep request behavior in `api.ts`/domain hooks rather than duplicating fetch logic in pages. Handle loading, empty, error, and saving states where a workflow needs them.
- Keep React 18 compatibility. Do not apply React 19-only composition guidance.
- Make controls keyboard operable, label fields, provide visible focus, respect reduced motion, and keep mobile targets usable.

## Go HTML templates

- Keep HTML markup and `html/template` actions in embedded `.tmpl` files under the owning package's `templates/` directory. Go source builds typed view data, loads/parses the files, and executes named templates; do not embed template source in Go string constants or construct template actions by concatenating strings.
- Use contextual escaping for all dynamic values. Mark data as trusted HTML only when it is static markup from an application-owned embedded build/template and that trust boundary is documented; never pass user content as `template.HTML`, `template.JS`, or equivalent.
- Remove superseded inline template strings after migrating them, and update the relevant spec/QA evidence before closing its TODO item.
