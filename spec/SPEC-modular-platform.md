# Модульная платформа Zubrium: целевая архитектура

> **dev_v2:** При расхождениях новые решения о Coordinator, обработчиках Router, независимых workers, схеме `public` и ABI имеют приоритет: [SPEC-coordinator-platform.md](SPEC-coordinator-platform.md), [SPEC-architecture-review.md](SPEC-architecture-review.md). Разделы ниже требуют полной переработки и отражают предыдущее направление.

> **Новое архитектурное решение:** [Coordinator и модульная платформа](SPEC-coordinator-platform.md) определяет профиль с генерацией composition root, независимые `workers/`, автоматическую публикацию и разделение Router Engine / Router Presentation. При расхождении этих разделов с текстом ниже применять новое решение; реализация ещё требует проверки.

Статус: согласованное направление, реализация и проверка не завершены. Экспериментальная ветка `dev_v2`. Основание — план, согласованный с пользователем, и экспорт «Модульность Zubrium CDN.json».

## Границы и сборка

Платформа — статически компонуемый Go-монолит. Единственная точка сборки — `cmd/zubrium`; конфигурация, HTTP и прочие адаптеры находятся на внешней стороне модулей. YAML loader — обычный package `cmd/zubrium/config`, без отдельного Go module.

Core, каждый engine и каждый HTTP/UI-компонент Presentation — самостоятельные Go modules. Целевые engines: Loader, Website, Router, Content и Forms. Каждый engine предоставляет один типизированный presentation facade; его операции объединяют принадлежащие engine features. Каждая feature оформляется пакетами `model`, `application`, `repository` и `pkg`. Composition root регистрирует только включённые build-профилем engines и выдаёт каждому scoped Core capabilities. Динамическая загрузка библиотек не входит в первую версию.

Целевые Presentation modules: `fileapi`, `sitesapi`, `router`, `adminapi` и `adminui`. `fileapi` адаптирует File API к Loader; `sitesapi` адаптирует операции Website; `router` содержит только settings/delivery HTTP-адаптеры Router; `adminapi` управляет учётными записями и групповыми назначениями Core и служит внешней границей admin-операций Content/Forms; `adminui` только раздаёт собранные статические assets. Подробные контракты и текущая полнота каркаса перечислены в [SPEC-engine-apis.md](SPEC-engine-apis.md).

### Единая база и хранение данных движков

Платформа использует одну PostgreSQL-базу и одну схему данных `core`. Движки не имеют собственных баз, схем, DSN, runtime-учётных записей или Atlas migrations. Core — единственный владелец PostgreSQL-подключения и единственной Atlas migration history. Он хранит свои реляционные данные и общую таблицу `core.module_data`, в которой постоянные данные всех engines представлены как JSONB. Точная модель и контракт описаны в [SPEC-module-data.md](SPEC-module-data.md).

Каждый engine остаётся отдельным Go module и владельцем смысла своих данных: он определяет model/application/typed repository, JSON-контракт, валидацию, индексную проекцию и переходы версий данных. Физическое чтение и запись выполняются только через scoped typed Go API Core; engine не получает `*sql.DB`, DSN и произвольный SQL. Composition root регистрирует стабильный `module_id` и выдаёт модулю capability, ограниченную его данными. `module_id` нельзя передать или сменить из HTTP-запроса. Доступ к данным другого engine через этот API запрещён.

Core migrations единолично управляют DDL таблицы `module_data` и реляционными таблицами Core. Изменение JSON-схемы engine не добавляет SQL migration: engine версионирует payload и выполняет Go upcasting через свой scoped store. В Go-коде остаётся запрет на ad-hoc schema DDL. Presentation не владеет БД и обращается к engines/Core через типизированные Go-контракты.

`fileapi` преобразует HTTP в типизированные вызовы Loader; прямой вызов Core из File API запрещён. Loader владеет протоколом загрузки, состояниями, checksum, streaming/buffered режимом и очисткой незавершённых сессий. Все его состояния хранятся как JSON-документы namespace `loader` в `core.module_data`; кеш сессий локален и производен. Для файлов, авторизации, staging и наборов Loader использует Core capabilities и не обращается напрямую к БД/S3. CRUD FileSet проходит File API → Loader → Core; управляющая группа ограничивает операции с набором, а членство в наборе не предоставляет доступ к байтам.

`sitesapi` вызывает Website facade; фоновые workers Website напрямую используют только выданные Core file/identity/module-data capabilities. `presentation/router` вызывает только Router facade. Router сопоставляет URL с отдельным Core-файлом или manifest формата `static-site-artifact/v1`; вызовов handler других движков в Router v1 нет. Content и Forms предоставляют свои typed facades, которые может адаптировать Admin API. Все межмодульные вызовы внутри монолита — Go-вызовы; HTTP, gRPC и сокеты между engines не используются. `adminui` раздаёт собранные статические assets и не содержит доменной логики.

Website, Router, Content и Forms могут отсутствовать в минимальном Core-профиле. Loader обязателен для сборки с File API. Core обязателен. Admin API и Admin UI включаются отдельными presentation modules. Обращение к не включённой возможности возвращает управляемую ошибку. Feature ZIP и существующие runtime ABI `legacy-react-v1`, `static-module-v1` и `static-html-v1` сохраняются; изменение ABI требует отдельной согласованной спецификации.

## Core: данные и доступ

Core владеет файлами, статичными группами доступа и наборами, пользователями, credentials и назначениями прав в своих реляционных Core tables. Данные Website, Content, Forms, Loader и других engines сохраняются JSONB-записями в `core.module_data`; движок сохраняет собственные typed models и сериализует их в scoped namespace. S3 хранит байты файлов под UUID. Байты неизменяемы; версии файлов, владельцы и индивидуальные файловые права в Core отсутствуют. Core отвечает за Atlas migrations, typed module data storage API, файловый кеш, потоковый доступ к S3 и авторизацию файловых операций. Движок не читает таблицы напрямую. Подробные файловые правила и критерии: [SPEC-core-v2.md](SPEC-core-v2.md); контракт хранения: [SPEC-module-data.md](SPEC-module-data.md).

Loader хранит upload sessions, idempotency records, parts и cleanup tasks как отдельные JSON-документы в своём namespace `loader`. Эта запись — долговременный источник истины для рестарта и нескольких экземпляров; локальный session cache производный. Временные байты частей Loader передаёт в Core staging API: Core управляет S3 и выдаёт непрозрачные staging references. Финальная регистрация файла и актуальная проверка прав выполняются Core до выдачи файла.

Запись в S3 и транзакция БД не являются атомарной операцией. Контракт реализации обязан предотвращать выдачу незавершённого объекта и предусмотреть идемпотентный повтор, восстановление после сбоя и безопасную очистку осиротевших объектов без удаления объекта конкурентной операции. Права проверяются до доступа к приватному содержимому и перед условной или кешированной выдачей.

Core всегда проверяет авторизацию. Статичные группы доступа определяют уровни `0/1/2`, назначаемые напрямую администраторам и сервисным учётным записям. Ролей и отдельных обычных пользователей нет. Управляющий администратор может создавать учётные записи и менять назначения только в группах, где имеет собственный уровень `2`; право управления администраторами делегируется отдельно. Файл может входить в несколько групп; достаточно разрешения одной из них. Динамические наборы создаются движками для поиска и не дают прав. Индивидуальных файловых разрешений, владельцев и неявного полного доступа администратора нет.

Все учётные записи представлены одной сущностью пользователя, без поля типа `kind`. Сервис — обычный пользователь со своим ключом и прямыми назначениями; слово «администратор» не задаёт отдельный тип или автоматические привилегии.

Первый администратор создаётся при первом запуске с правом управления администраторами и уровнем `2` во всех группах по умолчанию либо с явными ограничениями конфигурации. YAML инициализирует его назначения при создании и при первом появлении новой группы, не перезаписывая последующие изменения. Нельзя потерять последнего действующего управляющего администратора; предусмотрено операторское восстановление. При отсутствии заданного секрета создаётся криптографически случайный секрет, который выводится в журнал только при создании; хранится только проверочный хеш. Требуется безопасная процедура сброса, сериализация конкурентного bootstrap и документация о доступе к журналам. Секреты конфигурации поступают через окружение или файл секретов.

## Маршруты и пользовательские контракты

Router назначает адреса файлам либо операциям движков. Только явно настроенные публичные маршруты позволяют анонимную выдачу; Router обращается к Core со своей сервисной идентичностью и ограниченными правами. Движки могут резервировать маршруты; резервации и конфигурация записываются как файлы через Core. Общий файл содержит область действия веток. Изменение маршрута одной ветки не меняет поведение другой, а конфликты пользовательских и зарезервированных маршрутов должны выявляться до публикации. Изменённая конфигурация создаётся новым файлом; движок атомарно переключает свою ссылку. Снапшоты и явные назначения веток сохраняют действующие гарантии.

Website управляет каталогом фич, импортом ZIP, сайтами/snapshots, сборкой, prerender и медиа-обработкой (включая FFmpeg). Каждый импорт создаёт собственный FileSet в настроенной управляющей access group; доступ к файлам остаётся только групповым и не следует из FileSet membership. Content отвечает за snapshot-scoped модели и записи; Forms — за схемы и отправки. Движки проверяют только собственные ссылки; Core не ведёт глобальный реестр. Удаление общего файла выполняется отдельным явно уполномоченным workflow и не опрашивает engines.

Внешние HTTP API, формы ошибок, поддерживаемые форматы, feature ABI и существующие сценарии остаются целевым требованием совместимости, **за исключением** отменённых поля `role` и матрицы ролей `admin/moderator/staff/user`: новый API и админка переходят на индивидуальные права. Исторические версии контента, снапшоты, публичная выдача и предупреждения об удалении при необходимости реализуются engines и presentation, без версий файлов, публичного флага и глобальных ссылок в Core. Эта совместимость ещё не реализована и не проверена. Sitepack, экспортированный текущей поддерживаемой версией продукта, должен импортироваться с сохранением структуры, данных и файлов. Это не расширяет текущий Sitepack-контракт на исторические форматы, которые он уже отклоняет; их поддержка требует отдельного решения. Прямая миграция существующей БД не входит в текущий план.

## Перенос и приёмка

До переноса составить инвентаризацию маршрутов и методов API, форматов Sitepack и manifest, прав, интеграций, runtime ABI и пользовательских сценариев, затем сохранить проверяемые контрактные примеры. Перемещение в `legacy/` должно сохранить исполняемость и сборку эталона, включая относительные пути, frontend assets, Docker, миграции и команды CI; пользовательские данные и секреты не перемещать и не удалять. Новая реализация создаётся рядом и не объявляется заменой до полного паритета.

Приёмка включает сравнение поддерживаемых внешних контрактов, единый Core File API, групповые права, fail-closed поведение, конкуренцию и восстановление PostgreSQL/S3, независимость snapshot/Router release, работу минимального и full build profiles, Sites/Router/Admin APIs, UI delivery, browser QA и применимые Vitasil сценарии. Интеграции выполняются только на явно изолированных одноразовых ресурсах. Результаты и ограничения записываются в QA-отчёт; TODO закрывается только по фактическим результатам.
