# Публичные Go-контракты Website, Content и Forms

Статус: проект границ для приёмочных тестов; наличие описания не означает реализации. Приоритет общих правил и неразрешённые вопросы — [SPEC-coordinator-platform.md](SPEC-coordinator-platform.md) и [SPEC-architecture-review.md](history/SPEC-architecture-review.md). Каждый engine предоставляет типизированный facade из своего `presentation` package и не импортирует другие engines. Coordinator и Presentation передают им только явно выданные полномочия и зарегистрированные операции.

## Общие гарантии

- Входы содержат контекст отмены, сгенерированные системой идентификаторы, ожидаемые ревизии для изменяемых записей и ключ идемпотентности для повторяемых операций. Ни один endpoint не принимает DSN, S3 key, namespace или identity модуля от внешнего клиента.
- Ошибки позволяют различить недействительный ввод, отсутствие авторизации, отказ в доступе, недоступный или несуществующий ресурс, конфликт ревизии/идемпотентности и временную недоступность. Публичный слой не раскрывает наличие закрытых файлов или внутренние ошибки хранилища.
- После вызова авторизация проверяется Core на актуальном состоянии. Сбои между Core файлами и данными модуля обрабатываются durable workflow и повтором; общая распределённая транзакция не предполагается.
- Для каждого приёмочного случая фиксируются входные данные, предварительное состояние, действие, ожидаемый результат и постусловие. Табличные варианты считаются отдельно, но список вариантов заранее фиксируется и включает отказ, конкуренцию и восстановление; добавление множества одинаковых успешных вариантов не должно искусственно увеличивать показатель.

## Website

Facade принимает существующий `source_file_id`, idempotency key и необязательный ожидаемый digest. Клиент не задаёт целевой FileSet. Создание job проверяет полномочия пользователя и возвращает durable ID и состояние. При совпадении ключа и fingerprint возвращается та же job; другой fingerprint даёт конфликт. Worker через Core и настроенную capability проверяет ZIP, создаёт FileSet и файлы с группами исходника. Только после проверки результата и окончательного удаления архива версия становится `ready`; отказ очистки оставляет задачу в состоянии повтора.

Чтение каталога и jobs учитывает разрешения. Snapshot фиксирует идентичности и версии; изменение создаёт потомка. Задание сборки фиксирует входной snapshot и возвращает ID результата только после готовности. Website не вызывает Router и не переключает маршрут. Новые feature ZIP используют только согласованный lifecycle `render/hydrate/update/dispose`; формат manifest и точная форма context пока не согласованы и не должны выдумываться тестом.

## Content

Facade предоставляет чтение моделей и записей, сохранение черновика, явную публикацию и восстановление с ожидаемой ревизией. Модели содержат типы полей, cardinality и переводимость; разрешённые locale и порядок fallback задаются конфигурацией и не могут содержать циклы. Неизменяемые опубликованные ревизии передаются в рендер как зафиксированные входы. Конфликт или недействительные значения не меняют опубликованные данные и не перезаписывают чужой черновик.

Feature-owned browser requests are declared by each feature manifest and executed by feature code; external origins and typed request/response contracts follow [SPEC-feature-runtime.md](../engines/website/features/SPEC-feature-runtime.md). Request paths or parameters that vary by published record enter through the feature's typed `dataInputs` mapping. The site-level backend registry and placement request bindings are not part of the target contract. Routes support named parameters and Go RE2; template syntax and locale configuration remain open. Successful publication that needs a media derivative waits for a confirmed Media Worker result; an error does not replace the current published artifact.

## Forms

Административный facade управляет конфигурацией и опубликованной ревизией схемы, читает и удаляет результаты с актуальными Core group permissions. Публичный facade создаёт ограниченную по времени сессию опубликованной формы, возвращает непрозрачное полномочие для этой сессии и подтверждает отправку только с файлами, связанными с ней через сервер. Presentation координирует Loader и Forms; движки друг друга не вызывают.

Сессия позволяет возобновить части после перезагрузки до истечения срока. Истечение, изменение схемы или снятие публикации запрещает отправку и инициирует точечную очистку временных и загруженных файлов. Повтор подтверждения с тем же idempotency key и fingerprint возвращает тот же результат; изменённый fingerprint конфликтует. Готовые ответы неизменяемы, хранятся до удаления и не становятся публичными от факта отправки. Авторизованное удаление окончательно удаляет ответ и его вложения с durable повтором после частичной ошибки.

Точная форма транспортного token, его сериализация, лимиты и API связи конкретного upload session с form session ещё требуют проектирования. Пока нельзя считать отсутствие методов этих деталей свидетельством протестированного поведения.

## Статус тестирования

Текущие Go interfaces являются неполным каркасом: Forms не предоставляет публичную сессию формы; Content не выражает locale и policy fallback; Website не реализует durable import/build. До появления конкретных production adapters невозможно честно выполнять большинство поведенческих acceptance-сценариев. Тесты не должны проверять поведение собственной заглушки или выдавать такую проверку за покрытие engine.
