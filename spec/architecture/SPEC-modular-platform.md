# Модульная платформа Zubrium: целевая архитектура

> **Актуальное решение:** по устройству Core, Coordinator, PostgreSQL schemas и междвижковых durable workflows приоритет имеет [SPEC-core-architecture.md](../core/SPEC-core-architecture.md). Она заменяет прежние решения о single-schema Core, внешнем Coordinator и route-specific persistence внутри Core.

> **Модульная платформа:** [SPEC-coordinator-platform.md](SPEC-coordinator-platform.md) описывает profiles, независимые runtime modules и общие durable workflows. Core остаётся независимым от engines, workers и Presentation: все внешние обращения к Core проходят через DataBus, связанный с Core только в `main`. Реализация этого boundary ещё требует миграции и полной проверки.

Статус: целевая архитектура модульной платформы. Текущая реализация и границы её проверки указаны в [QA_REPORT.md](../../docs/QA_REPORT.md); открытая работа перечислена в [TODO](../../docs/TODO-admin-snapshots-content-files.md).

## Границы и сборка

Платформа — статически компонуемый Go-монолит. Единственный product executable, composition root и путь сборки/запуска платформы — Go module в `main/`; его тонкий entrypoint расположен в `main/cmd/zubrium/main.go` и является единственным файлом под `main/cmd/`. CLI находится в `main/internal/command`, runtime composition и статические профили — в `main/internal/composition`, конфигурация — в `main/internal/config`. Makefile и deployment build targets собирают только `main`-бинарник с выбранным статическим profile.

Core, каждый engine, worker и каждый HTTP/UI-компонент Presentation остаются самостоятельными Go modules, которые можно отдельно компилировать и тестировать, но не обязаны выпускать собственные binaries. Целевые engines: Loader, Website, Router, Content и Forms. Каждый engine предоставляет типизированный facade; его операции объединяют принадлежащие engine features. Каждая feature оформляется пакетами `model`, `application`, `repository` и `pkg`. Profile generator формирует статические imports, а composition root регистрирует выбранные компоненты. Динамическая загрузка библиотек не поддерживается.

`main` содержит process-local synchronous request/response DataBus; независимые operation contracts принадлежат корневому Go-модулю `pkg` (`pkg/contracts`). Прямые межмодульные вызовы запрещены без исключения. Presentation → engine и любой модуль → Core проходят только через bus. Engine → engine через bus тоже запрещено: такие взаимодействия разлагаются на Core Coordinator workflow из независимых operation tasks с class-scoped worker’ами; только этот путь асинхронный. Worker tasks обращаются к движкам и Core только через DataBus. Внутри одного модуля его слои и пакеты вызывают друг друга напрямую. Bus принимает только операции, статически зарегистрированные выбранным build profile, и маршрутизирует общий JSON envelope (`operation_id`, `version`, `payload`) к typed контракту владельца; payload строго декодируется и валидируется. HTTP остаётся ingress: adapter вызывает заранее назначенную operation, не раскрывает envelope и не принимает от клиента operation ID. Большие файлы передаются через отдельную scoped stream capability, не через JSON. Только adapter в `main` связывает DataBus Core operations с `core/presentation`; engines, workers и Presentation не импортируют Core. `main` не содержит бизнес-правил и не открывает SQL, S3 или Core infrastructure. Bus не хранит durable state, не гарантирует доставку после остановки процесса и не оркестрирует product workflows. Работа, требующая retry, leases, зависимостей или восстановления после restart, проходит через Core Coordinator, вызванный по DataBus. Прямые межмодульные вызовы запрещены.

Целевые Presentation modules: `fileapi`, `sitesapi`, `router`, `adminapi` и `adminui`. `fileapi` адаптирует File API к Loader; `sitesapi` адаптирует операции Website; `router` содержит только settings/delivery HTTP-адаптеры Router; `adminapi` управляет учётными записями и групповыми назначениями Core и служит внешней границей admin-операций Content/Forms; `adminui` только раздаёт собранные статические assets. Подробные контракты и текущая полнота каркаса перечислены в [SPEC-engine-apis.md](SPEC-engine-apis.md).

### Единая база и хранение данных движков

Платформа использует одну PostgreSQL database на логическую систему. Core — единственный владелец подключения и одной Atlas migration history, которая управляет схемами bounded contexts `access`, `files`, `uploads`, `file_index`, `engine_data` и `coordination`. Движки не имеют собственных DB credentials, SQL-доступа или Atlas migrations. Постоянные engine documents хранятся в общей scoped таблице `engine_data.records`; контракт, DDD-слои и физическая модель описаны в [SPEC-core-architecture.md](../core/SPEC-core-architecture.md).

Каждый engine остаётся отдельным Go module и владельцем смысла своих данных: он определяет модели, валидацию, JSON-контракт, индексную проекцию и переходы версии payload. Engine обращается к Core module-data через scoped operation bus и свой typed contract; `main` адаптирует вызов к Core capability. Engine не получает `*sql.DB`, DSN и произвольный SQL. `main` связывает стабильный opaque owner scope с DataBus client; scope нельзя выбрать или сменить из HTTP-запроса. Core хранит только нейтральный namespace и не знает engine identity.

Core migrations единолично управляют DDL всех Core schemas и таблиц. Изменение JSON-схемы engine не добавляет SQL migration: engine версионирует payload и выполняет Go upcasting через свой scoped store. В Go-коде запрещены ad-hoc schema DDL. Presentation не владеет БД и обращается к engines и Core только через типизированные DataBus contracts.

`fileapi` преобразует HTTP в заранее назначенные DataBus operations Loader; ни File API, ни Loader напрямую не импортируют Core. Loader владеет протоколом загрузки, состояниями, checksum, streaming/buffered режимом и очисткой незавершённых сессий. Его sessions, parts и cleanup tasks хранятся как документы в scoped `engine_data.records`; локальный session cache производен. Для файлов, авторизации, staging и наборов Loader вызывает только выделенные DataBus contracts; Core adapters в `main` выполняют соответствующие Core операции. CRUD FileSet проходит File API → DataBus → Loader → DataBus → Core; управляющая группа ограничивает операции с набором, а членство в наборе не предоставляет доступ к байтам.

`sitesapi` вызывает Website через DataBus; фоновые workers Website вызывают только выданные DataBus file/identity/record operations. Website возвращает валидированный manifest `static-page-artifact/v1`; он не назначает route и не вызывает Router. `presentation/router` направляет запросы зарегистрированным DataBus operations Router и связывает точный route с готовым page artifact. Exact route выдаёт один document, а assets разрешаются внутри того же artifact без fallback. Публичная доставка по умолчанию закрыта; байты upload routes проходят через operation → Loader → Core. Произвольные callbacks, operation IDs от посетителя, engine URLs и прямые storage writes запрещены. Content и Forms вызываются внешними Presentation adapters только через typed DataBus operations, без прямых facade handle’ов. Engine не импортирует и не вызывает другой Engine ни прямо, ни через DataBus; если workflow затрагивает несколько движков, его оркестрирует generic Core Coordinator как несколько независимых operation tasks, а worker’ы сами обращаются к движкам только через DataBus. Worker’ы не являются синхронным продолжением HTTP-запроса: асинхронность допустима только для междвижковых цепочек. Все межмодульные вызовы внутри монолита — Go-вызовы; HTTP, gRPC и сокеты между engines не используются. `adminui` раздаёт собранные статические assets и не содержит доменной логики. Общий browser transport (cookies, CSRF, Origin) выделен в нейтральный Presentation module `presentation/httpauth`; и Admin, и публичный Router используют его напрямую, не импортируя друг друга. SSE-уведомления Admin выделены в отдельный module `presentation/admin/base/notification`. Базовый Admin HTTP-сервер не знает engine facade и feature-модулей: он получает от `main` таблицу `HandlerMount` с уже сконструированными HTTP-хендлерами, применяет общий Core-ready guard и terminal 404. Модули Content, Forms, Website, Router, Files и Coordinator собираются в `main` из нейтральных `pkg/contracts`; базовый модуль больше не импортирует их и не образует cycle в `go.mod`.

### Durable workflow как единственный путь междвижковой цепочки

Core Coordinator хранит оркестрацию, но не знает доменных engine-контрактов. Корневая workflow-операция только валидирует неизменяемый payload и объявляет children с фиксированными operation ID, версией и task class; она не вызывает другой engine. Каждый child выполняется отдельным class-scoped worker’ом через DataBus. Зависимости между children задаются emission key, а не переданным клиентом task ID. Для `snapshot.fork.start` корневая задача порождает независимые `snapshot.fork.copy-content` (class `engine.content`) и `snapshot.fork.finalize` (class `engine.website`), причём finalize ожидает успешного copy. Publication (`publication.publish.start`) порождает build (class `engine.website`), activate (class `engine.router`) и finalize с зависимостью по emission key. Retirement (`retirement.retire.start`) порождает удаление каждой route (class `engine.router`) и page finalize (class `engine.website`) после всех route emissions. Content↔Website projection/build input/locale catalog также проходят через root workflow в `main/internal/contentbridge`: root только валидирует server-owned payload и эмитит children с фиксированными operation ID, версией, task class и `DependsOnEmissions`; прямых вызовов `engine.content → engine.website` и наоборот нет. Старт workflow для Admin привязан к module ID `admin.api`; клиентский HTTP-payload не может выбрать operation ID, class, owner или Core capability.

Компилируемый static allowlist DataBus точен для каждого профиля: непредусмотренная операция не попадает в реестр, а module-scoped dispatcher отклоняет операцию вне своего набора до вызова базового dispatcher’а. Тесты фиксируют полный набор ключей для `default`, `full`, `router` и `development-fixtures`, а также то, что HTTP request schema не содержит `operation_id`/`operationId`.

Website, Router, Content и Forms могут отсутствовать в минимальном Core-профиле. Loader обязателен для сборки с File API. Core обязателен. Admin API и Admin UI включаются отдельными presentation modules. Обращение к не включённой возможности возвращает управляемую ошибку. Целевой runtime принимает только ABI `static-lifecycle` с lifecycle `render / hydrate / update / dispose`; сборка проверяет manifest и отклоняет неподдерживаемый ABI без преобразования.

## Core: данные и доступ

Core владеет файлами, статичными группами доступа и наборами, пользователями, credentials и назначениями прав в bounded-context schemas. Активные группы задаются startup YAML и статическими group declarations выбранного profile, которыми управляет `main`; глобально уникальное имя является `group_key`, отдельный ID в YAML отсутствует. Повтор совпадающего имени объединяет объявления в одну группу. `main` передаёт Core объединённый список активных group keys вместе с конфигурацией до bootstrap/reconcile; Core не получает component descriptors и не знает владельцев групп. Явно заданный YAML bootstrap level, включая `0`, имеет приоритет, а не переопределённые группы движка получают начальный bootstrap level `2`. Profile сейчас задаёт group keys `features`, `content`, `router_routes`, `forms_schemas` и `forms_submissions`. Неактивная группа сохраняет назначения и связи файлов без доступа; повторное объявление того же имени реактивирует прежнюю группу без перезаписи этих данных. Данные Website, Content, Forms, Loader и других engines сохраняются JSONB-документами в `engine_data.records`; движок сохраняет собственные typed models в scoped capability. S3 хранит байты файлов под внутренними UUID keys. Байты неизменяемы; версии файлов, владельцы и индивидуальные файловые права в Core отсутствуют. Core отвечает за Atlas migrations, scoped record API, файловый cache, потоковый доступ к S3 и авторизацию файловых операций; внешние модули вызывают эти возможности только через DataBus. Подробности: [SPEC-core-architecture.md](../core/SPEC-core-architecture.md).

Loader хранит upload sessions, parts, engine-level idempotency records и cleanup tasks как отдельные JSON-документы в своём namespace `engine_data.records`. Эта запись — долговременный источник истины для рестарта и нескольких экземпляров; локальный session cache производный. Core staging/finalize idempotency хранится отдельно в schema `uploads`. Временные байты частей Loader передаёт в Core staging API: Core управляет S3 и выдаёт непрозрачные staging references. Финальная регистрация файла и актуальная проверка прав выполняются Core до выдачи файла.

Запись в S3 и транзакция БД не являются атомарной операцией. Контракт реализации обязан предотвращать выдачу незавершённого объекта и предусмотреть идемпотентный повтор, восстановление после сбоя и безопасную очистку осиротевших объектов без удаления объекта конкурентной операции. Права проверяются до доступа к приватному содержимому и перед условной или кешированной выдачей.

Core всегда проверяет авторизацию. Статичные группы доступа определяют уровни `0/1/2`, назначаемые напрямую администраторам и сервисным учётным записям. Группы могут объявляться startup YAML или статической конфигурацией profile (например, отдельные группы для схем и отправок Forms); Core получает только итоговый набор ключей. Совпадающие глобально уникальные имена обозначают одну группу. Ролей и отдельных обычных пользователей нет. Управляющий администратор может создавать учётные записи и менять назначения только в группах, где имеет собственный уровень `2`; право управления администраторами делегируется отдельно. Файл может входить в несколько групп; достаточно разрешения одной из них. Динамические наборы создаются движками для поиска и не дают прав. Индивидуальных файловых разрешений, владельцев и неявного полного доступа администратора нет.

Все учётные записи представлены одной сущностью пользователя, без поля типа `kind`. Сервис — обычный пользователь со своим ключом и прямыми назначениями; слово «администратор» не задаёт отдельный тип или автоматические привилегии.

Первый администратор создаётся при первом запуске с правом управления администраторами и уровнем `2` во всех активных группах, если YAML не задал другой bootstrap-уровень. Явный уровень startup YAML имеет приоритет над уровнем из profile; для группы, впервые объявленной profile, начальный уровень равен `2`. Последующие изменения групповых уровней сохраняются при restart и реактивации прежнего имени. Нельзя потерять последнего действующего управляющего администратора; предусмотрено операторское восстановление. При отсутствии заданного секрета создаётся криптографически случайный секрет, который выводится в журнал только при создании; хранится только проверочный хеш. Требуется безопасная процедура сброса, сериализация конкурентного bootstrap и документация о доступе к журналам. Секреты конфигурации поступают через окружение или файл секретов.

## Маршруты и пользовательские контракты

Router назначает адреса файлам, готовым `static-page-artifact/v1` артефактам либо зарегистрированным операциям. Только явно настроенные публичные маршруты позволяют анонимную выдачу; Router выполняет разрешённые операции с Core только через scoped DataBus client, связанный в `main` с сервисной идентичностью и ограниченными правами. Маршрут связывается с одним точным артефактом страницы; документ и его объявленные assets выдаются в рамках этого маршрута, без fallback. Ветки статически задаются при запуске: для каждой запускается отдельный Router с её branch ID и listener. Website snapshot принадлежит `page_id`, не содержит route или URL и не назначается ветке; публикация готового артефакта на адрес выполняется только через Router. Конфликты маршрутов выявляются до публикации.

Website управляет каталогом фич, импортом ZIP, независимыми деревьями page snapshots, сборкой, prerender и медиа-обработкой (включая FFmpeg). Каждый импорт создаёт собственный FileSet в настроенной управляющей access group; доступ к файлам остаётся только групповым и не следует из FileSet membership. Content использует system-scoped модель и записи, а selections и порядок относятся к конкретному page snapshot; Forms отвечает за схемы и отправки. Движки проверяют только собственные ссылки; Core не ведёт глобальный реестр. Удаление общего файла выполняется отдельным явно уполномоченным workflow и не опрашивает engines.

Внешние HTTP API и форматы данных определяются актуальными спецификациями Presentation и соответствующих engines. Версии внешнего API в URL не используются; сохраняются внутренние версии content, snapshots, feature builds, schema/payload contracts, component contracts и Atlas migration history. Прямая миграция существующей установки не является частью target-контракта; функциональность, не представленная действующими API и acceptance-сценариями, не переносится автоматически.

## Перенос и приёмка

Приёмка включает единый Core File API, групповые права, fail-closed поведение, конкуренцию и восстановление PostgreSQL/S3, независимость snapshot/Router publication, работу минимального и full build profiles, APIs, UI delivery, browser QA и применимые сценарии. Интеграции выполняются только на явно изолированных одноразовых ресурсах. Результаты и ограничения записываются в QA-отчёт; TODO закрывается только по фактическим результатам.
