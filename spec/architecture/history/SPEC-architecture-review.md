# Сверка новой архитектуры Coordinator

Статус: журнал архитектурной сверки. Более поздние решения о слоях Core, схемах БД и workflow зафиксированы в [SPEC-core-architecture.md](../../core/SPEC-core-architecture.md) и имеют приоритет ниже. Пользователь согласовал одну систему на БД, общий `engine_data.records`, новый пустой Atlas baseline и динамические durable workflows. Исторические вопросы ниже не являются открытыми решениями, если они противоречат этим контрактам; исторические заметки не подтверждают выполнение acceptance.

## Направление

Профиль сборки выбирает engines, workers, административные и публичные API и автоматизации. Генерируемый Coordinator связывает только выбранные компоненты. YAML запуска конфигурирует включённые компоненты и связи; неизвестная или отсутствующая в сборке возможность отклоняется при запуске. Все обращения к PostgreSQL и S3 проходят через Core, а engines не вызывают друг друга напрямую. Административные API работают на одном порту, публичная обработка Router — на отдельном.

Core остаётся владельцем пользователей единого типа, прямых групповых прав, неизменяемых файлов, FileSet и данных модулей. Новая целевая физическая схема — `public`, с одной историей Atlas; текущий код со схемой `core` сам по себе не подтверждает переход. Структуру служебных таблиц следует вывести из сценариев надёжности, а не переносить автоматически. Данные существующих БД не удаляются и не преобразуются без отдельного решения об эксплуатации.

Router разрешает публичный запрос в типизированное решение; зарегистрированное Coordinator действие выполняет внешний адаптер. Привязка к обработчику не даёт ему дополнительные права Core. Публичная отправка формы разрешена только через явно опубликованный маршрут. Загрузки обслуживает Loader, а согласование анонимной формы и её вложений выполняет presentation.

Website строит основу, Content инициирует применение опубликованного содержимого, а Coordinator может назначить готовый artifact Router по настройке. Archive, Media и Prerender — отдельно выбираемые workers; их работа восстанавливается после сбоев. Durable jobs, instance leases/fencing и атомарное переключение одного route спроектированы и реализованы в Core/Coordinator; trigger wiring, настоящие worker handlers, Router runtime и сквозное восстановление после внешних эффектов ещё требуют реализации и изолированной проверки.

## Изменения относительно прежних решений

| Область | Ранее | Новое направление |
| --- | --- | --- |
| Router | Только Core file или artifact, без handler routes | Сохраняется: Coordinator автоматизирует переключение route, не меняя допустимые target types |
| Публикация | Клиент отдельно переключает Router | Coordinator может переключать route автоматически при включённой связи |
| Workers | Архив, медиа и prerender внутри Website | Независимые подключаемые workers, доступные разрешённым движкам |
| БД | Таблицы в `core` | Целевая схема `public`, короткие имена и Atlas |
| Presentation | Отдельные модули API | Один административный порт и отдельный публичный порт, состав API выбирается профилем |
| Продуктовый runtime | Три существующих ABI | Только новый `render/hydrate/update/dispose`; текущие ZIP адаптируются |

Предыдущее решение о `no-store` по умолчанию, явном fallback и атомарности одного маршрута не отменено явно. Оно применяется к новой модели до отдельного изменения. Переключение набора маршрутов не считается атомарным.

## Решения пользователя от 17 ноября 2026

1. Website создаёт FileSet версии по настроенной управляющей группе; клиент передаёт исходный file ID, но не FileSet.
2. Новая версия поддерживает только новый ABI; текущие ZIP Vitasil необходимо адаптировать. Фактическая совместимость старых архивов не предполагается.
3. Ручное изменение route не выключает автоматизацию: следующая успешная публикация снова назначает рассчитанный artifact.
4. Admin UI использует общий UI provider. Его контракт, доставка, независимость доступности административного входа и совместимость версий требуют проектирования.
5. Публичные маршруты Content поддерживают именованные параметры и ограничения Go RE2; точный синтаксис и нормализация ещё определяются.
6. Экземпляр с отличающимися YAML-связями того же сайта и маршрута не запускается. Состав сравниваемой конфигурации и протокол её обновления ещё определяются; секреты не должны раскрываться в диагностике.
7. При ошибке применения контента продолжает выдаваться текущая публикация, задача повторяется согласно настроенной политике.
8. Посетитель может возобновить загрузку вложения после перезагрузки страницы до истечения срока сессии формы. Восстановление не должно раскрывать другим посетителям сессию или файлы.
9. Отправленные ответы форм нельзя редактировать; просмотр и удаление определяются групповыми правами.
10. Перед обновлением YAML-связей останавливаются все экземпляры; после обновления одинаковой конфигурации экземпляры запускаются снова. Протокол проверки и регистрации активных экземпляров необходимо определить.
11. По истечении сессии формы посетитель начинает отправку и загрузку заново; перенос вложений между сессиями не предусмотрен.
12. При недоступности общего UI provider вход и настройка системы остаются доступны через встроенный минимальный резервный интерфейс. Точный перечень его операций уточняется.
13. Удаление ответа формы окончательно удаляет сам ответ и все его вложения целиком, включая членство в других группах и наборах. Последствия и порядок обработки частичных ошибок должны быть явно описаны и проверены.
14. Снятие формы с публикации или изменение её схемы закрывает незавершённые сессии и запрещает их отправку. Для продолжения посетителю потребуется новая сессия по актуальной опубликованной схеме.
15. Резервный интерфейс ограничивается входом и восстановлением настройки общего UI provider; предоставление остальных административных функций не требуется.
16. В резервном интерфейсе выбирается ранее загруженная совместимая версия UI provider; загрузка нового ZIP в нём не предусмотрена.
17. Для удаления ответа и всех вложений достаточно обычного подтверждения удаления ответа. Оно не требует отдельного подтверждения для других групп и наборов.
18. При снятии формы с публикации или изменении её схемы незавершённые сессии отменяются, а их временные и уже загруженные файлы безопасно очищаются.
19. Выбор другой совместимой версии общего UI provider в резервном интерфейсе сразу после проверки совместимости переключает админку и отдельно запускает пересборку и переключение затронутых опубликованных сайтов. Для каждого затронутого сайта создаётся дочерний snapshot с новой версией provider. Обновление запускается и для маршрутов с выключенной автопубликацией. Если конкретный сайт не удалось обновить, он остаётся на прежней версии; оператор видит ошибку и вручную запускает повтор. Сайт отдаёт прежний artifact до успешной сборки и переключения.
20. Ответы форм хранятся бессрочно до явного удаления.
21. После исчерпания попыток автопубликации оператор вручную запускает повтор; до успешного завершения сохраняется текущая публикация.
22. Версию UI provider через резервный интерфейс выбирает пользователь с уровнем 2 в выделенной группе доступа provider. Название группы задаётся конфигурацией; право управления пользователями само по себе доступа не даёт.
23. Если во время обновления provider опубликована более свежая версия сайта, устаревший результат не переключается: обновление пересобирается от новой публикации.
24. Если один snapshot назначен нескольким маршрутам, для обновления provider создаётся один дочерний snapshot; затронутые маршруты переключаются по отдельности.
25. Если выбранная версия provider несовместима с опубликованной фичей сайта, этот сайт не обновляется, причина показывается оператору, а прежняя публикация остаётся активной.

## Исходный перечень вопросов к исходной спеке

Раздел сохранён как история анализа, а не как актуальный блокирующий опрос. Ответы и текущий статус см. в решениях пользователя и специализированных спецификациях выше.

### Сборка и конфигурация

- Определить формат профиля, версию формата, команду генерации и проверку воспроизводимости. Фиксировать зависимости компонентов в декларациях сборки и проверять отсутствующие зависимости, циклы и неизвестные имена до компиляции. Динамическая загрузка модулей в предлагаемую первую версию не входит.
- Уточнить идентичность конфигурируемых сайтов, контентных источников, маршрутов и воркеров, а также поведение удаления связи из YAML при следующем запуске. Несовпадение YAML-связей экземпляров запрещено; обновление выполняется с остановкой всех экземпляров. Требуется определить канонизацию и атомарное сравнение при запуске, обнаружение оставшегося старого экземпляра и восстановление после аварийной остановки.
- Определить жизненный цикл запуска и остановки, readiness при отказе зависимости, политику секретов и требования к версиям профиля и YAML. Профиль определяет наличие кода, YAML не добавляет код в бинарник.

### Автопубликация и конкурентность

- Определить источник монотонного поколения связки, момент его изменения и неизменяемый набор входов: snapshot, версия основы, опубликованная revision контента, конфигурация и route revision.
- До реализации доказать протокол, при котором только результат актуального поколения может сменить route, даже после истечения lease, смены конфигурации, ручного переключения или падения между сохранением результата и обновлением route. Проверить, достаточно ли существующих CAS и batch одной namespace; иначе описать минимальную транзакционную возможность Core. Нельзя объявлять последовательные операции разных модулей атомарными.
- Определить дедупликацию событий, порядок coalescing нескольких публикаций, отмену и очистку результатов устаревших задач, повтор после неопределённого ответа и наблюдаемое состояние частичного отказа. Старая активная публикация сохраняется при ошибке до успешного переключения.

### Workers и задания

- Согласовать, какой компонент владеет долговременной записью задания, кто может ставить и отменять его, и как подтверждаются claim, lease и fencing token. Истекший исполнитель не должен подтверждать результат; повторная работа не должна публиковать дубликаты или удалять чужие файлы.
- Определить формат входа и результата каждого worker, ограничения ресурсов, isolation, timeout, retry/backoff, максимальное число попыток, очистку временных объектов и политику хранения ошибок. Core credentials и произвольные команды/пути не передаются из публичных запросов.
- Проверить применимость `module_data` к очереди: конкурентный claim, доступность, starvation, индексы, истечение lease и атомарная фиксация результата. При необходимости отдельная возможность остаётся владением Core.

### Анонимные формы и загрузки

- Определить срок и область действия непрозрачного секрета сессии формы, binding к опубликованной ревизии, полям и конкретной загрузке, отзыв и защиту от подмены `file_id`. Возобновление после перезагрузки доступно до истечения срока; финализация проверяет завершённые файлы и связь с сессией на сервере.
- Определить права отдельной сервисной идентичности для загрузки, проверку типов и размеров, лимиты на посетителя и форму, срок незавершённых сессий, cleanup orphan-файлов и поведение при повторе после потери ответа. Подтверждённая отправка должна быть идемпотентной; черновые файлы не раскрываются посетителю по одному UUID.
- Ответы не редактируются и хранятся до явного удаления. Изменение схемы или снятие публикации отменяет незавершённые сессии и очищает их файлы. Удаление ответа окончательно удаляет его и все вложения после обычного подтверждения; обеспечить безопасное возобновление удаления после частичной ошибки.

### Данные Content и граница браузера

- Определить локализацию: наследование и удаление локалей, отсутствие перевода, fallback и стабильность опубликованных ревизий. Уточнить владение связью snapshot и контента и момент создания независимой копии данных потомка.
- Целевое решение: манифесты фич объявляют точные разрешённые `https` origins и типизированные контракты запросов/ответов; feature code выполняет browser requests, CORS проверяется удалённым сервисом, а `connect-src` формируется из точных origins закреплённых manifest-ов. Опубликованный Content может передавать относительные paths или типизированные параметры, но не менять origin. В target нет site-level backend registry, редактора per-placement request bindings, proxy или внешней сети для prerender worker. Нормативный контракт: [SPEC-feature-runtime.md](../../engines/website/features/SPEC-feature-runtime.md).
- Определить формат входа/выхода обоих этапов prerender, фиксируемые зависимости, локали, динамические маршруты, политику сетевого доступа и поведение при отсутствии контента. Новый ABI требует точных схем context, ошибок и lifecycle, а также стратегии миграции согласованных ZIP.

### Router и административные права

- Определить типизированные разновидности действий и их версии, таблицу разрешённых методов и путь регистрации без пользовательских функций или произвольных URL. Уточнить конфликты routes, резервирование системных API, доверенные proxy и нормализацию host/path.
- Явно назначить необходимые группы для настройки каждой возможности и сервисные идентичности публичных обработчиков. Уровень 1 даёт чтение, уровень 2 — запись; право управления пользователями отдельно и не заменяет групповые права. Выдача групп требует право управления пользователями и уровень 2 у выдающего.
- Согласовать контракт ошибок и раскрытие существования закрытых ресурсов, cache policy, ограничения запросов, аудируемые административные действия и изоляцию branch/host.

## Критерии готовности спецификации

Согласованные контракты описывают владельца данных, права, входы и выходы, проверки, состояния, конкурентные изменения, сбои, восстановление, границы кеширования и приёмочные сценарии. Изменения общей архитектуры отражаются в соответствующих специализированных документах с явным статусом. Реализация считается подтверждённой только после проверки исходного кода и изолированных тестов; записи о legacy являются историческими свидетельствами, а не доказательством новой реализации.
