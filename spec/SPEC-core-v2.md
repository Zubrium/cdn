# Core v2: файловое ядро

Статус: историческая спецификация файлового Core v2 и текущей реализации. Целевая архитектура, DDD-слои, раздельные PostgreSQL schemas и встроенный Coordinator определяются [SPEC-core-architecture.md](SPEC-core-architecture.md), которая имеет приоритет при любом расхождении. Описанные ниже single-schema таблицы `core.*` и отдельный Coordinator подлежат замене; документ сохранён как источник текущих контрактов и свидетельств предыдущей реализации, а не как целевая схема. Ранее зафиксированные результаты относятся только к указанным состояниям в [CORE-TEST-COVERAGE.md](../docs/CORE-TEST-COVERAGE.md) и [QA_REPORT.md](../docs/QA_REPORT.md).

## Назначение и границы

Core владеет единой PostgreSQL-схемой `core`: реляционными таблицами файлов, групп, наборов, пользователей, credentials и назначений прав, а также таблицей `core.module_data` с JSONB-данными всех движков. Core обеспечивает физическое хранение и scoped API, но не интерпретирует предметные payloads и не реализует бизнес-правила Website, Content, Forms или Loader. Движки не имеют собственных баз/схем и обращаются к своему namespace только через типизированную capability Core. Core проверяет файловые права и управляет постоянными файловыми байтами в S3. Ролей в новой модели нет.

PostgreSQL-схема `core` — источник истины для Core-модели и всех JSONB-документов движков; S3 хранит байты объектов под внутренними UUID-ключами. Только Core обращается к PostgreSQL и S3 напрямую. Engine получает ограниченный scoped Go API; Presentation не владеет storage и вызывает typed Go contracts. Модули не выполняют SQL и не читают чужие таблицы. Все schema DDL хранится в единственном Core migration set Atlas; production Go запускает закреплённый Atlas CLI `v1.3.0`, но не содержит SQL-команд создания/изменения схемы. Core bootstrap создаёт схему `core` с журналом в `public.atlas_schema_revisions`; таблицы и дальнейшая migration history ведутся в `core.atlas_schema_revisions`. Runtime PostgreSQL login отделён от мигратора, является прямым членом только `NOLOGIN` роли `zubrium_core_runtime` и получает только DML-права на Core tables, включая `module_data`; у login и grant-role нет других членств или повышенных атрибутов. Runtime membership не позволяет переключиться на мигратора или другую роль. Runtime и migration URLs обязаны указывать на одинаковые PostgreSQL host, port и database; приложение отклоняет расхождение адресов. Миграционные credentials не используются для запросов приложения. Схема Core — чистый начальный baseline; существующие базы и данные нельзя сбрасывать или переносить без отдельного разрешения. Развёртывание описано в [CORE-OPERATIONS.md](../docs/CORE-OPERATIONS.md).

## Файлы и жизненный цикл

Core также предоставляет универсальные отзываемые `sessions`, каждая из которых привязана к конкретному `credential_id`. Это не браузерные сессии: Core проверяет токен, активность credential/principal и сроки хранения, но не работает с cookie, CSRF или HTTP Origin. HTTP Presentation отвечает за cookie-транспорт и браузерную защиту.

- HTTP File API передаёт запросы Loader Engine; он загружает файл возобновляемой сессией: создание резервации, потоковая передача частей, чтение статуса, commit или abort. Инициатор передаёт `Idempotency-Key`, имя, MIME, размер, итоговый SHA-256, атрибуты и одну или несколько целевых групп. Части принимаются отдельными потоковыми запросами с номером и SHA-256; статус позволяет продолжить с недостающими частями после паузы или обрыва соединения. Loader проверяет каждую часть, итоговую сумму, полноту и размер; Core повторно проверяет итоговый SHA-256 непосредственно перед публикацией.
- Сессии, idempotency records, состояния частей и cleanup принадлежат Loader логически и сохраняются как JSON-документы namespace `loader` в `core.module_data`; локальный кеш Loader — производная оптимизация. Core API обеспечивает восстановление после перезапуска и координацию нескольких экземпляров; отдельной Loader схемы и upload-session таблиц нет. Временные байты передаются в S3 только через Core staging API; Core сохраняет staging-объекты отдельно от видимых файлов и не включает их в каталоги до commit.
- Сессия привязана к создавшей её учётной записи. Только она может читать её статус или отменять её; Loader при каждой операции подтверждает identity через Core, а Core заново проверяет активность пользователя и уровень `2` во всех целевых группах на каждой части и commit. Отзыв доступа блокирует продолжение и commit; инициатор может отменить сессию, чтобы освободить ресурсы. Loader ограничивает число, размер и срок жизни частей и инициирует удаление просроченных/отменённых staging-данных через Core.
- Loader Engine автоматически выбирает потоковый или буферизованный режим по конфигурационному порогу и общему лимиту памяти процесса; исчерпание бюджета переводит операцию на поток. Core использует один S3 `PutObject`, поэтому настроенный `max_object_bytes` ограничен лимитом S3 API. Core предоставляет закрытые `PutStagedObject`, `ReadStagedObject` и повторяемую purge-операцию: запись проверяет SHA-256 и уровень `2`, чтение заново проверяет пользователя и текущие назначения. Незавершённые reservations восстанавливает Core, готовые staging-объекты очищает Loader по durable cleanup state. Сроки, recovery и acceptance Loader описаны также в [SPEC-module-data.md](SPEC-module-data.md); итоговая проверка реализации остаётся открытой до обновления QA evidence.
- Успешная загрузка создаёт файл с новым UUID. Байты неизменяемы: изменение содержимого означает создание другого файла с другим UUID. Core не поддерживает версии файла, замену байтов или восстановление версии.
- Имя, допустимые метаданные и принадлежность к группам доступа и наборам можно менять при наличии соответствующих полномочий. Служебная ревизия метаданных для проверки конкурентных изменений и кеша допустима; это не версия содержимого и не создаёт историю файлов.
- Каждый файл принадлежит как минимум одной группе доступа. Нельзя удалить его последнюю принадлежность. Группа может быть временно отсутствующей в текущей конфигурации: принадлежность сохраняется, но не предоставляет доступ. Это состояние не является основанием удалить файл.
- Core удаляет файл окончательно, включая байты в S3; корзины и пользовательского восстановления нет. Файл, находящийся в нескольких группах, можно удалить при уровне `2` хотя бы в одной из них. Core не проверяет ссылки сайтов, форм или контента и не предупреждает об их последствиях.
- Новые идентификаторы генерирует система; пользователь не вводит UUID вручную. Переданные байты, размер и тип содержимого проверяются в установленных ограничениях; произвольное имя файла не используется как путь в S3.

### HTTP File API

`presentation/fileapi` — внешний HTTP-адаптер к Go-контракту Loader Engine. Он передаёт bearer credential в Loader и не принимает пользовательский `principal_id` или `module_id`. File API не вызывает Core напрямую, не обращается к БД/S3 и не реализует протокол загрузки. Loader подтверждает identity через Core и вызывает типизированные операции Core для авторизации, файлов, наборов и staging. Loader владеет сессией, частями, контрольными суммами, idempotency и режимом передачи; Core повторно проверяет актуальные полномочия при каждой файловой операции.

| HTTP операция | Маршрут | Контракт |
| --- | --- | --- |
| Начать загрузку | `POST /api/v2/files/uploads` | JSON с `name`, `contentType`, `size`, `sha256`, `groups[]`, `attributes`; обязательный `Idempotency-Key` |
| Статус загрузки | `GET /api/v2/files/uploads/{id}` | Только инициатор; возвращает полученные части и expiry, чтобы продолжить загрузку |
| Отправить часть | `PUT /api/v2/files/uploads/{id}/parts/{number}` | Поток `application/octet-stream`, обязательные Content-Length и `X-Content-SHA256`; часть можно повторить идемпотентно |
| Завершить загрузку | `POST /api/v2/files/uploads/{id}/commit` | Loader проверяет сессию, части и checksum; Core повторно проверяет текущие уровни групп и создаёт файл идемпотентно |
| Отменить загрузку | `DELETE /api/v2/files/uploads/{id}` | Только инициатор; Loader завершает сессию и запрашивает очистку staging через Core |
| Список файлов | `GET /api/v2/files?group=&q=&cursor=&limit=` | Core возвращает только доступные файлы, без total count и утечки через cursor |
| Метаданные | `GET/PATCH/DELETE /api/v2/files/objects/{id}` | Изменяющие методы требуют `If-Match: "{id}-r{revision}"`; байты неизменны |
| Содержимое | `GET/HEAD /api/v2/files/objects/{id}/content` | Авторизованная потоковая выдача; GET поддерживает одиночный HTTP Range; ответ закрыт от shared cache |
| Членство в группе | `PUT/DELETE /api/v2/files/objects/{id}/groups/{group}` | Обязательный `If-Match`; Core проверяет запись и запрет удаления последней группы |
| Наборы файлов | `GET/POST /api/v2/files/sets`, `GET/PATCH/DELETE /api/v2/files/sets/{id}`, `GET /api/v2/files/sets/{id}/files`, `PUT/DELETE /api/v2/files/sets/{id}/files/{fileId}` | Loader делегирует операции Core; каждому набору назначается статичная управляющая группа: уровень `1` читает, `2` меняет имя и состав |

Тело загрузки разбивается клиентом на отдельные потоковые части; это не один multipart/form-data запрос, который нельзя возобновить после потери соединения. Streaming/buffered выбирает Loader по конфигурации и доступному memory budget; выбранный режим сохраняется в сессии и не может быть принудительно изменён HTTP-запросом. `Idempotency-Key` повторно использует только ту же резервацию с теми же метаданными; другой запрос с этим ключом завершается конфликтом. Для файла, сессии или набора с отсутствующим либо закрытым доступом HTTP-ответ не раскрывает существование ресурса. `namespace` набора — метка организации, не `module_id` и не capability; Core разрешает операцию только после проверки его статичной управляющей группы. `namespace` и управляющая группа неизменяемы после создания; PATCH меняет только имя. Уровень `1` в управляющей группе читает набор и его доступные файлы; уровень `2` меняет имя и состав. Добавление файла требует уровня `2` в управляющей группе набора и уровня `2` хотя бы в одной активной группе файла. Удаление membership требует уровень `2` в управляющей группе и не удаляет файл. Membership в наборе никогда не предоставляет право чтения файла.

### Сбой и конкурентность PostgreSQL/S3

Состояние загрузки, idempotency records, части и задания очистки принадлежат Loader логически и сохраняются JSON-документами Loader в `core.module_data`; файловые метаданные и группы принадлежат Core. Межсхемной или отдельной Loader DB нет. Loader использует scoped store Core, CAS и идемпотентные Core staging/finalize вызовы. Временные байты хранятся как непрозрачные staging-объекты, которыми управляет Core API; видимый файл появляется только после проверки и финального Core commit. Восстановление сверяет JSON-состояние Loader с Core по idempotency key и не читает Core tables напрямую. Запись S3 и транзакция Core DB не атомарны. До завершения загрузки файл не выдаётся. Уникальные staging keys и синхронизация загрузки с очисткой исключают удаление байтов активной или другой операции. Повтор после неопределённого ответа не создаёт дубликатов; повторное использование idempotency key для другого запроса отклоняется.

Удаление сначала делает файл недоступным через Core; затем S3 и метаданные очищаются с безопасным повтором после сбоя. Это техническое состояние операции, не корзина: восстановление пользователем не предоставляется. Конкурирующие выдача, загрузка, удаление, изменение групп и прав не должны раскрывать закрытые данные, повторно публиковать удалённый объект или оставлять доступ к частичной записи. Для управления метаданными и принадлежностью использовать проверку конкурентных изменений, чтобы потерянный ответ или устаревшая запись не затирали чужое изменение.

## Статичные группы доступа

Список групп задаётся YAML-конфигурацией при запуске. Уровни назначаются напрямую каждой учётной записи администратора или сервиса, без ролей и наследования через роли. Через административный интерфейс назначениями управляет администратор, у которого есть отдельное право управления администраторами и уровень `2` в соответствующей группе. Создание новой фичи, модели или записи не создаёт новую группу доступа и не требует перезапуска.

| Уровень | Право в группе |
| --- | --- |
| `0` | Нет доступа через эту группу |
| `1` | Чтение файлов группы и разрешённых метаданных |
| `2` | Чтение и запись: загрузка, изменение метаданных и принадлежности, удаление |

Для файла достаточно прямого назначения уровня хотя бы в одной действующей группе; `0` означает отсутствие разрешения, а не явный запрет. Индивидуальных разрешений на файл, ролей и явных запретов нет. Уровень `1` разрешает только чтение; добавление фичи или загрузка её файлов требуют уровня `2` в соответствующей группе. Уровень `2` сам по себе не даёт право управлять учётными записями и назначениями: для этого дополнительно требуется право управления администраторами.

Чтобы добавить существующий файл в другую группу доступа, субъект должен иметь уровень `2` на файл через одну из его текущих действующих групп и уровень `2` на целевую группу. Дополнительного права расширять доступ нет. Добавление может открыть файл всем субъектам, у которых есть чтение целевой группы; это следствие операции. Удаление принадлежности также требует прав записи и не должно оставлять файл без единой сохранённой группы.

Если группа убрана из YAML, Core запускается: её сохранённая принадлежность и назначения не предоставляют доступа, пока группа не возвращена в конфигурацию. Файлы и другие группы не удаляются. Если отсутствуют все группы файла, файл недоступен; возвращение хотя бы одной прежней группы восстанавливает действие её сохранённых назначений. Право управления администраторами не обходит этот запрет. Изменения конфигурации и назначений должны учитываться всеми экземплярами без выдачи устаревших прав.

## Динамические наборы

Набор — динамическая сущность для поиска и организации файлов, отдельная от статичной группы доступа; данные наборов принадлежат реляционной Core-модели. Наборы создаются, читаются, изменяются и удаляются через File API → Loader → Core. При создании обязательно задаются namespace, имя и одна статичная управляющая группа. Создание требует уровня `2` в этой группе; чтение — уровня `1` или `2`; изменение имени, состава и удаление — уровня `2`. `created_by` может храниться как audit-атрибут, но не является владельцем и не предоставляет полномочий. Namespace и управляющая группа после создания неизменяемы, чтобы не менять границу доступа неявным PATCH; для новой границы создаётся новый набор. При добавлении Core требует активную учётную запись, уровень `2` в управляющей группе набора и уровень `2` хотя бы в одной текущей активной группе файла. При чтении набора Core дополнительно фильтрует каждый файл по его собственным группам. Один файл может находиться в нескольких наборах и группах доступа. Набор не выдаёт прав на файлы и не меняет их группы доступа. Удаление набора или исключение файла из набора не удаляет файл.

При получении набора и поиске Core возвращает только файлы, доступные вызывающему субъекту. Имена, идентификаторы, счётчики, курсоры и прочие метаданные ответа не должны раскрывать существование закрытых файлов или недоступных наборов. Поле `File.Groups` содержит только группы файла, для которых у вызывающего сейчас есть уровень чтения; наличие других групп не раскрывается. На каждую операцию над набором уровень проверяется по текущим DB назначениям; потеря группы в YAML закрывает операции до её возврата. Полномочия сервисных учётных записей ограничиваются назначенными группами и задачами.

Действие человека через админку не получает полномочия сервисного ключа движка автоматически: presentation/engine проверяет прямой уровень администратора для соответствующей операции и группы, а обращение engine к Core проходит также под собственным сервисным ключом с необходимым уровнем. Например, просмотр набора фич требует `1`, импорт новой фичи — `2` у администратора; сервису Website тоже нужен соответствующий доступ для чтения и записи файлов. Прямые сервисные операции без пользователя ограничиваются назначениями самого сервиса. Анонимный публичный маршрут Router остаётся отдельным явно настроенным сценарием.

Пример: Website Engine распаковывает ZIP и создаёт набор сборки фичи из manifest, HTML, JS и assets, сохраняя файлы в заранее настроенной группе доступа. Content Engine помещает контентные файлы в нужную группу доступа и добавляет их в наборы фич, моделей или записей. Одна модель или файл могут использоваться несколькими фичами: наборы могут пересекаться; Core не вводит отношения между моделями или записями.

## Идентичность и публичная выдача

В Core существует одна сущность пользователя: поле типа `kind`, категории пользователей и роли отсутствуют. Термины «администратор» и «сервисная учётная запись» описывают применение одной и той же сущности, а не разные типы или неявные привилегии. Движки, Router и другие сервисы используют обычных пользователей с отдельными ключами и собственными прямыми назначениями групп. Право управления пользователями назначается отдельно и само по себе не даёт группового доступа. Все операции Core требуют проверенной идентичности. У файла и группы нет понятия владельца.

Первоначальный администратор создаётся при первом запуске с отдельным правом управлять администраторами. По умолчанию ему назначается уровень `2` во всех группах, если конфигурация при создании не задаёт для группы другой уровень. Конфигурация инициализирует назначения только при создании: последующие изменения через админку сохраняются после перезапуска и не перезаписываются YAML. Если позднее в YAML впервые добавлена группа, первоначальному администратору для неё назначается `2` по умолчанию или явно указанный для этой новой группы уровень. Возврат уже известной ранее группы не считается первым добавлением и восстанавливает её сохранённые назначения, не перезаписывая их. Первоначальный администратор не имеет неявного обхода групповых проверок: его фактические назначения могут быть ограничены конфигурацией или последующими разрешёнными действиями.

Администратор с правом управления администраторами может создавать других администраторов и сервисные учётные записи, выдавать и отзывать это право другим администраторам и управлять ключами. Новый администратор, созданный через админку, имеет уровень `0` во всех группах, пока создающий явно не назначит права. Назначать или изменять уровень другого администратора либо сервиса в конкретной группе может только администратор с правом управления администраторами и собственным уровнем `2` в этой группе. Он не может таким способом выдать доступ к группе, где у него нет `2`. Это же право управления требуется для создания сервисных учётных записей; их групповые уровни подчиняются тому же правилу делегирования.

Перечень активных групп и прямых уровней доступен только субъекту с правом управления администраторами: названия групп раскрывают внутреннюю структуру системы. Само это право позволяет увидеть список, но назначить уровень в группе по-прежнему можно только при собственном уровне `2` в ней.

Нельзя отключить или удалить последнего действующего администратора с правом управления администраторами или отозвать у него последнее такое право. При проверке действующий управляющий администратор должен быть активен и иметь действительный ключ. Защита работает при конкурентных операциях и не оставляет частичных изменений; предусмотрена защищённая операторская процедура восстановления при потере ключей или доступа к группам. Если секрет первого администратора не задан, он генерируется случайно и выводится один раз; хранится только проверочный хеш. Bootstrap сериализуется между экземплярами и не пересоздаёт существующий ключ.

Core не знает анонимной выдачи и не хранит флаг публичности файла. Router определяет публичный маршрут в своей конфигурации, обращается к Core под собственной сервисной учётной записью и может получить только файлы, разрешённые этой записи. Администратор настраивает назначения для Router. Публичный маршрут не превращает всю группу Router в автоматически опубликованный каталог; публикуются только явно назначенные маршруты или обработчики.

Запреты операций над медиа, заявками, контентом и иными продуктами принадлежат соответствующим engines/presentation, а не файловой модели Core. По прямому решению пользователя поле `role` и старая матрица `admin`, `moderator`, `staff`, `user` удаляются из нового API и админки. Это явно согласованное исключение из прежнего требования сохранить все внешние контракты; остальные контракты по-прежнему требуют переноса и проверки. Адаптер не должен незаметно вводить роли заново.

## Зафиксированный Go-контракт Core

Публичный контракт реализации зафиксирован в test-local интерфейсе [`coreV2RuntimeContract`](../tests/go/core/presentation/core_v2_contract_test.go). Production `Runtime` должен реализовать эти сигнатуры до приёмки. Изменение сигнатуры сначала отражается в этой спецификации, затем в интерфейсном тесте; реализация не должна заставлять переписывать приёмочные сценарии по ходу работы.

- `Principal` представляет единственный тип учётной записи и сообщает `ID`, `Name`, `Active`, `CanManageAdministrators`. Дополнительного `kind`, `role` или матрицы ролей нет. Создание учётной записи возвращает её ID и секрет нового ключа один раз; назначения групп по умолчанию равны `0`. Управление ключами, блокировкой и отдельным правом управления администраторами выполняется операциями контракта.
- `ListAccessGroups` возвращает активные сконфигурированные группы с прямым уровнем вызывающего, но только после проверки отдельного права управления администраторами.
- `File` содержит системный `ID`, доступные вызывающему `Groups []string`, непрозрачные `Metadata map[string]string`, `ContentType`, размер, verified SHA-256 и служебную ревизию метаданных. Значение `Metadata["name"]` — имя файла. Пути, владельцы, visibility и типы продуктовых сущностей не входят в контракт Core. Байты неизменяемы; новый набор байтов создаёт новый UUID.
- `CreateFile(ctx, session, requestKey, groups, metadata, contentType, size, expectedSHA256, body)` требует уникальный сгенерированный UUID ключ запроса, хотя бы одну активную группу, уровень `2` во всех исходных группах и валидный ожидаемый SHA-256. Core проверяет размер и хеш потока до публикации строки `ready`, записывает verified hash в нормализованную файловую строку и повторно проверяет текущие права перед commit. Повтор идентичного запроса с тем же ключом возвращает прежний ID; конфликт метаданных или body с тем же ключом завершается `ErrRequestConflict`. Неверный размер, хеш или метаданные не создают доступный файл.
- `UpdateFile` принимает ожидаемую ревизию и новую map-метадату. Она не меняет байты, а устаревшая ревизия завершается `ErrRevisionConflict`. Изменение состава групп — отдельные `AddFileToGroup` и `RemoveFileFromGroup`, также с ревизией. Последняя группа не удаляется. Любой субъект с `2` хотя бы через одну группу файла может удалить весь файл.
- `ListFiles` фильтрует по одной статичной группе, `ListFileSet` по набору, `SearchFiles` применяет поиск и необязательные группу/набор. Сигнатуры и порядок аргументов заданы тестовым интерфейсом. Сначала проверяется уровень `1` в управляющей группе набора (если указан набор), затем права на каждый файл до пагинации: возвращаются только доступные записи, cursor не раскрывает количество скрытых строк.
- Диапазоны `ReadFileRange` включают обе границы: `start=1,end=2` для `one` выдаёт `ne`. Метаданные и права проверяются при каждом чтении, даже если байты были в локальном кеше.
- `FileSet` содержит ID, namespace, name, immutable management group, revision и timestamps. `(namespace, name)` уникален: повторное создание или переименование в занятое имя возвращает конфликт. `CreateFileSet` требует уровень `2` в выбранной активной группе; `ListFileSets` и `GetFileSet` возвращают только наборы с уровнем `1/2`; `UpdateFileSetName`, membership changes и delete используют exact expected revision и уровень `2`. Membership mutation увеличивает set revision. Namespace и management group нельзя менять через PATCH. Все denied/missing set responses через File API скрывают наличие закрытой группы.
- Свежая схема хранит набор в `core_file_sets` с `id`, audit-only `created_by`, `namespace`, `name`, `management_group`, `revision`, `created_at` и `updated_at`; связь набора с файлом хранится отдельно в `core_file_set_members(file_set_id, object_id)`. Namespace — метка workflow, не `module_id` и не граница module-data capability. В `core_objects` хранится verified SHA-256 байтов вместе с UUID-ключом S3, размером, content type и служебной ревизией. Прямые назначения и сохранённые принадлежности используют ключ конфигурационной группы, поэтому её выключение не удаляет данные.
- `RuntimeConfig` явно задаёт `AccessGroups map[string]access.Level`, module-data byte/count/page/batch limits, лимит байтов файла и метаданных, `CacheMaxBytes`, `CacheTTL`, `MaxCachedObjectBytes` и параметры фонового обслуживания. В YAML для каждой группы уровень bootstrap-администратора опционален: отсутствующее или `null` значение означает согласованный уровень `2`; явное `0`, `1` или `2` сохраняется. Runtime pool содержит не менее трёх PostgreSQL connections: одно для долговременного `LISTEN`, ещё два для одного потокового commit Loader. `loader.max_concurrent_commits` явно ограничивает параллельные commit и требует `core.max_connections >= 1 + 2 * max_concurrent_commits`; это резервирует отдельную пару для каждого nested stream и исключает deadlock при пуле, занятом параллельными commit. Максимальный размер одного объекта, который Core может целиком прочитать для кеширования, не превышает общий лимит кеша; ошибочная или неполная operational config отклоняется до запуска. Удалённые без восстановления файлы не имеют `DeletedRetention`. Конфигурация групп назначает уровни первоначальному пользователю только при создании или первом добавлении группы; повторный запуск не затирает административные изменения.
- Ошибки авторизации возвращаются как `ErrUnauthorized` для отсутствующей/отозванной идентичности и `ErrForbidden` для действующего пользователя без достаточного уровня. Не найденный файл возвращает `ErrFileNotFound`. Отказ проверки БД не превращается в разрешение из кеша.

## Кеш и несколько экземпляров

Каждый экземпляр Core имеет локальный ограниченный кеш метаданных и байтов часто запрашиваемых файлов. Общий лимит, TTL и максимальный размер отдельного кешируемого файла настраиваются явно. Большие файлы возвращаются потоком из S3 и не загружаются целиком в память. Кеш не хранит решение об авторизации как основание для последующей выдачи.

PostgreSQL — общая инфраструктура оповещения об изменениях файлов, принадлежности к группам, состава конфигурации и назначений прав. Перед каждой выдачей, в том числе из кеша, Core проверяет актуальные права субъекта и состояние/ревизию файла в БД. Потерянные или задержанные уведомления не позволяют выдать устаревшие данные или сохранить отозванный доступ. Если актуальность или права нельзя проверить из-за недоступности БД, доступ закрывается. После восстановления соединения кеш и подписка должны быть приведены в согласованное состояние.

## Границы движков и удаления

Движок сам отвечает за смысл своих файлов и собственные ссылки. Его данные и ссылки хранятся JSON-документами в namespace движка таблицы `core.module_data`; смена ссылок выполняется атомарным batch CAS через typed Core API и не требует прямого SQL. При изменении контента или конфигурации движок загружает новый файл, переключает свою ссылку, проверяет использование старого файла по собственным документам и затем вызывает Core для удаления старого. Core не предоставляет произвольный SQL или глобальный реестр продуктовых ссылок. Если batch переключения завершился ошибкой, действующая ссылка сохраняется; новый файл подлежит последующей очистке. Сбой между обновлением ссылки, вызовом Core и записью в S3 обрабатывается повторяемой операцией очистки, а не общей транзакцией PostgreSQL и S3.

Каждый движок проверяет только собственные ссылки. Общий ответственный процесс может удалить общий файл без опроса остальных движков; в этом случае ссылки других движков могут перестать работать. Core не хранит глобальный реестр ссылок и не блокирует удаление по продуктовым зависимостям. UI и движки отвечают за применимые предупреждения и подтверждения. Снапшоты и импорт/экспорт Sitepack остаются задачами движков: они должны сохранять необходимые файлы и внешние контракты без введения версий файла в Core.

## Приёмка

До отметки о выполнении проверить на изолированных ресурсах:

1. Создание, чтение, потоковую загрузку и выдачу, метаданные, несколько групп и наборов, поиск и фильтрацию закрытых файлов; повторную загрузку и отказ без частичных видимых изменений.
2. Все комбинации прямых уровней `0/1/2` для администраторов, сервисов и нескольких групп; создание с `0`, выдачу уровней только управляющим администратором с `2` в нужной группе, делегирование и отзыв права управления, защиту последнего управляющего администратора. Проверить сохранение изменённых назначений после перезапуска, первое добавление и возвращение YAML-группы, отсутствие последней принадлежности и отказ при недостаточном уровне без частичных изменений.
3. Сервисный ключ Router, публичный явно назначенный маршрут и отказ анонимного прямого Core-запроса; отсутствие утечки через метаданные набора и кеш.
4. Несколько экземпляров, изменение и отзыв прав, потерю уведомлений, разрыв/возврат соединения с PostgreSQL и недоступность S3; при невозможности проверки прав выдача закрыта.
5. Сбои между БД и S3, повторную очистку, конфликт параллельных операций, окончательное удаление и отсутствие восстановления; отсутствие Core-версий, владельцев, индивидуальных файловых грантов, корзины и продуктовых правил.
6. Удаление `role` и старой матрицы из нового API и админки, перенос остальных legacy-контрактов и Sitepack на границах engines/presentation, а также изолированные unit, интеграционные и браузерные сценарии. Покрытие нового Core и каркаса — не менее 70% исполняемых строк; одно число не доказывает безопасность и совместимость.

Потоковая S3-загрузка текущего каркаса применяет SigV4 `UNSIGNED-PAYLOAD`; при дальнейшей реализации обеспечить защиту содержимого при передаче через TLS. HTTP допустим только по явно включённой настройке доверенной локальной среды; это не обеспечивает целостность по недоверенной сети. Реальное поведение и доступность конфигурации подтверждаются проверками, а не этой спецификацией.
