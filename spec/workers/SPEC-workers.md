# Worker контракты и безопасность исполнения

Статус: контракты и частичные handlers реализованы, но Archive/Media/Prerender не подключены к production composition и не прошли приёмку. Website API для import/build/media остаётся fail-closed. Coordinator и общие гарантии определены в [SPEC-coordinator-platform.md](../architecture/SPEC-coordinator-platform.md).

## Worker и Core

Worker — статически включённый обработчик зарегистрированной component operation/version. Он не является engine и не обращается к PostgreSQL, S3 или cache напрямую. Вход и результат — ограниченные нейтральные DTO; file IDs, engine record IDs и иные ссылки остаются непрозрачными для Coordinator.

Target operation identities неизменны: компонент `worker.archive` предоставляет `feature-import` версии `1`, `worker.media` — `derivative` версии `1`, `worker.prerender` — `render-page` версии `1`. Owner и handler задаются только статической composition; они не входят в пользовательский request payload. Domain API принимает типизированный сценарий и передаёт его в engine-owned workflow; engine создаёт durable workflow через scoped Core `WorkflowClient`, а workflow атомарно порождает worker tasks через зарегистрированные generic operation/version contracts. Core сохраняет и диспетчеризует непрозрачные workflow/tasks и не импортирует worker-пакеты, их DTO или бизнес-правила. Admin инициирует тот же доменный workflow через API владельца, не создавая worker task напрямую и не передавая произвольные operation IDs или payload. Изменение DTO несовместимым образом требует новой `ContractVersion`, а не неявного переиспользования версии `1`.

Handler получает context с отменой, deadline и данные одной Worker-task. Он возвращает ограниченный JSON result, безопасный machine error code или список дочерних Tasks. Child может быть `worker` с WorkerRef либо `join`-barrier без handler. Регистрация Worker передаётся из статической composition root; профиль не может указать произвольный импорт, команду или executable.

Внешние эффекты могут выполняться более одного раза: гарантия Coordinator — at-least-once. Каждый handler обязан использовать стабильный idempotency key либо reconciliation до повторного внешнего действия. Секреты передаются через Core capability/secret provider или opaque references; они не помещаются в task payload, result, logs или error code.

## Retry, timeout и граница процесса

`TaskExecutor` ограничивает concurrency, task timeout, attempt count Worker-task, lease, polling, exponential backoff, payload/result размер и число динамических дочерних Tasks. Join-task не claims: Core завершает его после успеха всех dependencies. Ошибка хранения, отказ renewal или потеря instance lease делает Core unhealthy и останавливает claims. Потеря lease отдельной Worker-task ожидаема: устаревший handler не может обновить задачу или породить детей после смены fencing token.

Отмена context — кооперативная. Go не может безопасно завершить зависшую goroutine. CPU/memory-heavy, network-facing или недоверенная обработка (в том числе Chromium и декодеры медиа) должна исполняться в отдельно supervised процессе/контейнере с явными CPU, memory, filesystem, network и wall-clock ограничениями. In-process timeout не является sandbox.

Ошибки handler нормализуются к bounded machine code. Диагностический текст, stack trace, payload и результат не возвращаются в административную сводку. Повтор разрешается отдельной авторизованной операцией; уже совершённый внешний side effect не отменяется Core.

## Постановка worker-задач

Ручной запуск создаёт durable workflow, а не отдельный процесс и не повторяет старую задачу. Admin domain action и engine-generated workflow используют один контракт: Presentation валидирует публичный запрос и полномочия, engine владеет семантикой запроса/его payload и через scoped Core capability сохраняет workflow в PostgreSQL. Root task всегда ссылается на зарегистрированный Worker. Child может быть Worker-task или join-task; join-task содержит только зависимости и автоматически завершается Core после успеха всех предшественников. Worker остаётся статическим обработчиком generic task, а не отдельной пользовательской сущностью или вторым queue backend. Core знает только component/operation ID, version, generic payload/result, leases и transitions; конкретные worker-типы не добавляются в Core.

Пользователь не выбирает component ID, operation ID, contract version, owner, task handler, payload JSON, executable или команду. Каждое действие запускается из доменного API/экрана и принимает только типизированные поля владельца операции (например source file ID + ожидаемый digest; snapshot ID + locale + pinned build inputs; snapshot ID + placement ID + field path + source file ID). Worker получает идентификатор выполнения из `Task.ID`; поле `job_id` в существующих Worker v1 JSON-контрактах остаётся только для совместимости сериализованного формата, при наличии должно совпадать с `Task.ID`, а при отсутствии адаптер Worker заполняет его из конверта Task. Media profile разрешается сервером из `x-media` точного manifest version, закреплённого snapshot; клиент не передаёт preset ID или произвольные параметры обработки. Запуск защищён direct group level `2` в настроенной Coordinator-группе и доменной авторизацией на входы; просмотр сводки остаётся level `1`. Текущий group key `coordinator_jobs` сохраняется, чтобы не терять существующие grants. HTTP adapter обязан проверять group access на каждом запросе; UI checks не заменяют серверную авторизацию. Idempotency key и нормализованный input входят в hash workflow; повтор ключа с тем же input возвращает существующий workflow, иной input даёт conflict. Admin показывает список workflows и их task graphs; payload, result и diagnostics остаются скрытыми.

Worker registration остаётся статической и fail-closed. Выбранный profile без любого handler/factory/supervisor, необходимого объявленной операции, не объявляет её доступной и не принимает запуск. Добавление нового worker требует отдельного worker-owned contract/handler и static composition registration; Core schemas/application vocabulary не меняются.

### Prerender activation

Prerender строит для конкретной page identity и locale immutable `static-page-artifact/v1`, проверяет digest и все файлы, затем durable publication workflow находит зарегистрированные Router targets для этой page identity и активирует каждый `(route, locale)` независимым Router CAS. Создание/удаление route, URL/path, Router startup branch и Website snapshot-to-branch assignment в worker workflow не входят. Отсутствующий или неоднозначный target и CAS conflict завершают соответствующую активацию контролируемой ошибкой, но не удаляют готовый artifact и не меняют предыдущую выдачу этого target; остальные targets продолжают обрабатываться. Workflow сохраняет результат по каждому target и допускает безопасный повтор. Target изменяется только после состояния `ready`; stale inputs отклоняются.


## Специфичные worker сценарии

### Archive

Archive импортирует ZIP как обычный Core file reference, валидирует central directory, manifest и каждый entry до записи результата. Запрещены absolute/traversal/ambiguous paths, symlinks, дубликаты, чрезмерные размеры, число записей и compression ratio. Для распаковки проверяются хэши нераспакованных bytes; вывод создаётся как immutable Core files в наборе, созданном Website по configuration. Частичный output не помечается готовым. Повторяемые шаги используют стабильные keys; исходный ZIP удаляется только после durable фиксации и проверки результата.

`workers/archive/handler.go` реализует ограниченный Core-backed импорт: source spooling, ZIP/manifest validation до output writes, scoped CAS progress, idempotent immutable file creation и FileSet membership reconciliation. `Handler.WorkerHandler` и descriptors адаптируют его к generic Coordinator identity, но handler не зарегистрирован в production composition; source cleanup и сквозная приёмка отсутствуют.

### Media

Media Worker-task получает immutable source file ID, snapshot ID, placement ID и declarative field path. Website resolves and pins the canonical profile from `x-media` in the exact feature manifest version bound to the snapshot; the client cannot choose a profile, version, preset, or FFmpeg argument. Существующий versioned Media run record сохраняет serialized key `job_id`, связанный с Core `Task.ID`, вместе с source identity/checksum, canonical profile digest, processor version и idempotency key; это историческое поле данных не является идентификатором определения Worker. Identical fingerprints reuse the same run/result; a changed profile digest, processor version or source checksum starts a distinct run.

Media Worker-task разрешается из manifest-bound profile, pinned snapshot и field identity. Он валидирует входные stream types и фактические output MIME/container, применяет явные CPU/memory/time/input/output/frame/stream/concurrency limits; processor version задаётся статической конфигурацией. Для каждого объявленного output создаётся новый immutable Core file с checksum, content type и размером; он наследует группы источника и добавляется в тот же FileSet. Оригинал сохраняется. Media operation возвращает успех только после готовности и проверки всех outputs; Website лишь тогда фиксирует новые derivative IDs в поле. Частичный результат не становится доступным как готовый набор; failure/cancel очищает принадлежащие этому run временные данные и не меняет старое значение поля или предыдущие outputs.

`workers/media/handler.go` содержит versioned Worker handler, durable module-owned run state, legacy preset fingerprint (manifest-based profile resolution is not implemented), Core-backed immutable derivative и source-group propagation. Существующие JSON payload version и ключи записи сохраняются. `workers/media/ffmpeg.go` ограничивает staged bytes, protocol arguments, временной каталог и wall-clock, но явно не является OS sandbox; `NewHandler` отклоняет такой runner, пока composition не предоставит внешний supervisor. Перенос FileSet memberships также пока недоступен через текущую Core file capability. Production factory, supervisor и сквозная приёмка отсутствуют.

### Prerender

Prerender получает версионированный render plan (`render-plan/v1`) как ограниченный JSON payload, подготовленный Website/внешней composition. Plan включает digest всех входов, точные snapshot/build revisions, маршруты/placements, публичную content projection и references на feature assets; он не содержит credentials, secrets, S3 paths, пользовательские executable paths или произвольные команды. Coordinator хранит plan как opaque payload; Core не парсит его. Worker не вызывает Website, Content или Router API и не получает их storage access.

Для исполнения worker запускает Chromium в отдельно supervised процессе/контейнере с явными CPU, memory, filesystem, process и wall-clock limits. Сеть отключена по умолчанию; включить можно только явно описанный безопасный allowlist публичных GET/HEAD endpoints, с блокировкой loopback, private, link-local и metadata адресов на каждом redirect/DNS resolution. Worker исполняет `static-lifecycle` согласно [SPEC-feature-runtime.md](../engines/website/features/SPEC-feature-runtime.md), ждёт завершения ограниченных render/readiness стадий и записывает HTML/assets только через ограниченную Core file capability. Input digest включает snapshot, locale catalog revision, locale, locale-specific publication revision и page selections; output содержит проверяемый artifact manifest file ID и этот digest. Результат становится `ready` только после проверки всех файлов и ссылок. Ошибка, cancellation, timeout или несовпадение digest не заменяет предыдущий активный artifact. Независимая активация зарегистрированных `(route, locale)` targets выполняется durable publication workflow через Router CAS; каждый target сохраняет собственный результат и может быть повторён отдельно.

`workers/prerender/contract.go` и `validation.go` задают/проверяют ограниченный envelope и artifact result metadata; `FailClosedWorker` прекращает обработку с `ErrRenderUnavailable` и не создаёт output. Payload остаётся семантически opaque; typed Website/page/runtime projection, Chromium renderer, OS supervisor, Core persistence и production factory отсутствуют. Owner-scoped чтение результата дочерней task остаётся закрытым: `WorkflowClient.Get` возвращает workflow result root task, а `WorkflowControl` скрывает task results. Website не может безопасно получить artifact IDs дочернего worker через существующие capabilities и поэтому остаётся fail-closed до отдельного согласования этого API.

## Приёмочные сценарии

Каждый отдельный набор входных данных считается отдельным сценарием согласно [ACCEPTANCE-MATRIX.md](../../tests/ACCEPTANCE-MATRIX.md). Для WorkerCatalog и TaskExecutor нужны реальные проверки: дубликатная регистрация, неверная версия, payload/result bounds, cancellation, timeout, panic, store failures, sibling cancellation, retry/backoff, delayed Worker-tasks, join barrier, emission-key dependencies, циклы, atomic child creation, concurrent claim, lease takeover, stale fencing и shutdown.

Для Archive нужны реальные повреждённые ZIP, path traversal (включая Windows drive paths), symlink, duplicate entries, max-size/count/ratio и digest сценарии; затем — end-to-end сохранение в disposable Core/S3. Для Media — source/profile fingerprint и idempotency, exact `x-media` manifest/profile and processor version, отказ произвольным клиентским preset/FFmpeg parameters, несколько renditions с полной готовностью до фиксации поля, сохранение прежнего значения при отказе, наследование групп и того же FileSet, оригинал без изменений, quota/timeout/cancel/restart/retry, output checksum/MIME/size и Core authorization/revocation. Для Prerender — plan version/digest/input mismatch, locale-bound inputs, валидный HTML/assets, readiness и runtime errors, network denial/allowlist redirect/DNS, process limits, cancellation/timeout/restart, безопасное отсутствие частичного output, прежний artifact и независимые Router CAS/частичные результаты для каждого `(route, locale)`. Unit проверки с fake полезны, но не заменяют disposable PostgreSQL/S3 и OS-enforced process isolation.
