# Core: слои, данные и автоматизация

Статус: целевой контракт, прямое расположение DDD-слоёв и Core/Coordinator базовые контракты реализованы и прошли отложенные Go/Atlas проверки. Общий функциональный порог по acceptance input sets всех продуктовых модулей остаётся отдельной открытой задачей; данный документ сам по себе его не подтверждает. Evidence: [QA_REPORT.md](../docs/QA_REPORT.md) и [ACCEPTANCE-MATRIX.md](../tests/ACCEPTANCE-MATRIX.md).

## Назначение и границы

Core — единственный владелец постоянного состояния продукта и единственная точка доступа к PostgreSQL, S3 и общему файловому cache. Все движки, workers и entrypoints получают ограниченный контракт Core и не получают pool, DSN, SQL-интерфейсы, S3-клиент или прямой доступ к внутреннему cache. Бизнес-правила движков остаются у движков; Core не содержит понятий `snapshot`, `site`, `route`, `content`, `form` или иных предметных моделей конкретного продукта.

Одна PostgreSQL database соответствует одной логической системе. Несколько экземпляров Core работают с этой же системой, координируются через PostgreSQL и используют одну конфигурационную эпоху. Core не поддерживает несколько независимых систем в одной database.

Схема переходит на новый Atlas baseline для пустой database. Старые базы, данные и S3 объекты не сбрасываются, не переносятся и не изменяются. Старый формат не совместим: новый startup должен обнаружить прежнюю схему и отказать без попыток удалить или конвертировать её. Перенос существующих данных, если он понадобится, оформляется отдельной задачей с отдельной процедурой.

## Go-слои

Все слои принадлежат одному Go module `core`; это пакеты с явным направлением зависимостей, а не отдельные Go modules.

```text
presentation ──> application ──> domain
infrastructure ────────────────> domain ports
infrastructure ────────────────> application ports
```

- `domain` содержит модели, ошибки и порты хранения/времени/событий. У моделей допустимы только конструкторы с проверкой и обработкой ошибок; политики доступа, сценарии использования и инфраструктурные проверки находятся в application. Сетевые клиенты, SQL-типы, JSONB-драйверы и зависимости от движков запрещены.
- `application` содержит команды, запросы, политики доступа, валидацию Core-контрактов, сценарии использования и транзакционные границы. Здесь же живёт Coordinator как внутренний сервис Core. Application зависит от доменных контрактов и не импортирует инфраструктурные реализации.
- `infrastructure` содержит реализации портов: PostgreSQL, S3, локальный cache, clock и другие адаптеры. Все SQL и вся работа с PostgreSQL выполняются только здесь. Все DDL и grants принадлежат Atlas migration set; application/runtime выполняет только операции над данными и запускает Atlas CLI по настроенной миграционной идентичности.
- `presentation` предоставляет единый стабильный Core API, типизированные DTO/capabilities, lifecycle и простой composition/DI builder. Он связывает интерфейсы application с infrastructure. Engine получает только выданную ему capability и не может выбрать чужой `engine_id` из пользовательского запроса.

Импорты направлены внутрь: `domain` не импортирует другие слои; `application` импортирует `domain`; `infrastructure` реализует порты и может импортировать `domain`/`application`; внешние модули импортируют только публичный пакет `core/presentation` и нейтральные типы контрактов. Четыре слоя расположены непосредственно в `core/{domain,application,infrastructure,presentation}`; каталогов `internal` внутри Core быть не должно. Core не импортирует пакеты конкретных движков или workers и не публикует capabilities, названные в честь конкретного потребителя. Компоненты, их descriptors и обработчики передаёт внешний composition root; Core работает только с общими типами и непрозрачными payload/result. Между слоями нет циклических импортов. `make lint-core-boundary` разбирает Go imports через AST всех локальных Go-модулей репозитория, включая `legacy`, запрещает Core импортировать или объявлять зависимости на любой другой локальный модуль и ограничивает импорты Core из любого потребителя пакетом `core/presentation`. Target также входит в `make lint` и `make vet`; acceptance-тесты проверяют физическую структуру и тот же контракт.

## Регистрация компонентов и жизненный цикл

Coordinator — часть Core application и не отдельный Go module или самостоятельный владелец БД. Core Coordinator регистрирует и координирует только общие типы компонентов: `engine`, `worker`, `entrypoint` и их операции. Статический composition root импортирует выбранные реализации и передаёт Core descriptors/factories при сборке. Динамическая загрузка Go-кода и произвольные import paths не поддерживаются.

Descriptor компонента содержит только нейтральные данные: стабильный ID, вид компонента, версию контракта, объявленные операции, зависимости и обработчики задач. Core проверяет уникальность ID, зависимости, совместимость контрактов и доступность всех указанных factories до побочных действий. Engine-specific поля не попадают в Core descriptor, кроме непрозрачных входов и результатов зарегистрированной операции.

Запуск выполняется как `validate configuration → construct infrastructure → register components → start components → check readiness → activate Coordinator workers`. Ошибка регистрации, startup или readiness закрывает систему до открытия входящих API. Остановка прекращает новые задания, ограниченно ждёт активные обработчики и закрывает компоненты в обратном порядке зависимостей.

Entrypoint является адаптером внешнего протокола и не получает инфраструктуру. HTTP listener, роутинг, сериализация конкретных API и публичные маршруты принадлежат presentation-модулям. Core выдаёт им только необходимые typed capabilities. Core может регистрировать нейтральные operation/handler contracts, но не знает HTTP paths, route IDs или структуры запроса отдельного движка.

## Долговечные workflow и promises

Workflow — Core-механизм для отложенных межкомпонентных действий. Его идентичность, шаги, зависимости, запланированное время, попытки, lease, fencing token, результаты и ошибки сохраняются в PostgreSQL. В v1 ссылка — пара UUID workflow/task в typed Core contract; отдельный `PromiseRef` или Go `Future` не вводится. Результат читается через Core API после перезапуска и только в scope выданной capability.

Workflow стартует зарегистрированной engine operation с версией контракта, opaque JSON input и idempotency key. Workflow сохраняет `root_task_id` и терминальный `result`; каждый root и дочерний task содержит opaque JSON payload/result. Обработчик может вернуть результат и атомарно запросить дочерние задачи, включая задачи других зарегистрированных компонентов. Coordinator проверяет регистрацию и версии контрактов; движки не импортируют и не вызывают друг друга напрямую.

Правила выполнения:

1. Каждая задача привязана к workflow, зарегистрированному component/operation ID и версии входного контракта. Неизвестные обработчики отклоняются до сохранения workflow.
2. Дочерние задачи и зависимости создаются только при успешной фиксации результата родителя. Фиксация результата, закрытие lease и добавление дочерних задач проходят в одной PostgreSQL-транзакции.
3. Повтор запроса с тем же ключом идемпотентности и тем же fingerprint возвращает прежний workflow. Повтор ключа с другим input даёт conflict.
4. Worker-pool ограничен явными настройками concurrency, timeout, lease, max attempts и retry backoff. Источник времени для lease — PostgreSQL. Просроченный lease можно перехватить; старый fencing token не позволяет записать результат или породить дочерние задачи.
5. Семантика выполнения — at-least-once. Внешние side effects требуют идемпотентности или reconciliation в вызываемом компоненте; Core не обещает ровно один запуск процесса.
6. Ошибка терминальной задачи переводит workflow в failed и не запускает её потомков. Уже исполняемые независимые задачи завершаются или отменяются по workflow policy; их поздние фиксации проверяются по lease/fencing и состоянию workflow.
7. Отмена workflow — явная команда: ожидающие задачи становятся cancelled; активные обработчики получают отменённый context; поздняя фиксация после отмены отвергается. Сторонний side effect, уже совершённый до отмены, компенсирует или согласует владеющий им компонент.
8. Poll/subscribe уведомления являются подсказкой; PostgreSQL остаётся источником истины. Сбой уведомлений не меняет статусы, зависимости и право читать результат.
9. Размер input/result, общее число задач workflow, число дочерних задач на один шаг и срок хранения результатов задаются явно в operational config. Секреты, большие бинарные данные и файлы в JSON input/result запрещены; передаются opaque Core file references.

Для первой версии граф строится динамически по мере выполнения обработчиков; условная логика остаётся внутри зарегистрированной operation, а её результатом служит ограниченный набор дочерних задач. Произвольный пользовательский DSL, циклы графа и динамическая загрузка кода запрещены. Зависимость может ссылаться только на уже существующую задачу того же workflow; циклы не создаются. Терминальный результат workflow выбирает его зарегистрированный root operation и сохраняет в durable task record.

## PostgreSQL: схемы и таблицы

Core владеет одной Atlas migration history, которая создаёт и проверяет следующие bounded-context schemas. Внутри схемы имена таблиц короткие; префикс `core_` и повторение имени схемы в имени таблицы не используются.

| Schema | Таблицы первой версии | Владелец и назначение |
|---|---|---|
| `access` | `users`, `bootstrap`, `credentials`, `groups`, `grants` | Идентичности и прямые уровни доступа. Единственный тип пользователя; `kind` и ролей нет. Группы задаются startup config. Отсутствующая/выключенная группа закрывает доступ, но не удаляет назначения и связи файлов. |
| `files` | `objects`, `memberships` | Неизменяемые байты, метаданные, физический S3 key, checksum, служебная revision и принадлежность статичным access groups. |
| `uploads` | `requests`, `staged` | Core idempotency/finalization state и непрозрачные временные S3 objects. Не хранит consumer-specific сессии, номера частей или предметные workflow. |
| `file_index` | `sets`, `members` | Поисковые наборы и membership; наборы не выдают доступ к файлу. |
| `engine_data` | `records` и `revision_seq` | Общая JSONB модель данных движков, ограниченная зарегистрированными engine/namespace capabilities. Собственных engine schemas/tables/migrations нет. |
| `coordination` | `runtime`, `instances`, `workflows`, `tasks`, `dependencies` | Единственная логическая система на БД, leases, durable workflow, динамические задачи и граф зависимостей. |

`access.sessions` хранит общий механизм отзываемых сессий использования одного конкретного credential. Запись привязана к `credential_id`; хранятся только хеш токена, principal через credential, сроки idle/absolute expiry и отметка отзыва. У сессий нет полей `browser`, `cookie`, CSRF или HTTP Origin. Внешний способ предъявления токена выбирает Presentation.

Все foreign keys, индексы, checks, владельцы объектов и grants явно заданы Atlas. Runtime login имеет только DML/sequence permissions, ограниченные перечисленными Core schemas; он не может менять DDL, grants, роли или Atlas history. Отсутствующий в configuration access group не удаляется каскадно и не даёт доступ.

Ранее существовавшие таблицы публикаций и Router targets удаляются из общей Core/coordination модели. Маршрут, активная цель и специфичные generation принадлежат Router и сохраняются в его namespace `engine_data.records`. Для безопасной активации Core предоставляет общую fenced/CAS-команду над зарегистрированной engine record: она сверяет текущую lease/fencing epoch и expected record revision в одной транзакции. Её параметры остаются нейтральными и не содержат `route_id`, `file_id` или publication-specific типов.

`system_id` удаляется из coordination rows: одно подключение к БД соответствует одной системе. Единая строка `coordination.runtime` сохраняет non-secret configuration fingerprint и монотонную epoch. Несовпадение fingerprint при активных leases запрещает startup; после остановки всех экземпляров новая конфигурация увеличивает epoch, а старые незавершённые задачи переводятся в безопасное терминальное состояние по правилам workflow.

## Оправдание полей и удаление лишнего

Каждое хранимое поле должно участвовать в проверяемом инварианте, API-представлении, CAS, аудитном требовании или восстановлении после сбоя. В частности:

- file object `revision` остаётся, поскольку защищает metadata CAS и помогает проверять cache invalidation; это не версия содержимого.
- upload request `request_hash` остаётся, чтобы один idempotency key нельзя было повторно применить к другому содержимому.
- `files.objects.updated_at`, `uploads.requests.updated_at` и `uploads.staged.updated_at` остаются как курсоры восстановления и очистки после неопределённого исхода S3/DB операции. У этих таблиц удалён неиспользуемый `created_at`.
- У `access.groups` удалён неиспользуемый `created_at`: существование и активность группы задаются конфигурацией, а отдельный аудит её создания не требуется.
- У `file_index.members` удалён неиспользуемый `added_at`: порядок и время добавления членства не входят в контракт поиска.
- У `coordination.runtime` удалён неиспользуемый `updated_at`: конфигурационное состояние полностью описывают fingerprint и epoch. У `coordination.instances` удалён дублирующий `heartbeat_at`: живость экземпляра задаёт единственный `lease_until`, продлеваемый Core.
- workflow/task lease, epoch и fencing token остаются для takeover и запрета записи устаревшего worker.
- engine record `payload_version`, `index_data`, `revision` и expiry остаются, поскольку поддерживают версию сериализации движка, разрешённый поиск, CAS/ABA safety и TTL.
- `file_index.sets` не хранит `created_by`: набором управляет его static management group, а отдельного audit требования в v1 нет.

Поля сверены с SQL-запросами и контрактами; regression test запрещает повторное появление удалённых operational timestamps и проверяет recovery index. Ни имя, ни дублирование префикса не являются достаточным основанием удалить поле, которое поддерживает указанный инвариант. Нет неявных defaults для размера payload, cache, lease, concurrency и хранения workflow result.

## Единые инварианты хранилища

- Go-код не содержит SQL DDL (`CREATE`, `ALTER`, `DROP`, schema grants). Только Atlas migration files определяют схему.
- Engine данные изменяются только через scoped Core contract; каждый запрос и batch привязан к зарегистрированной capability, проверяет размеры и разрешённые поля, применяет CAS и параметризованные запросы.
- Байты файлов остаются в S3. Core повторно проверяет актуальные права перед чтением/commit; отсутствие PostgreSQL проверки закрывает доступ, независимо от локального cache.
- S3 и PostgreSQL не считаются одной транзакцией. Операции состоят из повторяемых этапов с durable state/cleanup; неопределённый исход разрешается чтением состояния из PostgreSQL перед удалением байтов.
- Модули не обращаются к чужим namespaces и не выполняют междвижковые SQL JOIN. Межмодульные ссылки передаются как opaque IDs и разрешаются владельцем контракта.

## Приёмка

Схема принимается на свежей одноразовой PostgreSQL database: Atlas создаёт все schemas, таблицы, constraints, индексы и grants; Go sources не содержат DDL. Проверяются запрет/сохранение legacy database без её изменения, отсутствие retired `core_*` таблиц и `system_id`, независимая проверка прав доступа, файлы, staging recovery, file sets, cross-engine record isolation, CAS/ABA и отказ при неизвестной capability.

Workflow acceptance включает: несколько экземпляров на одной database; одинаковый fingerprint допускает совместную работу, отличающийся при живом lease отвергается; регистрация обязательна и уникальна; повтор idempotency key; динамическое добавление зависимых задач; запрет цикла/чужого workflow/неизвестного handler; получение результатов после restart; child-task commit атомарен с parent completion; delayed execution, retry, terminal failure, cancellation, lease takeover, stale fencing rejection, DB outage fail-closed и очищение по настроенной retention policy.

Архитектурная приёмка проверяет границы пакетов: `make lint-core-boundary` подтверждает независимость Core от всех соседних модулей и единственную точку импорта потребителями `core/presentation`; acceptance-тесты дополнительно проверяют DDD-границы внутри Core. Domain не импортирует framework/infra; application не импортирует SQL/AWS/pgx; только infrastructure содержит query/driver code; engine/worker/entrypoint imports не достигают infrastructure; у Core ровно один внешний facade/DI boundary. Интеграционные проверки выполняются только на изолированных disposable DB/S3 и очищают только созданные для них идентификаторы.
