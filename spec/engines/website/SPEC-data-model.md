# Snapshot-scoped flat data model and feature bindings


Status: target system-wide model/content and page-scoped placements, agreed 19 November 2026. Model-to-model relations and record-to-record relations are retired. This contract supersedes historical snapshot-scoped statements below.

## Product decisions

- One logical system owns one revisioned `dataModel`, shared by all pages.
- Content records, drafts, publication pointers and history are system-scoped and locale-specific; each record has a locale-specific ID. Translations are separate records linked by a stable translation ID. Pages share those records for a locale.
- Each page has an independent Website snapshot tree. A snapshot is exactly one immutable page version, identified by `page_id`; its payload has page structure, metadata, placements, typed bindings and feature dependency lock, but no route or URL.
- Structural model changes update the system-wide model revision, not page snapshots. Page structure/placement changes create a child snapshot only in that page's tree.
- `/site` owns page placements, feature arguments and direct typed `dataInputs` bindings. System-level model structure is shared. `/content` owns the Admin-managed system locale catalog/default locale, locale-specific record values, drafts, publication/history, and locale-specific page-snapshot editorial selections/order for placements.
- Public routes and route-to-artifact assignment belong exclusively to Router. A route has locale-specific artifact targets selected from the negotiated visitor locale; it receives completed single-page artifacts after prerender.

## Locale catalog and translated records

Content Admin manages the system locale catalog through a revisioned CAS operation. The catalog contains a non-empty set of canonical BCP 47 locale tags and exactly one `default_locale` from that set. Duplicate canonical tags and a default outside the set are invalid. The catalog revision participates in the content workspace and public build projections. A locale cannot be removed while it has draft/published records, page selections, or an active Router target; those references must first be explicitly unpublished or removed.

Each editorial record belongs to exactly one supported locale and has a server-generated record ID. A translation group uses a server-generated `translation_id`; it contains at most one record for each locale and cannot cross entity boundaries. A record without other locale translations is still an ordinary record in a translation group. Model cardinality, unique field validation, draft revision, publication pointer and history are evaluated per locale. Publishing one locale does not publish, unpublish, or mutate another locale.

Page selections/order are keyed by page snapshot and locale. A selection may only reference records of its own locale. Missing localized records are not replaced with another locale's values. Public route paths do not include locale; Router selects the locale-specific artifact target after locale negotiation.

## Model editor

`/site/data-model?snapshot=...` is a searchable model list. It shows model name, cardinality, field count, and whether its fields are referenced by feature bindings. The list supports grouping/filtering between collections and singleton models and sorting by name or field count. Every row opens:

`/site/data-model/:model?snapshot=...`

where `:model` is the stable generated entity key. The selected snapshot remains in the query string. Browser back/forward and the explicit return link preserve normal navigation and the shared `SiteWorkspace` draft.

The model page has one vertical scroll owner. It edits the model name, cardinality, and ordered fields. Field editing includes name, type, uniqueness, enum options, drag ordering, labelled handles, and named up/down controls. Deleting a model or field and changing a field type or cardinality use the existing confirmation flow and report affected feature bindings. Generated UUIDs are not displayed in visible interface text.

The model list and model page do not contain a relation tab, relation counter, relation dialog, connector, canvas, empty relation state, or disabled placeholder.

## Model structure

Fields support text, long text, integer, number, boolean, date, date/time, URL, email, enum, and media. Every editorial value is optional. The server validates supplied values by type and format, enum membership, uniqueness, media ownership/access, and the current singleton cardinality.

Changing a model from `many` to `singleton` is allowed only when both current draft and published state contain at most one record. A new singleton receives exactly one empty draft record. Clearing a singleton record preserves its record ID and removes supplied field values; clear remains a draft until explicit publication.

Record IDs are generated by the server and remain stable through sorting, publication, snapshot fork, and history restore. A record contains `id`, `translation_id`, `locale`, `entityId`, `sortOrder`, and `values`. Each locale variant has a distinct `id`; translated variants share `translation_id`.

## Feature data contract and bindings

Feature manifests remain format 2 and keep the existing runtime ABI. `dataInputs` declares `scalar`, `record`, or `collection` ports and typed output fields. A port maps directly to fields on one root entity. If a request endpoint or parameter is content data, it is an ordinary typed model field: `/content` edits the value and `/site` binds it to the feature's declared input. Origins, request slots, and per-placement request bindings are not registered or configured by the Website editor; request/response contracts and allowed origins belong to the feature manifest and runtime contract in [SPEC-feature-runtime.md](features/SPEC-feature-runtime.md).

Each placement's `DataInputBinding` contains:

- `inputKey`;
- `entityId`;
- `fieldId` for scalar ports;
- `fields` with `inputPath` and `fieldId` for record/collection ports;
- optional unique-field route lookup for record ports;
- optional detail SEO field mappings.

Snapshots and API payloads use only the flat model contract. Relation traversal, relation previews, relation validation, and `relationIds` are not part of the model. The owning Presentation decoder rejects unknown fields.

For a collection input, `/content` chooses all published records or an ordered subset for that placement. A detail record may resolve from a unique field and a path argument. Scalar and record inputs resolve one selected record, or the sole published singleton automatically.

## Persistence and runtime

Runtime resolves only published records and selected placement order for the negotiated locale. It does not follow record graphs. A feature receives scalar values, record objects, or ordered collection arrays assembled from direct fields of one model and that locale. Missing optional values are omitted or represented by empty records/arrays according to the input kind; values from another locale are never used.

System-wide model revisions and records are shared by all page snapshots in the system. Content drafts, locale-specific publication histories and published pointers use a system-wide locale scope; editorial selections/order use `(page_snapshot_id, locale, placement_id, input_key)`, while referenced locale-specific record IDs remain system-wide. Child page snapshots do not fork records or publication history. A model/schema or locale-catalog change validates all affected page bindings and locale references before commit; incompatible bindings block the change rather than silently changing a page. Cache/build identity includes page snapshot digest, system-model revision/digest, locale-catalog revision, locale-specific published Content revision and page-scoped selection revision.

## Permissions and failure behavior

Existing role guards, branch isolation, optimistic revisions, local recovery, unsaved-change protections, destructive confirmations, media ownership checks, and publication safeguards remain in force. A stale revision cannot partially save or publish content. Invalid model bindings or retired relation data cannot create a snapshot.
