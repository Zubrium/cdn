# Site editor and model-driven content

> **dev_v2:** Разделы об историческом редакторе страниц и маршрутов ниже служат только справочным материалом для миграции. Целевой контракт Website задан в разделе `Target: dynamic pages and template library` (строки 22–30) и [SPEC-website-engine.md](SPEC-website-engine.md); для модели, публикации, владения Router и runtime приоритет имеют соответствующие целевые спецификации. Не переносить в новый API legacy-маршруты и владение моделью данных на уровне snapshot.

Статус: целевой workflow страниц и шаблонов согласован; реализация и приёмка остаются открытыми. Целевой контракт плоской модели и записей определён в [SPEC-data-model.md](SPEC-data-model.md); семантика route targets — в [SPEC-route-targets.md](../router/history/SPEC-route-targets.md). Схемы CMS на уровне feature и связи между моделями/записями выведены из эксплуатации и не являются требованиями миграции.

Историческая навигация редактора: `Страницы`, `Версии`, `Бэкенд`, `Настройки сайта`, `Дизайн-система`, `Модель данных`; `/site/backend` не является частью target. Выбор снапшота, предупреждения и общая кнопка сохранения остаются в шапке workspace во всех режимах. `/site/pages` является списком, а не встроенным мастер-детейлом: одна запись объединяет данные страницы и её основной/дополнительные маршруты, отдельными записями показаны файловые маршруты. Список поддерживает поиск по названию, URL, стабильному ключу и отображаемому имени фичи, группировку по первому сегменту URL и сортировку только для отображения.

Страница открывается на весь экран по `/site/pages/:pageId` с вкладками `Фичи`, `Параметры`, `SEO`. Размещение открывается по `/site/pages/:pageId/features/:placementId`, где настраиваются аргументы фичи, контентные `dataInputs`, параметры страницы/query и detail-ссылки. Оба маршрута сохраняют query выбранного снапшота. Переходы создают отдельные browser history entries, поэтому кнопка браузера «Назад» возвращает на предыдущий список или страницу; на экранах также есть явные ссылки возврата. На телефоне список и выбранная страница являются отдельными URL-экранами; это сохраняет рабочий draft, но не создаёт искусственную вложенную навигацию.

Файловый маршрут создаётся из списка и открывается по `/site/pages/files/:routeId`. Он выбирает готовый публичный файл из `/media`, задаёт фиксированный URL и режим `inline`/`attachment`. Параметры пути, regex и catch-all для файлового маршрута недоступны. Точный серверный и публичный контракт описан в [SPEC-route-targets.md](../router/history/SPEC-route-targets.md).

Упорядоченные редакционные списки поддерживают drag-and-drop за отдельную ручку с подписью. Порядок фич на странице, выбранных записей размещения, записей модели, элементов массивных аргументов и скалярных/объектных полей формы контента, включая табличный вариант, сохраняется в существующих данных редактора. Кнопки «выше/ниже» остаются доступной альтернативой для клавиатуры и точного перемещения. Перетаскивание не запускается со ссылок, полей и кнопок внутри строки.

## Ownership

- `/site` owns the snapshot's structure: pages, routes, placements, SEO, design, the graphical data model, feature arguments, and typed `dataInputs` bindings from each placement to model entities and fields. All feature arguments are configured here.
- `/content` owns model records, local drafts, publication history, and record selection/order for each placement. It generates forms from the selected snapshot's flat model and edits only each record's own `values`.
- `/media` owns uploads, file metadata, and deletion. Other editors may pick an existing authorized file; they never upload a file into a feature or record.
- `/snapshots/branches` is the only place that assigns snapshots to statically configured branches. `/site` may select its working snapshot, but it has no branch picker or assignment action.

## Target: dynamic pages and template library

Целевая Website API создаёт страницы динамически; сервер генерирует стабильный UUID каждой страницы и её root snapshot. `/site/pages` показывает страницы настроенного сайта; создание синхронно завершает страницу в состоянии `ready` и возвращает её готовый root snapshot, создавая пустую страницу или копию точной текущей ревизии выбранного шаблона. Для страницы из шаблона пользователь задаёт имя, которое заменяет имя страницы в конфигурации шаблона. Создание не назначает URL: создание Router route и привязка artifact остаются отдельными workflow. У каждой страницы собственное дерево snapshots; общая модель данных сайта и записи не копируются в snapshots страниц.

The site-scoped template library has a separate full-screen editor, not an implicit mode of the page editor. It edits the reusable page name, SEO, ordered feature placements, feature arguments, typed `dataBindings`, exact feature versions/dependency lock, and free insertion slots supported by the placement contract. It does not edit routes, URLs, branches, site-wide data model, record values, or editorial selections. Slots allow adding any available feature into valid positions; they do not introduce shared HTML wrappers or lifecycle roots.

Creating a page from a template materializes its current configuration into an independent root snapshot. Later template edits or deletion do not change that page. Applying a template to an existing page is a separate explicit action: show a full replacement diff and warn that placement selections reset, then require confirmation. It creates a child snapshot in that page's tree, keeps the page ID and existing Router route bindings, and replaces page name, SEO, placements, arguments, and bindings. The parent, other pages, site-wide records and content values remain unchanged. The applied template ID and revision are audit provenance only; runtime does not depend on the template.

Template editing uses revision/digest compare-and-swap. Applying or creating from a template pins the exact current revision and revalidates feature versions, dependency closure, arguments, and bindings against the current site model. A stale revision, missing build, incompatible binding, or concurrent page/content change produces a controlled conflict without a partial page or snapshot. Unsaved template/page drafts and replacement confirmation follow the existing workspace warning and destructive-confirmation patterns.

## Model and placement editing

The flat model is part of an immutable snapshot configuration. `/site/data-model` is a searchable list of models and `/site/data-model/:model` is a full-screen model page identified by the stable generated entity key. The page edits the model name, cardinality, and ordered fields, with enum/unique controls, drag ordering, labelled handles, and named up/down alternatives. There is no canvas, relation tab, connector, relation inspector, or empty relation state. Generated IDs are not presented as editable or primary labels. A structural save creates a child snapshot and does not change the parent or branch assignment. Before removing or changing a bound field, the editor identifies affected bindings and requires an explicit decision.

Feature ZIP manifests use format 2. `arguments` defines values configured by `/site`; typed `dataInputs` defines only runtime input ports. Each placement binds a port directly to one model entity and stable field IDs and validates output type and route lookup against the pinned build. Relation paths and `relationIds` are rejected. The editor does not copy editorial values into arguments and does not choose records for a collection. The selected feature version and runtime ABI are part of the immutable placement contract.

Argument source controls match the existing route resolver: query values can populate a route-coercible scalar argument or an array of route-coercible scalars. Objects and arrays of objects remain literal arguments and use nested controls. When a route capture, query binding, or media argument binding becomes invalid after a manifest or route change, the editor keeps the saved value visible as a repairable warning. Build-registry loading, an empty registry, and a missing pinned build are distinct states; a missing build explains how to restore or register the immutable build.

Page routes remain serialized to the existing `path`, `static`, `param`, `regex`, and `catchAll` nodes. The editor accepts a complete URL/segment as text and offers a visual segment builder for static text, named parameters, an optional catch-all, and regex presets for integer, number, slug, UUID, and date. Raw regex2 input remains available as an expert mode. The editor previews captured values and rejects duplicate capture names, empty matching patterns, `/` inside a regex segment, invalid catch-all placement, and malformed values before save; the server remains authoritative.

Each placement groups configuration under `Data sources`: page/path and query arguments, model content, and public values supplied to the feature. When an endpoint depends on a record, `/content` edits its model field and `/site` binds that field to a typed `dataInputs` port; `/site` does not register origins or configure request bindings. The feature manifest declares request and response contracts, and feature code performs the request and parses the response, as specified in [SPEC-feature-runtime.md](features/SPEC-feature-runtime.md). Content bindings use readable model, field, and output names instead of generated IDs, describe the resulting projection, and state that actual records and their order are edited in `/content`. Stale direct bindings remain visible with an inline repairable warning after a route or model change.

The registry rejects format 1 and the retired manifest `content.*` CMS schema. There is no compatibility endpoint or data conversion for per-feature CMS records or `contentRelations`. Public form submission validation remains the explicit `form.submissionSchema` contract in the feature manifest.

## Record editing and publication

`/content` selects a snapshot and presents `many` models as record collections and each `singleton` model as one record form. A new singleton automatically receives one empty draft record and is not published until the user explicitly publishes it. Its form has no add, duplicate, reorder, or delete-record actions. Confirmed clear resets field values while retaining the record ID. Forms are generated from model field types; every CMS value may be omitted, while supplied values, uniqueness, and media ownership are validated. Record IDs are generated and remain stable across sorting and publication. Media fields select an existing file in `/media`.

Saving creates a revisioned content draft inside the same snapshot. Autosave and manual save retain local edits on network failures and revision conflicts. Publishing is explicit and updates the snapshot's public records and placement selections atomically; it does not create a structural snapshot. History restore creates a new draft and requires a separate publication. Only published records and selections are exposed to runtime, public HTML, and prerendering.

Collection bindings choose the entity and field projection in `/site`. `/content` then either uses all published records or an ordered list of selected record IDs for each placement. A catalog, detail page, and slider can therefore use the same `Product` records, with the slider showing a subset without duplicating product fields. Detail route lookup uses a bound unique model field.

## Shared workspace behavior

The site workspace uses one snapshot selection and one local structural draft across pages, versions, settings, design, and data-model views. It has a single explicit save that creates a child snapshot. Changing views or selecting another page preserves the draft; leaving the workspace, changing snapshots, or discarding a conflict requires an explicit decision. There is no persistent server-side structural draft. Content drafts and publication are independent of this structural save.

The pages list supports search across page/file names, routes, feature keys and labels; grouping by the first route segment; and display sorting by manual route priority, name, route, or type. Display sorting never changes route priority. Page routes are edited from the full-screen page editor; the route dialog accepts a complete root URL or one child segment and offers the existing visual segment builder and expert regex syntax. File routes are edited separately and cannot include dynamic segments. Deep links between `/site/pages`, a page, a feature placement, and a file route preserve the selected snapshot and local structural draft. Existing role checks, revision checks, media-owner checks, unsaved-change warnings, and destructive confirmations remain enforced.
