# Forms Engine: целевая спецификация

Статус: контракт Forms v2. Forms владеет схемами, сессиями посетителей и неизменяемыми ответами. Публичный HTTP-транспорт принадлежит Router Presentation; байты вложений проходят через Loader. Core остаётся единственной границей постоянного хранения и авторизации.

## Схемы и поля

Схема привязана к `snapshot_id` и содержит сгенерированный UUID `id`, стабильный `key`, монотонную `version` и `fields`. Изменение полей или ключа увеличивает версию; повторное сохранение идентичного содержимого не создаёт новую версию. Изменения защищены `expected_revision`. Административные операции со схемами требуют уровня `2` в Core-группе `forms_schemas`, чтение схем — уровня `1`; права на ответы проверяются независимо по `forms_submissions`.

Каждое поле — объект с обязательными `type` и `required`. Поддерживаемые типы: `text`, `email`, `number`, `boolean`, `select`, `file`. Разрешены только ограничения, относящиеся к типу:

- `text` и `email`: `min_length`, `max_length`, `pattern` (Go RE2, до 256 байт);
- `number`: `minimum`, `maximum`;
- `select`: от 1 до 128 уникальных `options`;
- `file`: `max_files` от 1 до 20, `max_file_bytes` и точный список `allowed_content_types`.

Имена полей соответствуют `^[a-z][a-z0-9_]{0,63}$`; схема содержит 1–128 полей. Неизвестные поля и ограничения отвергаются. File MIME types должны быть точными и безопасными для активного содержимого; HTML, JavaScript, SVG, XML и CSS запрещены. Формы и Router проверяют эти ограничения независимо на границе сохранения и при обработке запроса.

## Публичные маршруты и cookie

Посетитель не передаёт `snapshot_id`, `form_id`, версию схемы, access group, FileSet, Core file ID или Loader credential. Router route config закрепляет форму и ожидаемую версию. Перед записью Router проверяет соответствие действующей схеме; после изменения схемы старый route закрывает операции до явного обновления binding. Каждая зарегистрированная Forms operation использует exact route:

| Operation | Метод | Поведение |
|---|---|---|
| `public.form-session` | `POST` | Создать сессию или вернуть ещё активную сессию из cookie |
| `public.form-session` | `GET` | Прочитать состояние своей сессии |
| `public.form-session` | `DELETE` | Отменить незавершённую сессию и очистить cookie |
| `public.form-upload` | `POST` | Передать один raw file body через Loader; для формы `field` задаётся query параметром |
| `public.form-submit` | `POST` | Подтвердить значения формы с `Idempotency-Key` |

Сессия — постоянная запись Forms, привязанная к точному snapshot/form/schema version. Forms создаёт криптографически случайный capability token длиной 256 бит и сохраняет только его SHA-256. Router извлекает токен из cookie и передаёт operation в типизированном envelope; cookie-имя, CSRF boundary и HTTP-заголовки не входят в Core или Forms Engine.

Router устанавливает host-only cookie без `Domain`, `Path=/`, `HttpOnly`, `SameSite=Strict`, истечением по TTL сессии. `Secure` задаётся явной конфигурацией. При `Secure=true` используется имя `__Host-zubrium-form-<form_id>`; иначе `zubrium_form_<form_id>`. Token никогда не возвращается в JSON и не попадает в URL. Ответы сессии и формы всегда `Cache-Control: no-store`. Неизвестная, отменённая или истёкшая сессия отвечает без раскрытия существования закрытых данных и удаляет устаревшую cookie там, где она известна. После успешного submit cookie сохраняется, чтобы повтор с тем же ключом идемпотентности мог получить прежнюю квитанцию, если первый ответ потерялся; `DELETE` очищает cookie, а создание следующей сессии заменяет её.

Session/submit operations должны собираться вместе; публичная Forms-сессия требует явной cookie-конфигурации. Загрузка без привязки к форме может работать как отдельный Loader route. Form-bound upload дополнительно требует Forms, формы и версии, FileSet, access group, положительный лимит байтов и MIME allowlist. Новый Core file остаётся приватным. Отдельный exact GET route нужен, чтобы публично отдать файл.

## Загрузка вложений и подтверждение

Клиент отправляет один raw file body на form-bound upload route и указывает `field=<field_id>`. Имя файла, группа доступа, FileSet и пределы приходят только из route config. Forms проверяет cookie capability, активную сессию, закреплённую схему, тип поля, лимиты количества/размера и MIME. Router повторно проверяет сервисный доступ к destination group и FileSet, ограничивает тело, пишет его в приватный staging-файл (`0600` в owner-only каталоге), считает SHA-256 и передаёт данные Loader. Loader единственный создаёт Core file.

После Loader commit Forms проверяет созданный файл через Core и фиксирует attachment reservation в сессии. Затем Router добавляет файл в настроенный FileSet. Если индексирование завершилось ошибкой, повтор с тем же ключом завершает добавление без второй копии; уже завершённая форма-сессия сохраняет attachment. Конфигурация задаёт отдельные ограничения concurrency и общего объёма staging. Router не реализует rate limiter: публичный listener нужно прятать за внешним proxy, настройка которого является ответственностью deployer.

Сессия имеет состояния `active`, `submitting`, `submitted`, `cancelled`. Upload reservation получает стабильный ID и idempotency hash. Повтор с тем же ключом и параметрами возвращает reservation; несовпадение формы, поля, типа, группы, размера или содержимого приводит к конфликту. Для публичного загрузочного запроса обязателен `Idempotency-Key`; изменённые байты под тем же Loader ключом отвергаются.

Перед сохранением ответа Forms повторно валидирует все поля и каждую ссылку на attachment. Неизвестные поля, неверный тип, отсутствующее обязательное значение, чужой/незавершённый attachment, повтор одного attachment или изменённая схема отклоняются. Успешное подтверждение атомарно резервирует в durable session ID, fingerprint, проверенные значения, attachment IDs и дату ответа, затем идемпотентно создаёт неизменяемую submission и переводит сессию в `submitted`. Повтор того же ключа и fingerprint возвращает прежнюю квитанцию; другой payload даёт конфликт. Состояние `submitting` восстанавливается cleanup-процессом после рестарта.

Пользователь может возобновить сессию после перезагрузки страницы до истечения TTL. TTL — от 1 минуты до 24 часов. При истечении или изменении схемы незавершённая сессия отменяется, отправка запрещается, временные файлы и зарегистрированные вложения очищаются повторяемой задачей. При недоступности Core операция завершается fail-closed. Пересечение отмены/истечения с upload или submit сериализуется CAS по записи сессии: после перехода в `submitting` нельзя отменить отправку, а upload не может начать новую операцию.

## Ответы и права

Submission содержит `form_id`, `schema_version`, статус, неизменяемые `values`, дату и revision. Чтение и экспорт требуют уровня `1` в группе `forms_submissions`; смена статуса и удаление — уровня `2` в той же группе. Эти операции не требуют доступа к `forms_schemas`, чтобы оператор ответов мог работать независимо от редактора схем. Изменение статуса не меняет ответы. Редактирование отправленных ответов отсутствует. Удаление требует обычного явного подтверждения и актуальной revision, затем окончательно удаляет submission и все его attachments как Core files, включая их связи с группами и FileSet. Core revisions и CAS обеспечивают повторяемое удаление и защиту от конкурирующих изменений. Ответы хранятся бессрочно до явного удаления.

CSV-экспорт проходит курсором по доступным записям с теми же фильтрами `snapshot_id`, `form_id` и `state`, что и список. CSV использует фиксированные столбцы `id`, `form_id`, `schema_version`, `state`, `created_at`, `values_json`; последнее поле содержит JSON-объект ответов. Формульные строки рекурсивно получают префикс `'` до сериализации. Экспорт целиком собирается до HTTP-ответа: при превышении `forms_api.export_max_rows` (1–10000) или `forms_api.export_max_bytes` (1024–67108864) сервер возвращает `413 export_limit_exceeded` без частичного CSV. Байтовый лимит ограничивает итоговый CSV и промежуточно сериализованные значения. `forms_api.export_max_concurrent` (1–16) ограничивает число одновременных экспортов; если все слоты заняты, API возвращает `429 export_busy` и `Retry-After`. Каждый cursor page читается отдельным вызовом Core; при параллельных добавлениях или смене статуса состав экспорта отражает последовательность прочитанных страниц и не является транзакционным snapshot. Если нужен срез без конкурентных изменений, экспорт следует повторить после их завершения.

## Административный API

- `GET /api/v2/admin/forms/schemas?snapshot_id=...` — страница схем;
- `GET /api/v2/admin/forms/schemas/{schema_id}?snapshot_id=...` — схема;
- `PUT /api/v2/admin/forms/schemas` — создание или обновление схемы с `expected_revision`;
- `GET /api/v2/admin/forms/submissions` и `GET /.../{submission_id}` — ответы;
- `GET /api/v2/admin/forms/submissions/export?snapshot_id=...&form_id=...&state=...` — полный CSV для выбранных фильтров;
- `PATCH /.../{submission_id}/status` — изменение статуса через CAS;
- `DELETE /.../{submission_id}?snapshot_id=...` с `If-Match` — окончательное удаление.

Сохранение схемы и статуса защищено CSRF при cookie-auth. Admin API не предоставляет публичную сессию, не возвращает upload capability и не принимает файлы напрямую. Полный HTTP контракт находится в [OpenAPI](../../presentation/openapi/forms.yaml); публичные cookie-маршруты — в [Router OpenAPI](../../presentation/openapi/router.yaml).

Admin UI разделён на `/forms` для схем и `/submissions` для ответов. Каждый маршрут требует уровня `1` только в своей группе: `forms_schemas` для схем и `forms_submissions` для ответов; создание и изменение схем требуют уровня `2` в `forms_schemas`, а статус и удаление ответов — уровня `2` в `forms_submissions`. Ни один из этих маршрутов не требует членства в другой группе. Редактор схем предлагает только явные типы и их ограничения, генерирует UUID схемы на сервере и использует `expected_revision` при записи. Изменение ключа или полей предупреждает о новой версии и о закреплённых версиях Router; автоматической смены Router bindings нет. Schema ID и версия показываются для копирования в явную конфигурацию маршрута. Для каждого поля оператор задаёт стабильный ключ `^[a-z][a-z0-9_]{0,63}$`; ответы проверяются по этим ключам.

## Приёмка

Проверить typed-field validation каждого типа и невалидных ограничений; Schema CAS и versioning; явное route binding и exact-match; cookie `HttpOnly`/`SameSite`/`Secure` и очистку; создание, чтение, resume и отмену сессии; raw upload через Loader с MIME/size/access checks; idempotent upload и submit; повторы после рестарта в `submitting`; смену схемы, истечение, отмену и очистку; запрет чужих и незавершённых файлов; immutable response; права администратора; удаление ответа и всех вложений; CSV-паритет с фильтрами списка, экранирование формул, лимиты строк/байтов, отказ без частичного файла и обработку повреждённого курсора. Для PostgreSQL/S3 использовать уникальную disposable среду. Проверки с публичной загрузкой должны запускаться только через Router и учитывать, что rate limiting требует внешнего deployment proxy.
